# 环境管理客户端方案 v1

本文档定义 `DysonSphereBox/` 客户端环境管理页的产品、前端和本地文件方案。环境管理页聚合 **Mod、蓝图、存档** 三类本地资源：

- Mod 由客户端维护一套“资源库 + 启用状态”；蓝图由客户端维护“资源库 + 客户端目录树 + 真实蓝图相对目录”。用户在环境页中启用时，客户端把资源库中的文件同步到《戴森球计划》对应本地目录；禁用时移除由客户端同步出去的文件。
- 蓝图额外支持类 Windows 文件夹结构。这个文件夹结构必须贴合戴森球计划自己的蓝图目录逻辑：启用蓝图时，在游戏蓝图根目录下创建对应真实文件夹并写入蓝图文件。
- 存档不建立虚拟目录，直接读取《戴森球计划》的存档目录并操作真实文件。
- 蓝图和存档支持重命名；Mod 第一版不支持用户重命名，显示名来自 Mod 清单或文件夹兜底。所有重命名必须走服务层，不能让前端直接拼接路径或直接改文件。

当前 Figma local 的环境页设计已经形成基本信息架构：页面标题为“环境”，顶部标签为“模组 / 蓝图 / 存档”；模组是平铺卡片；蓝图是带面包屑、文件夹和拖拽移动的平铺目录；存档是直接读取本地列表的卡片视图。本方案在该设计基础上补齐客户端真实落地规则。

## 1. 目标与边界

### 1.1 用户目标

面向已经安装或准备管理本地资源的玩家，环境页要让用户快速完成：

- 查看当前客户端资源库中的 Mod、蓝图，以及当前游戏存档。
- 启用或禁用某个 Mod、某个蓝图，让它进入或离开游戏实际目录。
- 用文件夹组织蓝图，像 Windows 资源管理器一样进入文件夹、返回上级、拖拽移动、重命名。
- 直接管理存档文件，包括刷新、打开目录、重命名、导入、导出、删除。
- 在游戏路径未配置、BepInEx 不可用、目标文件冲突、权限不足等情况下得到明确反馈。

### 1.2 不做的事情

- 环境页不是模组市场。现有“模组”页继续负责远端整合包搜索、安装、卸载、BepInEx 前置引导；环境页负责本地文件级启用/禁用和资源组织。
- 环境页不直接修改服务端数据，也不依赖账号体系。
- 存档不做客户端虚拟分组。存档列表以真实游戏存档目录为准。
- 禁用操作只删除由客户端环境管理同步出去的文件。未被本系统登记过的手动文件不自动删除。
- 首次打开环境页时必须提供“同步本机现有内容”的入口，把游戏目录里已经存在的 Mod、蓝图和存档纳入客户端可见范围。

| --- | --- | --- |

## 3. 本地目录与数据模型

### 3.1 客户端资源库

客户端需要在应用数据目录下建立环境资源库。运行时数据库目前跟随 exe 同级目录，环境资源库建议也由后端集中解析，避免前端硬编码。

建议目录：

```text
{AppDataRoot}/
  plugins/
    {modFolderName}/
      ...
  blueprints/
    {真实蓝图相对目录}/
      {blueprintFileName}
  environment/
    mods/
      metadata/
        {modId}/
          manifest.json
          sync-manifest.json
    blueprints/
      metadata/
        {blueprintId}/
          manifest.json
          sync-manifest.json
      tree/
        manifest.json
    snapshots/
      sync/
      delete/
      save/
    import-tmp/
```

`AppDataRoot` 第一版固定落在 exe 同级 `appData/` 下，满足便携版需求。Mod 资源库使用 `{AppDataRoot}/plugins/{modFolderName}`，该目录必须和游戏侧 `{GameDir}/BepInEx/plugins/{modFolderName}` 保持镜像关系；蓝图资源库使用 `{AppDataRoot}/blueprints/{真实蓝图相对目录}/{blueprintFileName}`，该路径必须和游戏侧 `{BlueprintRoot}/{真实蓝图相对目录}/{blueprintFileName}` 保持镜像关系。环境管理自己的元数据放在 `{AppDataRoot}/environment/.../metadata` 下，不能写进 Mod 或蓝图镜像目录，避免破坏“客户端镜像和游戏目录内容完全一致”的判断。

资源库扫描只读取 `{AppDataRoot}/plugins`、`{AppDataRoot}/blueprints` 和数据库记录；必须忽略 `{AppDataRoot}/environment/import-tmp`、`snapshots`、`metadata` 等环境管理内部目录，避免半成品或恢复快照出现在用户资源列表中。

### 3.2 目录定位策略

Mod 目录定位基于现有游戏路径配置：

- 配置项：`Game/StartupFilePath`
- 校验：`EnvironmentService.CheckDysonSphereExe`
- 自动定位：`EnvironmentService.LoadOrInitDysonSphereExe`
- 同步根：`{GameDir}/BepInEx/plugins`

蓝图和存档目录不依赖游戏安装目录推导，优先按当前 Windows 用户文档目录自动查询。浏览器检索到的公开资料和社区说明一致指向：

| 类型 | Windows 默认目录 | 说明 |
| --- | --- | --- |
| 蓝图 | `%USERPROFILE%\Documents\Dyson Sphere Program\Blueprint` 或 `%USERPROFILE%\My Documents\Dyson Sphere Program\Blueprints` | 游戏蓝图书籍本质上可以表现为目录结构；不同资料中 `Blueprint` / `Blueprints` 命名可能不一致，客户端需要兼容探测 |
| 存档 | `%USERPROFILE%\Documents\Dyson Sphere Program\Save` | 官方 FAQ、Steam 社区和 PCGamingWiki 均指向用户文档目录下的 `Save` |

目录依据：

| 来源 | 可采纳结论 |
| --- | --- |
| [《戴森球计划》蓝图版本官方公告](https://store.steampowered.com/news/app/1366540/view/5632298429345135213?l=schinese) | 蓝图系统是游戏官方能力，客户端环境管理应服从游戏蓝图库的组织方式 |
| [Steam 蓝图导入指南](https://steamcommunity.com/sharedfiles/filedetails/?id=2749555287) | 工厂蓝图 `.txt` 文件放入 `Documents\Dyson Sphere Program\Blueprint` |
| [戴森球计划知识库蓝图页](https://dsp-kb.top/zh-TW/blueprints/blueprints.html) | 下载后的工厂蓝图放入 `Dyson Sphere Program\Blueprint` 目录 |
| [DSPBluePrints 蓝图仓库](https://github.com/DSPBluePrints/FactoryBluePrints) | 蓝图包应连同文件夹一起放入游戏默认蓝图文件夹 |
| [Steam 蓝图书讨论](https://steamcommunity.com/app/1366540/discussions/0/3055114073648261028/) | 蓝图书在文件系统层面就是蓝图目录下的文件夹，移动、重命名文件夹会反映到游戏蓝图界面 |

实现原则：官方公告确认蓝图系统属于游戏内置能力；目录层级以游戏实际暴露的蓝图文件夹行为为准。也就是说，客户端不是自创一套蓝图分类，而是镜像和管理 `BlueprintRoot` 下的真实文件夹结构。

蓝图目录定位需要形成“资料依据 + 本机验证 + 用户确认”的闭环。公开资料只能证明游戏蓝图位于用户文档下的 `Dyson Sphere Program\Blueprint` 或兼容目录，最终写入前仍要以本机扫描结果和用户确认目录为准：

- `ResolveBlueprintRoot()` 返回 `path`、`source`、`confidence` 和 `needConfirm`。
- 已保存配置命中且目录存在时，`confidence = confirmed`。
- 通过 Known Folder 自动探测命中且目录内存在蓝图文件、蓝图子文件夹或游戏生成痕迹时，`confidence = detected`。
- 仅根据默认候选路径推断、且目录尚不存在时，`needConfirm = true`；前端必须让用户确认“使用此蓝图目录”后才允许创建和写入。
- 用户手动选择目录后保存到 `Game/BlueprintDirPath`，后续按已确认目录处理。

后端建议实现独立解析器：

```text
ResolveModRoot()       -> 读取 Game/StartupFilePath，返回 {GameDir}/BepInEx/plugins
ResolveBlueprintRoot() -> 从用户文档目录探测 Dyson Sphere Program/Blueprint 或 Blueprints
ResolveSaveRoot()      -> 从用户文档目录探测 Dyson Sphere Program/Save
```

蓝图和存档目录解析顺序：

1. 读取已保存配置。配置存在且目录有效时直接使用。
2. 查询 Windows Known Folder `FOLDERID_Documents`，拼接 `Dyson Sphere Program`。
3. 同时检查 `Blueprint`、`Blueprints`、`Save`、`save` 等大小写和单复数候选。
4. 如果候选目录不存在但父目录 `Dyson Sphere Program` 存在，蓝图目录允许按需要创建；存档目录默认不自动创建，优先提示未发现存档目录。
5. 如果仍未找到，前端提供“选择目录”，保存到配置后再次扫描。

配置项作为自动定位失败后的兜底：

| 配置组 | Key | 说明 |
| --- | --- | --- |
| `Game` | `BlueprintDirPath` | 用户手动指定的蓝图真实目录 |
| `Game` | `SaveDirPath` | 用户手动指定的存档真实目录 |

前端遮罩也要按资源类型拆分：

- Mod：游戏路径无效或 BepInEx 不可用时阻止启用/禁用，并提供“前往设置”或“安装 BepInEx”。
- 蓝图：蓝图目录未定位时只阻止蓝图启用/禁用/导入到游戏目录，不影响客户端目录树浏览。
- 存档：存档目录未定位时显示目录未找到，提供“重新扫描”和“选择目录”。

### 3.3 目标目录约定

| 类型 | 资源库 | 同步目标 |
| --- | --- | --- |
| Mod | `{AppDataRoot}/plugins/{modFolderName}` | `{GameDir}/BepInEx/plugins/{modFolderName}` |
| 蓝图 | `{AppDataRoot}/blueprints/{真实蓝图相对目录}/{安全文件名}.txt` | `{BlueprintRoot}/{真实蓝图相对目录}/{安全文件名}.txt` |
| 存档 | 无虚拟资源库 | `{SaveRoot}` 下的真实存档文件 |

### 3.4 核心数据表

建议新增环境管理领域模型，独立于现有 `mod_installed_packages`，避免混淆“远端整合包安装记录”和“环境页资源库项目”。

`environment_items`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 本地资源 ID，建议 UUID |
| `kind` | string | `mod` / `blueprint` / `blueprint_folder` |
| `name` | string | 用户可见名称；Mod 创建后由清单或文件夹名生成，第一版不允许用户改名 |
| `parent_id` | string nullable | 蓝图文件夹父节点；Mod 永远为空 |
| `state` | string | `default` / `enabled` / `disabled` / `conflict` / `missing` |
| `source_type` | string | `import_zip` / `import_dir` / `quick_text` / `marketplace` / `detected` |
| `library_path` | string | 资源库相对路径；Mod 指向 `plugins/{modFolderName}`，蓝图指向 `blueprints/{真实蓝图相对目录}/{文件名}` |
| `origin_path` | string | 首次同步或导入时的来源路径；用于诊断，不作为后续删除依据 |
| `blueprint_relative_dir` | string | 蓝图相对真实目录，例如 `科研建筑/矩阵`；非蓝图为空 |
| `size_bytes` | int64 | 资源大小 |
| `metadata_json` | json | Mod/蓝图扩展信息；Mod 中保存解析后的 `manifest.json`、显示名、版本、依赖、主页等 |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |

`environment_synced_files`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uint | 本地自增 |
| `item_id` | string | 归属资源 |
| `kind` | string | `mod` / `blueprint` |
| `source_path` | string | 资源库源文件绝对路径 |
| `target_path` | string | 游戏目录目标文件绝对路径 |
| `target_root_path` | string | 同步时使用的 ModRoot 或 BlueprintRoot |
| `relative_path` | string | 相对同步目标根的路径 |
| `sha256` | string | 同步时目标文件校验 |
| `file_size` | int64 | 文件大小 |
| `synced_at` | datetime | 最近同步时间 |

Mod 同步记录以目录镜像为核心：`source_path` 位于 `{AppDataRoot}/plugins/{modFolderName}`，`target_path` 位于 `{GameDir}/BepInEx/plugins/{modFolderName}`，`relative_path` 是相对 `{modFolderName}` 的路径。启用后的目标目录文件集合、相对路径、文件大小和 hash 必须与资源库镜像目录一致。第一版同步记录可以只记录文件，但镜像复核必须同时比较目录集合；资源库中存在的空目录也要创建到游戏侧，游戏侧多出的空目录也属于额外项，需要进入冲突或覆盖计划。

蓝图同步记录也以镜像为核心：`source_path` 位于 `{AppDataRoot}/blueprints/{真实蓝图相对目录}/{文件名}`，`target_path` 位于 `{BlueprintRoot}/{真实蓝图相对目录}/{文件名}`，`relative_path` 是相对蓝图根目录的路径。启用后的游戏侧蓝图文件必须与客户端镜像文件一致。

目标根目录变化规则：

- `target_path` 只能在仍位于当前解析出的 `target_root_path` 下时参与启用、禁用、删除和恢复。
- 如果用户更换了游戏目录、蓝图目录或手动配置目录，`RefreshManagedState` 必须先比较当前根目录和同步记录中的 `target_root_path`。
- 根目录不一致时，不得按旧绝对路径执行删除；item 标记为 `disabled` 或 `conflict`，前端提示“目标目录已变化，需要重新启用到新目录或打开旧目录手动处理”。
- 用户明确选择“打开旧目录”时只打开文件管理器，不执行删除。
- 重新启用到新目录时，使用客户端镜像作为来源，生成新的 `target_root_path`、`target_path` 和同步记录。

`environment_operations`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uint | 操作记录 |
| `operation` | string | `enable` / `disable` / `rename` / `import` / `delete` / `move` |
| `kind` | string | 资源类型 |
| `item_id` | string | 资源 ID |
| `status` | string | `pending` / `running` / `committed` / `rollback` / `success` / `failed` / `recovered` |
| `message` | string | 用户可读状态 |
| `detail_json` | json | 文件数量、失败路径、冲突路径、预期写入路径、回滚动作等 |
| `created_at` | datetime | 创建时间 |

`environment_operations.detail_json` 至少要能表达：

| 字段 | 说明 |
| --- | --- |
| `plan` | 源路径、目标路径、相对路径、预期 hash、动作类型 `copy/delete/move/rename` |
| `conflicts` | 冲突路径、冲突类型、所属 item、客户端镜像 hash、游戏侧 hash、可选动作 |
| `user_decision` | 用户选择的 `overwrite/skip/merge/rename/update_client_mirror/restore_game/open_only` |
| `snapshots` | 快照路径、原始路径、原始 hash、恢复动作 |
| `locks` | 本次操作持有的 item、目标路径或蓝图子树锁 |
| `result` | 成功数量、失败数量、失败路径、最终状态 |

`environment_save_index`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 本次扫描中的本地 ID，建议基于 `SaveRoot` 相对路径 hash 生成 |
| `name` | string | 存档显示名 |
| `file_path` | string | 存档真实绝对路径 |
| `relative_path` | string | 相对 SaveRoot 的路径 |
| `sha256` | string | 最近一次索引时的校验值，可按性能策略延迟计算 |
| `file_size` | int64 | 文件大小 |
| `last_modified_at` | datetime | 文件修改时间 |
| `last_seen_at` | datetime | 最近扫描发现时间 |
| `status` | string | `normal` / `missing` / `locked` / `invalid` |

存档索引只是最近扫描缓存，不是存档身份的最终权威。存档页面、重命名、删除、导入和导出都必须先以 `SaveRoot` 实时扫描结果为准，再更新 `environment_save_index`。如果玩家在游戏外重命名了存档，下一次扫描以新文件名和新相对路径生成当前列表；旧索引只能作为历史诊断或重命名辅助匹配，不能继续驱动 UI 展示一个已经不存在的存档。

`syncing` 是前端和 operation 派生出来的临时展示状态，不写入 `environment_items.state`。`changed` 是扫描预览和状态复核结果，也不写入 `environment_items.state`。当真实目录与客户端镜像不一致时，列表接口可以在 DTO 中返回 `syncHealth = syncing/changed` 或 `conflictReason`，但数据库 item 仍保持原本的 `enabled` / `disabled` / `conflict` 状态，直到真实操作完成或用户选择处理方式。

## 4. 首次同步与现有文件纳管

### 4.1 触发时机

环境页不能假设所有资源都由客户端导入。用户可能已经手动安装过 Mod、在游戏里保存过蓝图，或已有大量存档。因此需要独立的首次同步流程。

触发方式：

| 触发 | 行为 |
| --- | --- |
| 首次进入环境页 | 自动执行轻量扫描，只统计数量和可同步项，不立即复制大文件 |
| 点击“同步本机内容” | 弹出同步预览，用户确认后纳管 |
| 点击标签页刷新 | 重新扫描当前类型，并提示新发现内容 |
| 更换游戏路径或文档目录 | 清空当前扫描缓存，重新执行轻量扫描 |

前端建议在环境页顶部或每个标签空态中展示：

```text
发现本机已有 6 个 Mod、42 个蓝图、3 个存档。同步后可在客户端中管理。
```

按钮文案使用“同步本机内容”，不要使用“导入全部”，避免用户误解为会移动或删除原文件。

### 4.2 同步模式

首次同步分为三种模式：

| 类型 | 模式 | 说明 |
| --- | --- | --- |
| Mod | 复制进客户端资源库 + 补同步记录 | 游戏目录中的现有 Mod 会复制到资源库；原目标文件保留，并登记为已启用 |
| 蓝图 | 复制进客户端镜像资源库 + 按真实目录还原客户端目录树 + 补同步记录 | 真实蓝图目录中的文件夹会映射为客户端目录树；文件复制到 `{AppDataRoot}/blueprints` 并登记为已启用 |
| 存档 | 实时扫描 + 最近索引，不复制 | 存档仍以真实 SaveRoot 为权威，客户端只保存最近扫描信息 |

这三个模式有意不同：

- Mod 和蓝图需要客户端镜像副本，才能在禁用后仍保留客户端内的资源，并支持再次启用。
- 蓝图目录树不是纯 UI 虚拟概念，它必须能映射回戴森球计划蓝图根目录下的真实相对路径。
- 存档文件通常较大且有损坏风险，不应该在首次同步时复制或搬迁；客户端只纳入索引。
- 禁用 Mod/蓝图时只能处理 `environment_synced_files` 中登记过的文件，避免误删手动文件。

### 4.3 首次同步状态

新增同步预览 DTO：

| 字段 | 说明 |
| --- | --- |
| `kind` | `mod` / `blueprint` / `save` |
| `detectedCount` | 扫描发现数量 |
| `managedCount` | 已被客户端纳管数量 |
| `newCount` | 新发现、未纳管数量 |
| `conflictCount` | 命名或目标冲突数量 |
| `items` | 预览项列表 |

预览项状态：

| 状态 | 说明 |
| --- | --- |
| `new` | 可纳管的新资源 |
| `managed` | 已经在客户端资源库或索引中 |
| `changed` | 已纳管但真实文件发生变化 |
| `conflict` | 与现有客户端 item 或同步记录冲突 |
| `ignored` | BepInEx 框架文件、游戏生成缓存或不支持的文件 |

### 4.4 Mod 首次同步

扫描范围：

```text
{GameDir}/BepInEx/plugins
```

识别规则：

- 跳过 BepInEx 核心目录 `core`、`cache`、`interop`、`LogOutput.log` 等框架运行产物。
- 第一版只把 `BepInEx/plugins` 作为 Mod 本体管理范围。
- 优先把 `plugins` 下的一级目录识别为一个 Mod，并把该目录下所有文件作为该 Mod 的完整文件集接管。
- 第一版不支持裸露 `.dll` 文件作为 Mod 纳管。扫描时将其标记为 `ignored` 并提示用户先放入独立 Mod 文件夹；导入裸 DLL 时返回不支持原因，不创建资源库项目。
- `patchers` 不纳入第一版普通 Mod 启用/禁用范围。它属于更底层的预加载补丁目录，后续只有在安装记录明确声明时才作为高级能力处理。
- `config` 不纳入第一版 Mod 本体范围。配置文件通常是用户设置，禁用 Mod 时默认保留，不复制、不删除。
- 如果目录中存在 `manifest.json`、Thunderstore `README`、`icon.png` 或 DLL 元数据，可提取名称、作者、版本；提取失败则使用目录名或文件名。

全额接管规则：

- 一个 Mod 一旦被纳管，候选 Mod 根目录下的所有文件都复制进 `{AppDataRoot}/plugins/{modFolderName}`，形成该 Mod 的虚拟文件目录架构。
- 启用时按照虚拟文件目录架构把 `{AppDataRoot}/plugins/{modFolderName}` 完整复制到 `{GameDir}/BepInEx/plugins/{modFolderName}`，而不是只同步 DLL 或 `manifest.json`。
- 第一版不支持单文件 DLL Mod；所有 Mod 必须以 `{modFolderName}/...` 目录形式进入客户端镜像和游戏 `plugins` 目录。
- Thunderstore 包或 zip 导入时，先识别包根 `packageRoot`，再识别实际应落到 `BepInEx/plugins` 的 Mod 文件根 `modRoot`。`packageRoot/manifest.json` 用于元数据，`modRoot` 下所有文件作为同步文件集。
- 如果包根包含 `plugins/` 子目录，则 `plugins/` 下每个一级目录可识别为独立 Mod；如果只有一个根级 Mod 文件集，则整体识别为一个 Mod。
- `patchers`、`config` 等目录即使出现在 Thunderstore 包中，第一版也不写入游戏目录；导入预览中标记为 `ignored` 并提示用户。

Mod 元数据优先读取 `packageRoot/manifest.json`；如果没有包根清单，再读取 `modRoot/manifest.json`。这里的 `manifest.json` 指 Thunderstore/Mod 包清单，不是客户端资源库 `{modId}/manifest.json`。示例字段：

```json
{
  "name": "NebulaMultiplayerMod",
  "description": "With this mod you will be able to play with your friends in the same game!",
  "version_number": "0.9.22",
  "dependencies": [
    "xiaoye97-BepInEx-5.4.17",
    "nebula-NebulaMultiplayerModApi-2.1.0"
  ],
  "website_url": "https://github.com/NebulaModTeam/nebula"
}
```

解析规则：

- `name` 作为默认显示名，写入 `environment_items.name`；字段缺失、为空或 manifest 缺失时使用 Mod 文件夹名。Mod 第一版不允许用户重命名。
- `version_number` 作为卡片版本号，写入 `metadata_json.versionNumber`；字段缺失、为空或格式异常时显示“未知版本”。
- `description`、`dependencies`、`website_url` 原样保存到 `metadata_json.manifest`，用于右键“查看详情”。
- 原始 manifest 内容也保存到资源库 item 的元数据中，便于后续重新渲染详情或排查导入来源。
- `description` 缺失时详情显示“暂无描述”，`dependencies` 缺失时显示“无依赖信息”，`website_url` 缺失时不展示链接。这些属于正常兜底，不显示为解析错误。
- manifest JSON 格式错误时不阻止纳管，但记录解析错误，卡片退回文件夹名或文件名，版本显示“未知版本”。

纳管流程：

1. 解析 `plugins` 下的 Mod 根目录，生成候选项。
2. 对每个候选项递归枚举完整文件集，计算相对路径集合和文件 hash。
3. 读取候选项根目录的 Mod `manifest.json`；如果候选项来自导入包，则按 `packageRoot/manifest.json` 优先，提取 `name`、`version_number` 和详情元数据。
4. 写入 `environment_operations`，状态为 `pending`，记录候选 Mod 根目录、目标资源库目录、文件清单和预期 hash。
5. 把候选 Mod 根目录下所有文件复制到 `{AppDataRoot}/plugins/{modFolderName}` 的临时目录，保留相对目录结构，并校验文件集合、大小和 hash。
6. 复制和校验全部成功后，在数据库事务中创建 item，`source_type = detected`，`state = enabled`，并对每个真实目标文件写入 `environment_synced_files`，`target_path` 指向当前游戏目录中的既有文件。
7. 如果复制失败或校验失败，不创建 item，不写同步记录；清理临时目录，只把失败信息写入 `environment_operations` 和同步预览结果。

重要边界：

- 首次同步不移动、不删除游戏目录中的原 Mod。
- 之后用户点击禁用时，才根据同步记录删除游戏目录里的目标文件。
- 如果目标文件在首次同步后被手动修改，禁用时按“文件被修改”规则保留并提示。

### 4.5 蓝图首次同步

扫描范围：

```text
{BlueprintRoot}/**/*.txt
{BlueprintRoot}/**/*.bp
```

第一版首次同步默认只自动纳管 `.txt` 和 `.bp`。其它扩展名，包括 `.json`，不进入自动扫描结果；如果后续确认某类 JSON 是有效蓝图格式，应在导入流程中由用户手动选择并确认，而不是默认递归纳管。

目录映射：

- `BlueprintRoot` 下的真实子目录映射为客户端目录树中的 `blueprint_folder`。
- 文件所在目录决定 `parent_id`。
- 空文件夹也可以纳管为客户端目录树文件夹，但不需要写同步记录。
- 路径中的非法或冲突名称要安全化；如果安全化后重名，追加短 ID。安全化后的相对路径写入 `blueprint_relative_dir` 和 `library_path`，原始名称只作为 `metadata_json.originalName` 供详情展示，不能再参与真实路径拼接。

纳管流程：

1. 调用 `ResolveBlueprintRoot()`。
2. 遍历蓝图目录树，生成文件夹和蓝图候选项。
3. 生成待创建的 `blueprint_folder`、`blueprint` item、资源库目标路径和同步记录计划，但不立即提交数据库。
4. 把蓝图文件复制到 `{AppDataRoot}/blueprints/{真实蓝图相对目录}/{文件名}` 的临时路径，校验文件大小和 hash。
5. 复制和校验全部成功后，在数据库事务中创建文件夹、蓝图 item、`environment_synced_files`，记录资源库文件和真实蓝图文件的对应关系。
6. 如果复制失败或校验失败，不创建 item，不写同步记录；清理临时文件，只把失败信息写入 `environment_operations` 和同步预览结果。
7. 前端刷新后展示与真实蓝图目录一致的客户端目录树。

蓝图同步必须保留真实目录层级，因为戴森球计划蓝图书籍就是蓝图目录下的真实文件夹；客户端第一次同步应该尊重这个结构，而不是把蓝图全部摊平。

### 4.6 存档首次同步

存档首次同步只建立最近扫描索引，真实存档目录始终是权威来源：

1. 调用 `ResolveSaveRoot()`。
2. 扫描存档目录下符合规则的存档文件。
3. 按当前 `relative_path` 生成列表 ID，写入或更新 `environment_save_index`。
4. 对本次扫描未出现的旧索引标记为 `missing`，但不作为当前存档列表展示依据。
5. 前端存档标签展示本次实时扫描结果，并用索引补充最近记录、hash、大小等缓存信息。

存档不复制到 `{AppDataRoot}/environment`，也不写 `environment_items`。如果后续需要“存档备份库”，应作为单独功能设计，不能混入首次同步。

### 4.7 去重与再同步

再次点击“同步本机内容”时：

- Mod/蓝图通过 `target_path + sha256`、`origin_path`、`relative_path` 组合去重。
- 发现已纳管文件 hash 未变化时跳过。
- 发现真实文件变化时标记 `changed`。Mod/蓝图默认以客户端镜像为权威，不自动吸收游戏侧变化；用户可以在冲突处理里选择“用游戏侧更新客户端镜像”或“用客户端镜像恢复游戏侧”。
- 发现客户端资源库存在但真实目标不存在时，item 保持 `disabled` 或 `missing`，不自动删除资源库。
- 存档每次刷新都重新扫描 `SaveRoot`，以当前真实文件列表重建页面数据；`sha256 + size + modifiedAt` 只用于判断“旧索引可能是同一个被重命名的存档”，不能覆盖当前文件系统结果。

### 4.8 用户确认

同步预览需要让用户按类型确认：

| 操作 | 说明 |
| --- | --- |
| 同步全部 | 纳管所有 `new` 项 |
| 只同步当前标签 | 只纳管当前类型 |
| 跳过冲突项 | 默认选中 |
| 用游戏侧更新客户端镜像 | 仅对 `changed` 项显示，用户确认后才把真实目录变化写回客户端镜像 |

同步过程中前端显示进度；失败项保留在预览结果中，并写入日志。

### 4.9 同步事务与失败恢复

Mod、蓝图启用/禁用、首次同步纳管、蓝图真实目录迁移都必须按事务化文件操作实现。这里的“事务”不是要求文件系统具备数据库事务，而是用操作清单、临时文件和可恢复状态避免半同步：

1. 先生成同步计划，列出所有源文件、目标文件、预期 hash、冲突路径和回滚动作。
2. 写入 `environment_operations`，状态为 `pending`，`detail_json` 保存完整计划。
3. 对写入类操作先复制到同目录临时文件，例如 `{target}.dsbox.tmp`，校验 hash 后再原子 rename 到目标文件。
4. 对删除类操作先校验目标路径仍在允许根目录内，且 hash 与 `environment_synced_files` 一致；不一致时停止删除并标记 `conflict`。
5. 文件操作全部成功后，在数据库事务中写入或删除 `environment_synced_files`，更新 item 状态，把操作标记为 `success`。
6. 任一步骤失败时，把操作标记为 `failed`，清理临时文件；已经写出的目标文件如果能通过本次计划确认归属，则按回滚动作删除或还原，无法确认时保留并标记冲突。
7. 应用启动和进入环境页时扫描 `pending`、`running`、`rollback` 操作，执行恢复：清理 `.dsbox.tmp`、`.dsbox-part` 和 `{SaveRoot}/.dsbox-tmp/` 中已失效的临时文件，复核目标文件 hash 和同步记录，让 UI 回到 `enabled`、`disabled` 或 `conflict` 的明确状态。

覆盖和还原规则：

- 写入目标已经存在且需要覆盖时，必须先把旧文件复制或移动到 `{AppDataRoot}/environment/snapshots/sync/{operationId}/...`，快照中保存原相对路径、hash、大小和所属 item。
- 覆盖只允许发生在“当前 item 的旧同步文件”“hash 与源一致的补登记文件”或“用户在冲突处理中明确选择覆盖”的路径上。
- 对目录镜像执行“覆盖”时，不只是覆盖同名文件，还包括删除游戏侧存在但客户端镜像不存在的额外文件；每个被删除的额外文件也必须先进入本次快照。
- 如果覆盖、合并或“用游戏侧更新客户端镜像”涉及其它 item 已登记的目标路径，必须在同一个数据库事务中把受影响 item 标记为 `conflict`，并从它的同步记录中移除或标记受影响路径，避免两个 item 同时宣称拥有同一目标文件。
- 操作提交成功后可以清理本次快照；提交失败时优先用快照恢复旧文件。
- 如果旧文件无法快照、无法删除或无法恢复，操作必须失败并进入 `conflict`，不能把数据库状态更新为成功。

数据库记录不能先于文件结果宣称成功。前端看到 `syncing` 只是操作进行中状态，刷新或重启后必须能通过 `environment_operations` 和真实文件复核恢复。

服务接口不能在后台文件操作尚未完成时提前返回成功。`EnableMod`、`DisableMod`、`EnableBlueprint`、`DisableBlueprint` 必须等待真实复制、删除、hash 校验和数据库提交全部完成后，才返回最终状态；如果文件被游戏占用、权限不足或清理失败，接口返回失败，item 保持原状态或进入 `conflict`，不能先返回 `enabled` / `disabled` 再异步修正。

### 4.10 并发锁

环境管理服务必须在后端串行化同一资源和同一目标路径的写操作，避免用户连续点击或多个页面同时操作导致交叉覆盖：

- Mod 按 `item_id`、`{GameDir}/BepInEx/plugins/{modFolderName}` 和 `{AppDataRoot}/plugins/{modFolderName}` 加写锁。
- 蓝图按 `item_id`、目标蓝图相对路径和文件夹子树加写锁；移动或重命名文件夹时锁住整棵子树。
- 存档按真实存档文件路径加写锁；导入同名文件时同时锁住目标路径。
- 首次同步、刷新状态和启用/禁用不能同时修改同一个 item。读操作可以继续，但 UI 必须展示 `syncing` 或操作中状态。
- 后端获取锁失败时返回“已有操作正在进行”，前端禁止重复提交。

## 5. Mod 管理方案

### 5.1 视图

Mod 标签采用平铺卡片，不做文件夹：

- 卡片固定正方形，图标居中，底部显示名称、版本、状态。
- 名称优先使用 Mod `manifest.json` 的 `name`；版本优先使用 `version_number`，展示为 `v0.9.22` 这类短文本。
- manifest 缺失、解析失败或字段缺失时，名称回退到文件夹名，版本显示“未知版本”。
- 左键切换 `default -> enabled -> disabled -> enabled`。
- 右键菜单提供：查看详情、打开资源目录、删除；第一版不提供 Mod 重命名。
- 工具栏提供：搜索、刷新、打开 Mod 资源库、导入。

“查看详情”使用抽屉或弹窗展示 `metadata_json.manifest`：

| 字段 | 展示 |
| --- | --- |
| `name` | Mod 名称 |
| `version_number` | 版本 |
| `description` | 描述 |
| `dependencies` | 依赖列表，逐行显示 |
| `website_url` | 官网或仓库链接 |
| 字段缺失 | 使用“未知版本”“暂无描述”“无依赖信息”等兜底文案 |
| 解析错误 | 仅在 manifest JSON 无法解析时显示 |

卡片排序建议：

1. `syncing`、`conflict` 优先。
2. `enabled` 在前，`disabled` 和 `default` 在后。
3. 同状态按更新时间倒序。

### 5.2 导入

支持：

| 导入类型 | 说明 |
| --- | --- |
| zip | 解压到临时目录后识别 BepInEx 结构 |
| dll | 第一版不支持裸 DLL 导入；提示用户把 DLL 放入独立文件夹后导入 |
| 文件夹 | 第一版只识别可落到 `plugins` 的文件夹或 Thunderstore 包结构；纳管时接管 Mod 根目录下所有文件，`patchers`、`config` 内容先跳过并提示 |

导入流程：

1. 前端通过 Wails 调用 `EnvironmentManagerService.ImportMod`，传入文件路径或由后端打开选择器。
2. 后端识别 `packageRoot` 和 `modRoot`，生成只会写入 `BepInEx/plugins` 的完整同步文件清单。
3. 后端把 `modRoot` 下所有文件复制到 `{AppDataRoot}/environment/import-tmp/{operationId}`，保留相对目录结构，不直接写入游戏目录。
4. 后端校验临时目录文件集合、大小和 hash，并解析 `packageRoot/manifest.json` 或 `modRoot/manifest.json`，把 `name`、`version_number` 和完整 manifest 写入待提交元数据。
5. 校验成功后，把临时目录移动到 `{AppDataRoot}/plugins/{modFolderName}`；移动和数据库写入必须在同一个 operation 提交窗口内完成，失败时清理临时目录和半成品镜像目录。
6. 后端生成 `environment_items` 记录和客户端同步清单，状态为 `default`。
7. 前端收到新资源后展示在网格中。

安全规则：

- 所有解压和复制必须校验路径位于资源库或游戏允许目录内，复用现有 `fileops.IsSubPath` 思路。
- 禁止 zip 路径穿越。
- 导入 zip 或文件夹时默认不跟随、不接管符号链接、junction、硬链接或其它 reparse point；发现后标记为 `ignored` 并在导入预览中提示，避免把资源库或游戏目录边界外的文件带入同步计划。
- 禁止导入会写入游戏根任意位置的未知文件。无法识别为 `plugins` 可用结构时标记为 `conflict` 或导入失败，并给出原因。
- `modFolderName` 必须是 Windows 安全目录名：禁止 `<>:"/\|?*`，禁止尾随空格或点号，禁止 `CON`、`PRN`、`AUX`、`NUL`、`COM1` 到 `COM9`、`LPT1` 到 `LPT9` 等保留设备名，禁止 `.`、`..` 和任何路径穿越。
- 目录名比较按 Windows 大小写不敏感处理；如果安全化后与已有资源冲突，追加短 ID。

### 5.3 启用

启用表示把资源库镜像目录完整同步到游戏目录。典型路径：

```text
资源库：{AppDataRoot}/plugins/nebula-NebulaMultiplayerMod
游戏目录：{GameDir}/BepInEx/plugins/nebula-NebulaMultiplayerMod
```

启用成功后，这两个目录的文件集合、相对路径、大小和 hash 必须一致。

流程：

1. 校验游戏路径有效。
2. 校验 BepInEx 状态。若未安装，前端显示“需要优先安装 BepInEx”，并提供安装入口。
3. 读取客户端同步清单，生成同步计划。客户端同步清单来自 `{AppDataRoot}/environment/mods/metadata/{modId}/sync-manifest.json` 或等价数据结构，包含源文件相对路径、目标相对路径、hash 和 Mod manifest 元数据引用。
4. 分类目标目录当前内容：
   - 资源库镜像中仍存在的目标文件：属于本次期望文件。
   - `environment_synced_files` 中登记过、但资源库镜像中已经不存在的旧文件：属于待清理旧同步文件。
   - 资源库镜像中存在的空目录：属于本次期望目录，启用时需要创建。
   - 不在本次期望文件/目录、也不在旧同步记录中的文件或目录：属于未知项。
5. 对本次期望文件逐个检查：
   - 目标不存在：允许复制。
   - 目标存在且属于当前 item 的旧同步记录：允许覆盖，覆盖前按 4.9 写快照。
   - 目标存在且校验值等于资源库源文件：补登记后视为已启用。
   - 目标存在但属于其它 item 或未知来源：进入 `conflict`，等待用户选择覆盖、跳过或合并。
6. 对待清理旧同步文件，在 hash 与旧记录一致时加入删除计划；hash 不一致时进入 `conflict`。
7. 对未知项不做静默删除。若用户在冲突处理中选择覆盖，后端必须把选择写入新的操作计划；若用户选择合并，必须先生成“游戏侧文件写回客户端镜像”或“客户端镜像写入游戏侧”的合并计划，并在合并完成后重新执行启用复核；若用户选择跳过，本次启用不覆盖该路径，item 保持 `conflict` 或部分同步提示。
8. 递归复制 `{AppDataRoot}/plugins/{modFolderName}` 到 `{GameDir}/BepInEx/plugins/{modFolderName}`，写入临时文件并校验后落盘。
9. 清理已确认归属当前 item 的旧同步文件。
10. 复核目标目录与资源库镜像目录是否一致。若用户选择跳过，或合并计划执行后仍导致目标目录与客户端镜像不完全一致，不能返回 `enabled`，必须返回 `conflict` 并列出差异。
11. 只有复核确认目标目录与资源库镜像目录完全一致时，才写入新的 `environment_synced_files`。
12. 更新 item 状态为 `enabled`。
13. 写入操作日志并返回成功。

如果复制、覆盖、hash 校验或目录复核任一步失败，接口返回失败；不得写入新的 `environment_synced_files`，item 不得更新为 `enabled`。如果已经写出部分文件，按 4.9 执行回滚；无法安全回滚的路径进入 `conflict` 清单。

### 5.4 禁用

禁用表示移除游戏目录中的 `{GameDir}/BepInEx/plugins/{modFolderName}` 镜像目录，但保留 `{AppDataRoot}/plugins/{modFolderName}` 资源库目录。

流程：

1. 读取 `environment_synced_files`。
2. 对每个目标文件检查是否仍位于 `{GameDir}/BepInEx/plugins/{modFolderName}` 内。
3. 复核目标目录内被本系统登记的文件 hash，并检查目录内是否存在未登记文件。
4. 若全部登记文件 hash 一致且不存在未登记文件，先把整个 `{modFolderName}` 目标目录移动或复制到 `{AppDataRoot}/environment/snapshots/sync/{operationId}/disabled-target/`，再删除游戏侧目录。
5. 若目标文件被用户、游戏或其它安装器修改，或目录内存在未登记文件，默认不删除，标记为 `conflict` 并展示“目录包含非本系统文件，未自动移除”。
6. 删除后复核目标目录已经不存在或为空。
7. 只有复核成功后，才在数据库事务中删除同步记录，更新 item 状态为 `disabled`。如果复核失败，优先从快照恢复目标目录，恢复失败则进入 `conflict`。

如果游戏运行导致文件占用、目录删除失败或复核失败，接口返回失败；item 不得更新为 `disabled`。前端可以提示用户关闭游戏后重试。

### 5.5 删除

删除 Mod 表示删除客户端资源库中的 `{AppDataRoot}/plugins/{modFolderName}` 和对应元数据。删除前必须先处理启用状态：

- 如果 item 当前为 `enabled`，后端必须先执行一次完整 `DisableMod`。
- 只有 `DisableMod` 真实删除、复核和数据库提交全部成功后，才允许删除客户端镜像目录。
- 如果禁用失败、文件被占用、目标目录进入 `conflict`，`DeleteMod` 必须失败并保留客户端镜像，避免用户同时丢失游戏侧和客户端侧文件。
- 客户端镜像删除也要进入 `environment_operations`，优先移动到回收站或 `{AppDataRoot}/environment/snapshots/delete/{operationId}`，支持失败恢复。
- 删除成功后移除 `environment_items`、Mod 元数据和同步清单；操作日志保留删除摘要。

### 5.6 重命名

Mod 第一版禁止用户重命名。原因是显示名来自 Mod 清单或文件夹名，强行改名会和 `manifest.json`、依赖标识、DLL/目录引用产生歧义。

如果后续需要“显示别名”，应新增独立字段，例如 `display_alias`，并明确它只影响 UI，不影响同步路径、manifest 名称或依赖识别。

## 6. 蓝图管理方案

### 6.1 视图

蓝图标签使用类 Windows 文件目录：

- 根目录显示文件夹和蓝图卡片。
- 文件夹优先显示，蓝图其次。
- 顶部显示面包屑：`全部蓝图 / 科研建筑 / ...`。
- 支持双击或单击进入文件夹。
- 支持拖拽蓝图或文件夹到另一个文件夹。
- 支持拖到面包屑节点或空白区移动到目标目录。
- 右键空白区：新建文件夹、导入文件、快速导入。
- 右键项目：重命名、导出、删除。

### 6.2 目录树与真实路径

蓝图文件夹先由客户端数据表维护，但它不是只存在于 UI 的虚拟分组。每个文件夹都必须能映射成 `BlueprintRoot` 下的真实相对目录：

- `parent_id` 表示客户端目录树父目录。
- 移动文件夹时必须防止把文件夹移动到自身或后代节点下。
- 删除文件夹时必须二次确认，或采用“删除到回收状态 + 可撤销”。删除文件夹会影响其子文件夹和蓝图资源。
- `blueprint_folder` 本身不需要单独同步状态；只有当文件夹下存在已启用蓝图，或用户明确执行“同步文件夹结构”时，后端才在真实蓝图目录中创建对应目录。
- 客户端目录树中的每一级名称都要经过 Windows 文件名安全化处理，禁止 `<>:"/\|?*`、尾随空格或点号、`.`、`..`、路径穿越，以及 `CON`、`PRN`、`AUX`、`NUL`、`COM1` 到 `COM9`、`LPT1` 到 `LPT9` 等保留设备名；名称比较按 Windows 大小写不敏感处理。
- UI 可以展示用户输入名或原始导入名，但服务层用于拼接 `BlueprintRoot` 和 `{AppDataRoot}/blueprints` 的只能是安全化后的路径段；显示名变更必须重新计算安全路径并走重命名/迁移流程。
- 文件夹重命名或移动前，后端必须先生成迁移预览，列出受影响的已启用蓝图、旧真实路径、新真实路径和冲突项。
- 第一版默认阻止直接移动或重命名“包含已启用蓝图”的文件夹，除非用户在迁移预览中明确确认。
- 用户确认迁移后，后端按 4.9 的事务规则执行：先移动或重命名客户端镜像文件，再把客户端镜像文件写入新真实路径并校验，然后更新 `environment_synced_files`，最后只清理已登记且 hash 一致的旧蓝图文件和空目录。
- 迁移失败时不能删除旧真实文件；item 或文件夹进入 `conflict`，前端提供“打开旧目录”“打开新目录”“重新迁移”。

示例：

```text
客户端路径：全部蓝图 / 科研建筑 / 矩阵 / 电磁矩阵生产线
真实路径：{BlueprintRoot}/科研建筑/矩阵/电磁矩阵生产线.txt
```

### 6.3 导入

支持：

| 入口 | 行为 |
| --- | --- |
| 导入文件 | 默认选择 `.txt`、`.bp` 蓝图文件；`.json` 等未知扩展需要用户手动确认后再导入 |
| 快速导入 | 输入名称和蓝图编码，后端生成蓝图文件并写入资源库 |
| 拖拽导入 | 拖入文件到当前文件夹 |

导入后默认状态为 `default`，不会立刻同步到游戏目录。

蓝图导入安全规则：

- 导入写入客户端镜像也要使用 `{AppDataRoot}/environment/import-tmp/{operationId}` 临时目录；文件校验成功后再移动到 `{AppDataRoot}/blueprints/...` 并提交数据库记录。
- 导入失败不得留下可被列表扫描到的半成品蓝图文件或目录树记录。
- 导入文件必须位于用户选择路径内，复制到 `{AppDataRoot}/blueprints` 前要做扩展名、文件大小、路径边界和文件可读性校验。
- 拖拽导入目录时默认不跟随、不接管符号链接、junction、硬链接或其它 reparse point。
- 导入后的真实相对路径必须由服务层根据当前客户端文件夹和安全文件名生成，前端不能传入可直接拼接到 `BlueprintRoot` 的路径。

### 6.4 启用

启用蓝图表示把客户端镜像蓝图文件复制到游戏蓝图目录。蓝图同步应根据客户端目录树创建真实文件夹，让环境页的组织方式和游戏蓝图书籍目录一致：

```text
资源库：{AppDataRoot}/blueprints/{FolderA}/{FolderB}/{DisplayName}.txt
游戏目录：{BlueprintRoot}/{FolderA}/{FolderB}/{DisplayName}.txt
```

启用成功后，游戏侧蓝图文件内容、大小和 hash 必须与客户端镜像文件一致。

目标路径示例：

```text
{BlueprintRoot}/{FolderA}/{FolderB}/{DisplayName}.txt
```

若同目录下文件名冲突，不自动追加短 ID；进入 `conflict`，由用户选择覆盖、跳过，或先重命名客户端蓝图后再启用。单个蓝图文件不提供内容级合并。

同步流程同 Mod：

1. 调用 `ResolveBlueprintRoot()` 定位蓝图真实目录。
2. 根据 `blueprint_relative_dir` 或父级文件夹链生成目标相对路径，并逐级创建真实目录。
3. 检查目标冲突。
4. 复制客户端镜像文件到目标目录，写入临时文件并校验后落盘。
5. 复核目标文件与客户端镜像文件 hash 一致。
6. 只有复核确认目标文件与客户端镜像一致时，才在数据库事务中写入同步记录并更新状态为 `enabled`。

如果复制、hash 校验或目录创建失败，接口返回失败；不得写入新的 `environment_synced_files`，item 不得更新为 `enabled`。失败时按 4.9 执行回滚；无法安全回滚的路径进入 `conflict` 清单。

### 6.5 禁用

禁用蓝图只删除游戏侧 `environment_synced_files` 中记录过的目标文件，保留 `{AppDataRoot}/blueprints/...` 下的客户端镜像文件。若目标文件被用户或游戏修改，默认保留并标记冲突。删除前必须把待删蓝图文件复制或移动到 `{AppDataRoot}/environment/snapshots/sync/{operationId}/disabled-blueprints/`；删除文件后可以自底向上清理空目录，但只能清理本次同步路径上由环境管理创建或确认为空的目录，不能删除蓝图根目录。只有复核目标文件不存在、同步记录删除和状态更新都提交成功后，才返回 `disabled`；失败时优先从快照恢复。

禁用接口必须等真实删除和目录复核完成后才返回 `disabled`。如果游戏占用文件、权限不足或空目录清理失败，接口返回失败；item 不得更新为 `disabled`。

### 6.6 重命名

蓝图重命名分两种：

| 状态 | 行为 |
| --- | --- |
| 未启用 | 更新客户端目录树显示名，并重命名客户端镜像蓝图文件 |
| 已启用 | 先更新客户端镜像蓝图文件，再执行一次同步重命名：写入新目标文件，确认成功后删除旧同步文件 |

如果已启用蓝图的新名称与游戏目录文件冲突，则资源库名称可以保存，但同步状态进入 `conflict`，前端提示用户处理冲突。

已启用蓝图重命名也必须走迁移预览和事务规则：新文件写入并校验成功前，不删除旧同步文件；数据库同步记录只能在新目标文件确认存在后更新。

### 6.7 删除

删除蓝图或蓝图文件夹只删除客户端镜像和目录树记录，前提是所有已启用资源已经安全禁用：

- 删除单个已启用蓝图时，后端必须先执行 `DisableBlueprint`；只有游戏侧目标文件真实删除、空目录清理和数据库提交成功后，才删除 `{AppDataRoot}/blueprints/...` 下的客户端镜像文件。
- 如果禁用失败、目标文件被修改、文件被占用或目录清理失败，删除操作失败，客户端镜像文件和目录树记录必须保留。
- 删除文件夹时，后端先生成递归删除预览，列出子文件夹、蓝图数量、已启用数量和冲突数量。
- 文件夹内存在已启用蓝图时，必须逐个禁用成功后才允许删除客户端镜像树；任一项失败则停止删除并保留未删除部分。
- 客户端镜像删除优先进入回收站或 `{AppDataRoot}/environment/snapshots/delete/{operationId}`，避免误删后无法恢复。

## 7. 存档管理方案

### 7.1 视图

存档标签直接展示真实存档目录中的文件：

- 卡片显示存档名、最后修改时间、大小。
- 可选显示游玩时长、星球名等元数据；如果无法解析，显示基础文件信息。
- 工具栏提供搜索、刷新、打开目录、导入。
- 右键菜单提供：重命名、导出存档、删除。

存档没有 `enabled/disabled/default` 状态。它的状态来自文件系统：

| 状态 | 说明 |
| --- | --- |
| `normal` | 文件可读 |
| `locked` | 文件被占用，暂不允许重命名或删除 |
| `invalid` | 文件格式或扩展名不符合预期 |

### 7.2 扫描

后端扫描存档目录，返回：

| 字段 | 说明 |
| --- | --- |
| `id` | 基于当前 `SaveRoot` 相对路径 hash 的列表 ID |
| `name` | 去扩展名后的显示名 |
| `fileName` | 真实文件名 |
| `absolutePath` | 后端内部使用，前端可不展示 |
| `sizeBytes` | 文件大小 |
| `lastModifiedAt` | 最后修改时间 |
| `metadata` | 可选解析信息 |

存档扫描必须在进入存档标签、点击刷新、执行重命名/导入/删除后重新读取真实目录。`environment_save_index` 只用于补充最近扫描缓存；如果文件被外部改名，页面应显示新文件，而不是依赖旧 ID 保持旧名称。

扫描时必须忽略环境管理临时目录和临时文件，例如 `{SaveRoot}/.dsbox-tmp/`、`*.dsbox.tmp`、`*.dsbox-part`。这些文件只属于导入/覆盖过程，不能作为存档展示，也不能写入 `environment_save_index`。

### 7.3 重命名

存档重命名直接改真实文件名：

1. 校验新名称非空，并按 Windows 文件名安全规则处理：禁止 `<>:"/\|?*`、尾随空格或点号、`.`、`..`、路径穿越，以及 `CON`、`PRN`、`AUX`、`NUL`、`COM1` 到 `COM9`、`LPT1` 到 `LPT9` 等保留设备名；名称比较按 Windows 大小写不敏感处理。
2. 保留原扩展名。
3. 检查目标文件是否存在。
4. 文件被占用或游戏正在运行时，返回明确错误。
5. 执行 rename。
6. 刷新列表。

### 7.4 导入、导出、删除

| 动作 | 规则 |
| --- | --- |
| 导入 | 复制用户选择的存档文件到游戏存档目录；同名时进入冲突处理，由用户选择覆盖、跳过或改名导入 |
| 导出 | 选择目标目录后复制存档文件；导出失败不得修改源存档 |
| 删除 | 默认进入系统回收站；如果无法进入回收站，再二次确认永久删除 |

删除存档属于高风险动作，前端必须使用明确按钮文案，例如“删除存档”，不要用“确定”。

存档异常处理规则：

- 导入必须先写入 `{SaveRoot}/.dsbox-tmp/{operationId}/` 下的临时文件，校验文件大小和可读性后再 rename 成正式文件；如果目标文件系统不支持跨目录原子 rename，则临时目录必须创建在 `SaveRoot` 同一卷内。
- 导入和导出存档时默认不跟随符号链接、junction、硬链接或其它 reparse point；目标目录必须通过路径边界和可写性校验。
- 覆盖同名存档前必须确认目标文件未被占用，并把旧存档写入回收站或 `{AppDataRoot}/environment/snapshots/save/{operationId}`；覆盖失败时恢复旧文件。
- 游戏运行中默认阻止存档导入覆盖、重命名和删除；只允许导出这种只读操作。
- 删除到回收站失败时，前端必须展示永久删除风险，并要求用户第二次确认。
- 所有存档操作完成后立即重新扫描 `SaveRoot`，以真实目录结果刷新列表。

## 9. 前端状态管理

建议新增：

```text
frontend/src/pages/environment.vue
frontend/src/composables/useEnvironmentState.ts
frontend/src/services/environment.ts
frontend/src/components/environment/resource-card.vue
frontend/src/components/environment/blueprint-breadcrumb.vue
frontend/src/components/environment/context-menu.vue
```

`useEnvironmentState.ts` 负责：

- 当前标签、搜索词、加载态。
- Mod、蓝图、存档列表。
- 当前蓝图文件夹和面包屑。
- 正在执行的 item ID，避免重复点击。
- 首次同步预览、选择项、同步进度和失败项。
- 统一错误格式化和 message 提示。

交互规则：

- 左键切换状态可以在前端本地乐观展示 `syncing`，但不能把 `syncing` 当作最终状态持久化；后端返回成功后再展示 `enabled` / `disabled`，失败则回滚原状态并提示原因。
- 右键菜单不要被滚动容器裁剪，建议使用 Naive UI dropdown 或挂到 body。
- 蓝图和存档重命名使用内联输入框，Enter 保存，Esc 取消，失焦保存。保存失败回到编辑态；Mod 第一版不显示重命名入口。
- 拖拽移动仅用于蓝图，不用于 Mod 和存档。
- 删除资源库项目优先提供撤销提示；存档删除必须更严肃，因为是真实文件。
- 首次同步入口在没有资源库记录但扫描到真实文件时要明显可见；用户关闭后可在工具栏中再次打开。

## 10. 冲突与错误处理

### 10.1 冲突处理原则

出现 `conflict` 时，后端只负责给出可解释的冲突清单和可执行的操作计划，不替用户静默决策。前端必须展示冲突原因、影响路径、客户端镜像版本、游戏侧版本和推荐动作，让用户手动选择：

| 用户选择 | 适用场景 | 行为 |
| --- | --- | --- |
| 覆盖 | 用户确认以客户端镜像为准 | 写入前快照游戏侧目标，再用客户端镜像覆盖；成功后状态可回到 `enabled` |
| 跳过 | 用户暂时不处理某个冲突路径 | 不改动该路径，item 保持 `conflict` 或显示部分未处理 |
| 合并 | 目录型 Mod 或蓝图文件夹存在双方新增内容 | 后端生成合并预览，只复制用户勾选的文件；单个蓝图文件或存档同名冲突不提供内容级合并，只能覆盖、跳过或改名；合并后必须重新计算镜像和同步记录 |
| 用游戏侧更新客户端镜像 | 游戏侧改动才是用户想保留的版本 | 把目标文件复制回 `{AppDataRoot}` 镜像并更新 hash、metadata 或同步清单 |
| 打开目录 | 用户需要自行检查 | 打开客户端镜像目录或游戏目标目录，不修改状态 |

覆盖、合并、用游戏侧更新客户端镜像都必须重新生成 `environment_operations`，走 4.9 的临时文件、快照、校验和提交规则。

### 10.2 目标文件冲突

启用时遇到目标文件存在：

| 场景 | 行为 |
| --- | --- |
| 是当前 item 的旧同步文件 | 按 4.9 快照后覆盖 |
| sha256 与源文件相同 | 补登记，视为成功 |
| 属于其它 item | 进入冲突，提示来源，由用户选择跳过、合并或在确认风险后覆盖 |
| 不属于本系统 | 进入冲突，用户选择覆盖、跳过、合并或打开目录 |

默认不自动覆盖未知文件；只有用户明确选择覆盖或合并后，后端才生成新的写入计划。

### 10.3 文件被修改

禁用时若目标文件 sha256 与同步记录不一致：

- 不删除。
- item 状态标记为 `conflict`。
- 右键菜单提供“打开目标目录”“用游戏侧更新客户端镜像”“用客户端镜像恢复游戏侧”和“解除同步记录”。

“解除同步记录”只删除数据库记录，不删除真实文件；必须二次确认，并在日志中记录。

### 10.4 游戏运行中

Mod 和存档操作可能被游戏进程占用。后端应检测戴森球计划主进程是否运行：优先从已配置的 `Game/StartupFilePath` 解析进程名和安装目录匹配运行进程；如果配置缺失，再使用 `DSPGAME.exe` 等已知进程名兜底。

- Mod 启用/禁用：允许复制前先提示“建议关闭游戏后操作”，失败时显示被占用路径。
- 存档重命名/删除：如果游戏运行中，默认阻止，避免损坏存档。
- 蓝图启用/禁用：通常风险较低，但仍要处理文件占用错误。

## 13. 验收标准

- Mod 目录定位基于 `Game/StartupFilePath`；蓝图和存档目录优先从用户文档目录探测，并支持手动选择兜底。
- 首次进入环境页时能发现游戏目录里已有的 Mod、蓝图和存档，并展示同步本机内容入口。
- 执行首次同步后，已有 Mod 根目录下所有文件被完整复制进客户端资源库，形成虚拟文件目录架构，状态为 `enabled`，并补齐目标文件同步记录。
- Mod 文件夹存在 `manifest.json` 时，卡片名称使用 `name`，版本使用 `version_number`；字段缺失时使用文件夹名或“未知版本”等兜底；右键“查看详情”能展示描述、依赖、官网链接和原始解析信息。
- Mod 第一版不提供用户重命名入口；显示名来自清单或文件夹兜底。
- 第一版不支持裸 DLL 或单文件 DLL Mod；扫描和导入时必须提示不支持，不创建资源库项目。
- 执行首次同步后，已有蓝图按真实目录结构映射为客户端目录树，蓝图文件被复制进 `{AppDataRoot}/blueprints` 镜像资源库，状态为 `enabled`。
- 执行首次同步后，已有存档会出现在实时扫描列表中，并更新最近扫描索引，但不复制到资源库；存档始终以真实目录实时扫描为准。
- 游戏路径未配置时，环境页不能执行 Mod 写入游戏目录的操作，并能跳转设置页；蓝图和存档按各自目录定位状态独立处理。
- 游戏目录或蓝图目录变更后，禁用/删除不能继续使用旧 `target_path` 直接删除；必须提示重新启用到新目录或打开旧目录手动处理。
- Mod 资源以平铺方式展示；启用后目标文件存在于游戏 `BepInEx/plugins` 目录；禁用后只移除本系统登记的文件。
- 第一版 Mod 本体管理范围仅限 `BepInEx/plugins`；`patchers` 和 `config` 不会被普通启用/禁用流程复制或删除。
- 蓝图首次同步默认只自动纳管 `.txt` 和 `.bp`；`.json` 等未知扩展需要用户手动确认导入。
- 蓝图能创建文件夹、进入文件夹、面包屑返回、拖拽移动；启用后客户端镜像蓝图文件同步到游戏蓝图目录的对应真实文件夹中，不存在的真实文件夹会自动创建。
- 包含已启用蓝图的文件夹移动或重命名前必须给出迁移预览；确认迁移失败时旧真实文件仍保留，资源进入明确的 `conflict` 状态。
- 存档列表来自真实存档目录；页面刷新、重命名、导入、删除后都会重新扫描 `SaveRoot`，外部改名以游戏存档目录当前状态为准。
- 存档扫描必须忽略 `.dsbox-tmp`、`.dsbox.tmp`、`.dsbox-part` 等临时目录和临时文件。
- 蓝图和存档重命名都校验空名、非法字符、同名冲突。
- 未登记的目标文件不会被禁用操作误删。
- `syncing` 和 `changed` 只作为 operation 或列表 DTO 派生出的展示/健康状态，不写入 `environment_items.state`。
- 用户选择覆盖、合并或用游戏侧更新客户端镜像时，必须重新生成 `environment_operations`，并通过快照、校验和数据库事务提交。
- Mod 和蓝图启用/禁用、首次同步、蓝图迁移具备操作清单、临时文件、失败回滚和启动恢复；服务接口必须等真实复制/删除/校验完成后才返回 `enabled` 或 `disabled`，不能出现数据库显示成功但目标文件半写入的状态。
- 目标冲突、权限不足、文件占用都有明确提示，并记录到日志。
- 关闭应用再打开后，Mod 和蓝图的启用状态能从数据库同步记录恢复。
