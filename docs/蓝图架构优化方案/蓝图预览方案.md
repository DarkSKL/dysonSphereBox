# 蓝图生成过程增量预览方案

## 目标

蓝图生成时，预览区随算法进度逐步出现建筑和传送带；算法重新尝试时，已显示的临时布局可以撤回或替换。每条事件只传发生变化的对象，不重复发送完整蓝图串。

本次范围是生成代码架构优化和预览接口。后端决定何时新增、撤回、替换对象，并输出统一事件；前端保留订阅、协议类型及输入校验。场景管理、渲染器、动画和工作台实时预览接入不在本次范围内，后续使用方无需理解算法的回退或失败原因。

## 当前情况

- 生成阶段事件已存在，可用于更新状态文案。
- 旧 `building-batch` 仍只在完整蓝图通过自检之后发送，作为单独的兼容选项保留，不作为本方案实时过程的实现。
- 后端新增可选 `EmitPreviewDeltas`：真实机器行装配、路线提交、块平移和候选回退已能发送 `preview-delta`，不等待最终编码。通知器只发送发生变化的对象，单条事件最多 128 项操作。
- 请求与运行时事件统一使用 `taskId`。前端只保留 `FactoryGenerationProgress` 类型、事件校验、`observeFactoryGeneration` 订阅和 `generateFactory` 回调，按需通过请求的 `emitPreviewDeltas` 开启差量。已移除增量场景、渲染器、动画组件及其工作台接入。
- 原根目录的生成引擎和两个内嵌数据文件已集中迁入 `algorithm/`，根目录只保留五个公开接口文件；模式适配器、共享算法、阶段契约和预览通知器各自保留独立目录。测试文件、测试数据和验证脚本已移除。

现有最终结果查看器继续使用正式蓝图串。后端差量接口已可供后续预览模块接入，不表示前端过程动画已经实现。

## 架构重构优化方案

采用“统一入口 + 组合适配器 + 分阶段执行 + 统一结果”的结构。统一入口负责校验请求、准备公共上下文、选择适配器、管理取消和汇总结果；具体生成流程由适配器提供，入口不包含各布局和物流模式的算法分支。

```text
统一生成入口
  → 解析生成配置
  → 选择组合适配器
  → 准备 → 布局 → 装配 → 路由 → 收尾
  → 统一结果

各阶段 ──场景变化──> 预览通知器 ──preview-delta──> 前端
```

### 组合适配器

适配器以完整生成配置为选择键，不只替换某一个布尔选项。当前生成请求新增 `Density` 配置键，缺省归一为 `standard`；注册表按 `(Mode, Density)` 解析适配器。因此四种公开生成模式与两种密度配置可以分别寻址为八个组合实现。当前代码为标准和高密度键分别登记独立适配器对象，高密度先委托现有阶段实现，待专属算法落地时可逐阶段替换，不复制整条流程。

组合适配器应显式提供以下阶段实现：

- **准备适配器**：校验并转换该组合需要的输入，建立阶段上下文。
- **布局适配器**：生成该组合的空间布局计划和候选。
- **装配适配器**：按组合规则创建机器、建筑、端口及局部连接。装配规则不同时使用不同实现。
- **路由适配器**：为当前组合建立、提交和重试物流路线。
- **收尾适配器**：完成该组合需要的坐标变换、实体修订、编号、校验和编码准备；允许不同组合使用不同收尾流程。

各阶段使用窄接口和明确输入/输出，不依赖一个任意可变的全局状态袋。不同组合可组合调用共享的建筑原语、碰撞查询、路线搜索或校验组件；只有流程和约束相同的阶段才共用同一实现。适配器负责组合算法，不应仅做参数转发。

适配器解析集中在统一入口，根据规范化后的生成配置返回完整阶段组合。未知或不支持的组合在生成开始前明确报错，不允许运行中途回退到不匹配的默认实现。所有适配器最后都必须产出同一正式结果契约，保证复制、导出、保存和诊断链路不需要识别内部适配器类型。

### 目录组织

每个生成模式必须有独立目录，代码结构也必须按目录划分职责，而不只是建立目录或登记模式名称。先按生成模式分目录，再在模式目录内按密度配置分子目录。四种模式与两种密度配置对应八个可独立替换的组合；八个组合不意味着复制八套完整生成代码。

以下为目标目录结构，不代表所有实现已迁移完成：

```text
helper/blueprint/build/
  generate.go               # 对外兼容入口，衔接解析器与统一流水线
  types.go                  # 公开请求与结果类型
  progress.go               # 公开事件类型与观察者入口
  diagnostics.go            # 公开诊断类型
  performance.go            # 公开性能观察接口
  algorithm/                # 已迁入的生成引擎和内嵌数据
  contract/                 # 阶段接口、阶段输入输出、统一结果与预览操作契约
  registry/                 # 集中注册和解析组合，不包含生成算法
  pipeline/                 # 生命周期、公共准备、阶段编排与统一结果发布
  preview/                  # 增量通知器，不参与算法决策
  shared/                   # 多个模式复用的建筑原语、寻路、规则校验等实现
  adapters/
    mode1/                  # 直连带模式的代码边界
      common/               # 仅本模式多个组合共用的阶段能力，按需建立
      standard/             # 本组合的阶段选择与专属实现
      dense/                # 预留组合的阶段选择与专属实现
    mode2/                  # 物流配送器模式
      common/
      standard/
      dense/
    mode3/                  # 行星内物流塔模式
      common/
      standard/
      dense/
    mode4/                  # 星际物流塔模式
      common/
      standard/
      dense/
```

各组合目录只放该组合拥有或覆写的阶段文件，例如 `adapter.go`、`prepare.go`、`layout.go`、`assembly.go`、`routing.go`、`finalize.go`。并非每个目录都必须拥有这些文件：没有独立实现的阶段可显式引用共享实现，不必复制代码或创建空文件。具体归属遵循以下规则：

- 只有一个模式或组合使用的布局、装配、路由、收尾逻辑，归对应目录；不能长期留在公共目录，再用 `mode == ...` 选择。
- 同一模式的多个密度组合共用的能力，放在该模式的 `common/`；跨模式确实相同的能力，才放在顶层 `shared/`。
- 不同组合的装配或收尾流程不同时，直接提供不同阶段实现，不把差异全部塞进共享阶段的布尔开关。
- 组合目录之间不直接依赖；预留组合需要复用现有算法时，引用模式内 `common/` 或顶层 `shared/`，不直接调用另一个组合目录。
- `registry` 只负责组合登记与解析，`pipeline` 只负责运行阶段；二者都不承载某个模式的专属算法。

阶段接口放在独立的 `contract` 包，避免 Go 包循环依赖：`registry` 可以依赖具体组合包，`pipeline` 通过 `contract` 接收已解析的适配器，不反向导入具体模式；组合包依赖 `contract`、本模式 `common` 和跨模式 `shared`。共享能力与契约不得反向依赖具体组合、注册器或对外入口。模式专属实现也不得通过回调重新依赖旧 `build` 包的私有 Builder，从而把目录隔离变成空壳。

当前 `build` 根目录作为兼容门面，通过类型别名和函数转发保持服务调用路径稳定；原生成引擎已整体迁入 `algorithm/`。该目录保留 Go 包名 `build`，以保持 Wails 生成模型的命名空间兼容。算法文件移动时一起迁移 `geometry.json`、`models.json`，保持内嵌资源相对位置。

物理迁移解决根目录堆积，不等于所有模式的装配、路由和收尾都已按阶段解耦。后续仍按真实职责逐步迁入模式目录或共享目录；不能仅以存在八个组合目录宣称阶段拆分全部完成。上面的 `registry/`、`pipeline/` 是后续提取目标，当前注册和编排实现位于 `algorithm/`。

### 预览通知器

预览通知器作为旁路能力注入阶段上下文。装配、路由和收尾适配器在场景对象发生可见变化时发布统一的增量操作；通知器负责序号、任务标识和事件发送，不参与布局选择、路线搜索或最终校验。某个阶段无需展示中间变化时可以不发事件，但所有适配器必须遵守同一事件协议。

### 渐进重构

1. 先为当前公开组合建立适配器解析表，保持现有生成结果和请求契约不变。
2. 按准备、布局、装配、路由、收尾的顺序抽出阶段接口，先让现有流程通过一个组合适配器运行。
3. 将行为确实不同的组合阶段拆成独立实现；相同算法仍调用共享组件，避免复制整条生成流程。
4. 为各阶段注入同一个预览通知器，并逐步接入 `preview-delta`；用最终蓝图结果验证各组合适配器的输出一致性和约束完整性。

重构边界以“变化原因和算法流程”划分，不为每个内部函数机械创建适配器，也不把模式分支重新散落到公共阶段中。

当前迁移状态：

- **已完成组合寻址**：`Generate` 的模式选择已集中到 `(Mode, Density)` 组合注册表，旧请求的空密度归一为 `standard`，未知密度返回 `GEN_E_DENSITY`。两种密度组合分别登记独立适配器对象，预留组合暂时复用稳定阶段；`Request.Density` 已通过 Wails 绑定生成器暴露给 TypeScript。
- **已完成公共准备与分区提取**：公共请求准备抽为 `prepareGeneration`，参数规范化与产线拆列计算移入 `preparation.go`。分区算法迁入 `shared/zoning`，直连、配送与物流塔路径共同消费；原 `build.Zone` 公开结果类型保持不变，通过门面转换，避免因此改变 Wails 对外契约。候选 Builder 继续继承当前适配器。
- **已接入独立物流塔布局阶段**：`contract/station.go`、`contract/zone.go` 定义不依赖私有 Builder 的显式阶段数据。`station_preparation.go` 只核验配方、设施与容量，生成只读准备结果；`adapters/mode3|mode4/common` 分别拥有本模式能力与布局选择，四个 `standard|dense` 目录通过自己的 `Adapter()` 工厂装配真实布局阶段，不再只登记身份。预留组合复用本模式 `common`，不直接调用其他密度目录，也不宣称已有新的密度算法。
- **已迁移并校验布局算法**：`shared/stationlayout` 执行依赖排序、环绕机器行均衡分组与规范副产物出口预算，不持有建筑或回调旧 Builder。布局输出只包含分区、原产线索引、行机器数与分组大小，不允许布局器重新声明配方或生产流量；流水线在装配前验证每条产线恰好一次、机器总数守恒、单行容量及十二物理端口预算。
- **已迁移 mode1/mode2 的候选布局规划**：`adapters/mode1/common` 现在拥有直连带矩形、紧凑轮廓、水平回填和全局补电候选规则；`adapters/mode2/common` 拥有配送器基线、紧凑排布和球面反向组合候选规则。标准/预留密度组合共享本模式 `common`，build 包只消费候选数据并执行实体装配、寻路与终检。
- **尚未完成全部实体阶段迁移**：物流塔的实体装配、寻路与候选收尾目前位于 `algorithm/mode_station_assembly.go`、`algorithm/mode_station_pipeline.go` 及相关几何实现；mode1/mode2 的实体装配、路由和收尾同样集中于 `algorithm/`。内部兼容 mode 5/6 仍由现有注册器保留，不计入四种公开模式。根目录已清理，组合解析、部分公共收尾钩子和候选规划目录已具备，但不能视为所有阶段已经独立。
- **已接入真实增量通知器**：独立 `preview` 包只维护渲染值和三种操作，不依赖 Builder、Wails 或模式选择。`generation_preview.go` 在旧引擎与通知器之间转换姿态，四种公开模式的真实装配与提交边界已接入；尺寸探测使用的临时 Builder 默认不可见，真实候选才启用检查点。未开启选项或没有观察者时，不建立场景和对象身份。
- **前端仅保留接口**：已撤下过程场景、渲染器、动画组件和工作台接入；事件类型、输入校验与任务订阅保持可用，正式结果查看器保持现有使用方式。
- **已接入回退与最终候选恢复**：实体有任务内稳定 ID，移动只替换姿态；实际候选失败或切换时撤下可见对象。候选的内部最终渲染快照不进入正式结果 JSON，也不作为完整列表推送；最后只把真正获选候选与当前视图的差量发出，再输出完成标记。
- **后续架构优化边界**：沿现有独立契约继续迁移各模式的实际装配、路由与收尾实现；共享能力中的模式算法分支随迁移收敛。前端预览器、工作台动画链路属于后续独立模块，不作为本次实现内容。

后续调整算法时，需要核对产线数量守恒、阶段输入与输出、取消、候选回退和正式蓝图严格解码；预览接口需保持操作顺序、对象身份和最终结果一致。当前仓库不保留自动化测试与性能测量脚本。

后续架构与接口验证包括：

1. 四种公开模式的实际阶段实现与组合目录对应，而不是只有物流塔布局阶段已拆包。
2. 装配、路由、收尾可按组合独立替换，公共入口和共享能力不再代替组合决定专属算法。
3. 在实际桌面链路验证 `taskId`、有序序号和稳定对象 ID 的新增、撤销、替换操作，包含真实候选回退；后端纯引擎链路已接入，不得退回最终生成后模拟逐块出现。
4. 成功、失败、取消、切换任务及中大型蓝图完成接口验证，按事件重放的最终对象与正式结果一致；前端渲染效果另行设计验收。

## 最小事件设计

沿用现有生成进度通道，并将任务关联字段命名为 `taskId`，增加一种 `preview-delta` 事件。事件按任务顺序到达，每次只包含一组场景操作：

以下仅示意操作结构，省略建筑的其余姿态字段；实际字段由 `preview/types.go` 与 `frontend/src/types/factory-progress.ts` 定义。

```json
{
  "protocolVersion": 2,
  "taskId": "task-id",
  "kind": "preview-delta",
  "sequence": 12,
  "coordinateSystem": "layout-grid-v1",
  "operations": [
    {"type": "add", "objectId": "belt-17", "building": {"itemId": 2001, "localOffset": {}}},
    {"type": "remove", "objectId": "belt-09"}
  ]
}
```

首期只需要三种操作：

- `add`：显示新建筑或路线片段。
- `remove`：撤下当前尝试中已显示的临时对象。
- `replace`：以新数据替换同一对象，供坐标或连接更新使用。

生成成功、失败或取消仍以原有 `Generate` 调用结果为准：成功后前端结束动画并采用正式结果；失败或取消时清理本次临时预览，保留上一次成功预览。首期不增加候选解释、快照恢复、复杂修订协议或算法原因展示。

`sequence` 与普通阶段事件共享递增计数，不能只看差量事件是否逐个连号。实时差量使用协议版本 2；旧最终分块仍为版本 1。工作台启用实时渲染时应显式请求 `EmitPreviewDeltas`，不需要同时请求旧分块。

生成中的姿态属于 `layout-grid-v1`，最终提交的姿态属于 `blueprint-area-local-v1`，后者附带 `areas` 和主区域信息。坐标语义变化时，保留对象也明确发送 `replace`；前端不能把临时平面格坐标直接当作最终球面坐标。最终的版本 2 `preview-complete` 只核对对象总数与实际差量批次数，不再次发送完整建筑列表，更不发送蓝图串。

## 后端怎么发事件

在生成器已经拥有可视化对象数据的地方发事件，而不是为每个内部计算步骤发事件：

- 建筑或机器行确定临时坐标后，批量发送 `add`。
- 一条传送带路线找到并提交后，批量发送路线对应的 `add`。
- 算法撤销或替换临时布局时，发送对应的 `remove` 或 `replace`。
- 最终布局整理完成后，继续执行现有严格校验和蓝图编码；只有正式生成成功，预览才结束为成功状态。

不发送 A* 队列中的每个搜索节点。它们数量大且不是已提交的建筑布局；前端动画只展示实际提交的临时对象变化。前端不接收或判断回退原因。

事件中的对象需有请求内稳定的 `objectId`，因为最终蓝图建筑索引可能在记录整理阶段才确定。坐标和 Area 语义沿用生成器的建筑记录定义。

当前通知器在实体提交边界比较值快照，未变化的对象不会进入事件。内部快照仅用于求差和最佳候选提交，不等同于向前端反复推送全量。当前实现仍需对中大型方案测量检查点比较成本、事件数量和桌面桥接负载，不能用小型回归代替性能验收。

## 暴露给前端的接口

`frontend/src/pages/services/dysonSphere/factory.ts` 提供 `generateFactory(request, onProgress?, signal?)`。请求设置 `emitPreviewDeltas: true` 后，回调可在生成期间收到 `preview-delta`；不设置时维持普通生成。封装为每次调用创建唯一 `taskId`，在调用生成前订阅，并在结束或取消时解除订阅。

```ts
const result = await generateFactory(
  new build.Request({...request, emitPreviewDeltas: true}),
  event => {
    if (event.kind === 'preview-delta') {
      // 将 event.operations 交给后续预览模块；此处不实现渲染。
    }
  },
  signal,
)
```

需要自行调用生成绑定的使用方，也可直接用 `observeFactoryGeneration(taskId, onProgress, signal)` 订阅 `factory:generationProgress`。使用方先订阅，再提交带相同 `taskId` 的请求；主动结束时调用订阅函数返回的清理函数。订阅封装会过滤其他任务，并校验事件结构，使用方按 `sequence` 消费对象变化即可。

接口只传对象增删改及必要坐标元数据，不维护前端场景，不决定动画节奏，也不输出要求前端判断的回退原因。最终正式蓝图继续由生成结果返回或分片读取。

## 验收标准

- 正式生成返回前，订阅者已能收到生成过程中提交的建筑或路线变化。
- 事件只发送新增、移除或替换对象，不重复发送完整蓝图串。
- 回退时发送对应的移除或替换操作；按有序事件重放后的对象与正式蓝图一致。
- 失败或取消不会覆盖上一次成功结果。
- 关闭差量输出时不创建预览场景快照；预览通知不影响后台生成决策和最终蓝图导出。
- 根目录公开入口兼容，算法位于 `algorithm/`，前端只保留接口及协议校验。
