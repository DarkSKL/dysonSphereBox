# 游戏辅助悬浮窗技术方案

## 背景与目标

本方案描述 `DysonSphereBox` 如何实现类似炉石传说盒子、Hearthstone Deck Tracker 的游戏辅助弹窗：在《戴森球计划》运行时，将一个独立的透明悬浮窗口显示在游戏画面上方，用于展示提示、面板、快捷操作或运行状态。

目标不是把 UI 注入游戏进程，而是优先采用 Windows 桌面层面的外部 Overlay 方案：

```text
DSPGAME.exe
  负责游戏渲染与输入

DysonSphereBox.exe
  负责查找游戏窗口
  创建透明置顶 Overlay
  跟随游戏窗口移动、缩放、显示、隐藏
```

该方案适合窗口化、无边框窗口、窗口化全屏场景。真正独占全屏下，普通桌面窗口可能无法覆盖在游戏交换链之上，此时需要降级提示用户切换窗口模式，或者另行评估 Unity Mod / DirectX Hook 方案。

## 技术路线结论

推荐路线：

1. 主程序继续保持现有 Wails 主窗口，用于配置、Mod 管理、环境管理等完整操作。
2. 新增一个专用 Overlay 窗口或 Overlay 辅助进程，只负责游戏上方悬浮展示。
3. Go 后端通过 Windows API 查找《戴森球计划》的进程和主窗口。
4. Overlay 窗口设置为透明、无边框、置顶、默认鼠标穿透。
5. 后台循环同步 Overlay 的位置、尺寸、可见性和置顶层级。
6. 当检测到独占全屏或无法覆盖时，提示用户切换为无边框窗口/窗口化全屏。

不推荐第一阶段使用 DLL 注入、DirectX Hook 或读取游戏内存。这些方案复杂度高，容易触发杀软误报，且会被游戏更新、显卡驱动、渲染后端变化影响。

## 可选方案对比

| 方案 | 实现方式 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- | --- |
| 外部透明置顶 Overlay | 独立窗口覆盖游戏窗口 | 稳定、低风险、适合 Wails/Vue | 独占全屏可能盖不上 | 第一阶段主方案 |
| Unity Mod 内绘制 UI | BepInEx 插件在游戏内渲染 | 能进入游戏内部 UI 层 | 需要维护 Mod，与外部程序通信 | 深度集成时评估 |
| DirectX/OpenGL/Vulkan Hook | 注入并 Hook 渲染链 | 可覆盖独占全屏 | 难度高、风险高、兼容成本高 | 不作为当前方案 |
| 读取内存/注入逻辑 | 注入游戏进程读取状态 | 能拿内部状态 | 风险最高，维护困难 | 避免使用 |

## 总体架构

建议把 Overlay 拆成三个层次：

```text
frontend/src/pages 或 overlay 前端入口
  渲染悬浮面板、提示气泡、交互按钮

service/overlay
  对前端暴露启停 Overlay、查询游戏窗口状态、切换鼠标穿透等能力

helper/overlay/window
  封装 Windows API：查进程、找窗口、读窗口矩形、置顶、穿透、显示隐藏
```

如果 Wails v2 在同一进程内创建多窗口能力受限，建议使用独立 Overlay 辅助进程：

```text
DysonSphereBox.exe
  主界面和配置中心

DysonSphereBoxOverlay.exe
  透明悬浮窗
  通过本地 WebSocket / HTTP / 命名管道与主程序通信
```

独立进程的优点是主窗口和 Overlay 生命周期隔离，Overlay 可以使用更激进的窗口样式，不影响主界面可用性。

## 进程与窗口抓取方式

### 识别游戏进程

《戴森球计划》的常见进程名是：

```text
DSPGAME.exe
```

建议识别策略按可靠性排序：

1. 优先使用用户已配置的游戏安装目录，匹配进程可执行文件路径是否为该目录下的 `DSPGAME.exe`。
2. 其次按进程名匹配 `DSPGAME.exe`。
3. 再用窗口标题包含 `Dyson Sphere Program` 或本地化标题作为辅助判断。
4. 多个实例存在时，优先选择前台窗口或最近活跃窗口。

只按进程名匹配容易误伤同名测试程序，因此最好结合可执行文件路径。

### Windows API 流程

查找目标窗口的核心流程：

```text
1. EnumWindows 枚举所有顶层窗口
2. IsWindowVisible 过滤不可见窗口
3. GetWindowThreadProcessId 获取窗口所属 PID
4. OpenProcess 打开进程
5. QueryFullProcessImageName 读取进程可执行文件路径
6. 校验进程名/路径是否为 DSPGAME.exe
7. GetWindowText 读取窗口标题作为辅助信息
8. 找到后保存 hwnd、pid、exePath、title
```

窗口矩形建议优先使用 `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`，它比 `GetWindowRect` 更接近用户实际看到的窗口边界。若 DWM 调用失败，再回退到 `GetWindowRect`。

### Go 侧伪代码

```go
type GameWindowSnapshot struct {
	PID       uint32
	Hwnd      uintptr
	Title     string
	ExePath   string
	Visible   bool
	Minimized bool
	Rect      WindowRect
}

func FindDysonSphereWindow(expectedGameDir string) (*GameWindowSnapshot, error) {
	var matched *GameWindowSnapshot

	EnumWindows(func(hwnd uintptr) bool {
		if !IsWindowVisible(hwnd) {
			return true
		}

		pid := GetWindowProcessID(hwnd)
		exePath := QueryProcessImagePath(pid)
		if !IsDysonSphereProcess(exePath, expectedGameDir) {
			return true
		}

		rect := ReadWindowRect(hwnd)
		matched = &GameWindowSnapshot{
			PID:       pid,
			Hwnd:      hwnd,
			Title:     GetWindowTitle(hwnd),
			ExePath:   exePath,
			Visible:   true,
			Minimized: IsIconic(hwnd),
			Rect:      rect,
		}
		return false
	})

	return matched, nil
}
```

实际代码建议放在 `helper/overlay/window`，保持 Windows API 细节不泄漏到 service 层。

## Overlay 窗口样式

Overlay 窗口需要具备以下特性：

| 能力 | Windows 样式/API | 说明 |
| --- | --- | --- |
| 无边框 | `WS_POPUP` 或 Wails `Frameless` | 避免标题栏和边框 |
| 透明 | `WS_EX_LAYERED` / WebView 透明背景 | 只显示 Vue 渲染出来的内容 |
| 置顶 | `WS_EX_TOPMOST` / `SetWindowPos(HWND_TOPMOST)` | 保持覆盖在游戏窗口上方 |
| 不抢焦点 | `SWP_NOACTIVATE` | 同步位置时不打断游戏输入 |
| 鼠标穿透 | `WS_EX_TRANSPARENT` | 默认点击直接落到游戏 |
| 不出现在任务栏 | `WS_EX_TOOLWINDOW` | Overlay 不干扰 Alt+Tab |

推荐默认状态是鼠标穿透，只展示信息。当用户按下全局热键或从主程序开启交互模式时，临时取消 `WS_EX_TRANSPARENT`，让 Overlay 可以接收点击。

## 跟随与置顶策略

后台需要维护一个轻量循环，周期性同步 Overlay 状态：

```text
每 100ms - 250ms：
  1. 查找或刷新游戏窗口 hwnd
  2. 游戏不存在：隐藏 Overlay
  3. 游戏最小化：隐藏 Overlay
  4. 游戏窗口可见：读取窗口矩形
  5. Overlay 位置/尺寸不同：SetWindowPos 调整
  6. Overlay 层级可能被打乱：SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE)
```

`SetWindowPos` 的典型参数：

```text
SetWindowPos(
  overlayHwnd,
  HWND_TOPMOST,
  gameRect.Left,
  gameRect.Top,
  gameRect.Width,
  gameRect.Height,
  SWP_NOACTIVATE | SWP_SHOWWINDOW
)
```

需要避免每一帧都无条件移动窗口。建议比较上一次矩形和可见性，只有发生变化或到达置顶刷新间隔时再调用 Windows API。

## 独占全屏处理

普通桌面 Overlay 无法保证覆盖真正独占全屏。建议明确产品策略：

1. 首期支持窗口化、无边框窗口、窗口化全屏。
2. 检测到游戏窗口占满显示器但 Overlay 不可见时，提示用户切换为无边框窗口模式。
3. 不在首期实现 DirectX Hook。

可通过以下信号判断疑似独占全屏：

- 游戏窗口尺寸与显示器分辨率一致；
- 窗口样式缺少普通窗口边框；
- Overlay 已置顶但用户不可见；
- Alt+Tab 后 Overlay 才出现，回到游戏又消失。

这些信号只能辅助判断，不能百分百证明独占全屏。用户提示文案应写成“当前显示模式可能阻止悬浮窗显示”。

## 与 Wails 的集成建议

当前项目的 `main.go` 已经将主窗口设置为 `Frameless: true`，但主窗口承担完整应用操作，不适合直接变成 Overlay。

建议第一阶段采用以下落地顺序：

1. 新增 `service/overlay`，暴露窗口检测和 Overlay 开关状态。
2. 新增 `helper/overlay/window`，封装 Windows API。
3. 先实现“检测 DSPGAME.exe 并返回窗口快照”，用于设置页或调试页显示。
4. 再实现 Overlay 辅助窗口。若 Wails 单进程多窗口不稳定，则拆出 `DysonSphereBoxOverlay.exe`。
5. 前端新增 Overlay 调试面板：显示是否找到游戏、PID、窗口标题、窗口矩形、悬浮窗状态。
6. 最后接入实际悬浮内容，例如运行状态、蓝图解析提示、Mod 环境状态、快捷操作入口。

Wails 绑定方法示例：

```go
type OverlayService struct{}

func (service *OverlayService) FindGameWindow() (*GameWindowSnapshotDTO, error)
func (service *OverlayService) StartOverlay() error
func (service *OverlayService) StopOverlay() error
func (service *OverlayService) SetOverlayInteractive(interactive bool) error
```

新增或修改 Wails 绑定后，需要运行：

```powershell
go build ./...
wails generate module
```

## 前端悬浮内容设计

Overlay 前端不应复用主程序的大量导航和布局，建议单独使用极简布局：

```text
OverlayRoot
  ├─ TopHintBar
  ├─ FloatingPanel
  ├─ QuickActionDock
  └─ ToastLayer
```

设计边界：

- 默认不接收鼠标事件，避免影响游戏操作。
- 信息展示靠近屏幕边缘，不遮挡游戏核心区域。
- 可交互模式必须有清晰退出方式，例如热键或主程序按钮。
- 所有尺寸按游戏窗口像素定位，不依赖主窗口布局。
- 重要提示使用短文案，不使用遮挡大面积画面的弹窗。

## 数据来源边界

Overlay 只负责显示，不负责从游戏内部强行读取状态。第一阶段可展示的数据来源包括：

- `DysonSphereBox` 已知配置；
- 本地 Mod 安装状态；
- 环境管理状态；
- 蓝图解析结果；
- 用户手动触发的提示；
- 后续 Mod 插件通过本地接口主动上报的数据。

如果未来需要读取游戏内实时状态，优先评估 BepInEx 插件。插件在游戏内部读取状态，再通过本地 HTTP/WebSocket/命名管道发送给 `DysonSphereBox`，外部 Overlay 只做展示。

## 风险与限制

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 独占全屏无法覆盖 | Windows 桌面窗口可能被游戏交换链绕过 | 提示切换无边框窗口 |
| DPI 缩放错位 | 多显示器缩放比例不同导致坐标偏移 | 使用真实窗口矩形并开启 DPI 感知 |
| 多显示器切换 | 游戏窗口移动到其他显示器 | 每轮读取窗口矩形，不缓存显示器 |
| 置顶被抢 | 其他置顶窗口或游戏重建窗口 | 周期性刷新 `HWND_TOPMOST` |
| 鼠标误拦截 | Overlay 可点击时影响游戏操作 | 默认穿透，交互模式显式开启 |
| Wails 多窗口能力限制 | 主窗口和 Overlay 样式目标不同 | 必要时拆分 Overlay 辅助进程 |

## 实施阶段

### 第一阶段：窗口检测

交付内容：

- Windows 下枚举窗口；
- 定位 `DSPGAME.exe`；
- 返回 PID、标题、路径、窗口矩形、最小化状态；
- 前端调试页展示检测结果。

验收标准：

- 游戏启动后可稳定识别窗口；
- 游戏关闭后状态变为未找到；
- 多次 Alt+Tab 后仍能刷新窗口信息。

### 第二阶段：Overlay 原型

交付内容：

- 创建透明无边框 Overlay；
- 跟随游戏窗口位置和大小；
- 默认置顶和鼠标穿透；
- 游戏最小化时隐藏，恢复时显示。

验收标准：

- 窗口化/无边框窗口模式下可看到悬浮内容；
- 点击悬浮区域不会影响游戏操作；
- 移动游戏窗口后 Overlay 位置同步。

### 第三阶段：交互与内容接入

交付内容：

- 支持切换可交互模式；
- 接入主程序状态数据；
- 添加悬浮提示、快捷操作入口；
- 完善异常提示和用户引导。

验收标准：

- 用户可开启和关闭交互模式；
- Overlay 不影响默认游戏输入；
- 独占全屏不可用时给出明确提示。

## 后续决策点

在进入开发前需要确认两件事：

1. 是否接受“仅支持窗口化/无边框窗口，独占全屏提示切换模式”的产品边界。
2. Overlay 是优先尝试 Wails 同进程窗口，还是直接设计为独立辅助进程。

建议先按外部 Overlay 原型推进。只要《戴森球计划》以无边框窗口运行，这条路线就能实现接近炉石盒子辅助弹窗的体验，同时保持项目风险和维护成本可控。
