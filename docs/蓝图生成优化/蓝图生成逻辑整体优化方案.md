# 蓝图生成逻辑整体优化方案

> 文档性质：一次完整落地的单期改造方案，不拆成“先压间距、再补带路、再做排序”的多期路线。
> 目标范围：量化结果不变的前提下，把产线依赖、物料流量、传送带等级、自动入口数量、实体路线与空间布局统一纳入蓝图生成。
> 需求确认：用户继续使用现有的传送带等级选择；每种物料需要多少条带、多少个外部入口以及内部如何分流，均由生成器按实际流量自动决定，用户不设置入口数量。

## 1. 结论

当前生成器按量化结果逐条生成局部机器行和辅助设施，再按预设间距摆放、最后统一编码。局部结构虽可完整，但生产依赖图尚未成为全局物理物流图：产线块之间没有统一的供需配对、分流与接线规划。因此会出现区域空隙大、块的先后次序不符合物料流、带路未自动闭合，以及局部容量检查无法证明全图运输能力足够等问题。

本方案将生成主链调整为：

```text
可信量化快照
  => 构建守恒的物料供需边
  => 按用户选择的带等级计算并行带数与入口数
  => 把产线依赖整理成有向布局图（循环依赖缩并为组）
  => 生成机器行及物流端口
  => 按物料边自动生成内部带路和外部边界接口
  => 依据实际占地、带路和碰撞约束紧凑排布
  => 球面 Area 适配及全图预检
  => 统一编号、编码与严格自检
```

**核心决策：**

1. 量化负责决定配方、产量、机器数和每条产线的供需；蓝图生成不减少或暗中改变这些结果。
2. 用户选择的 `BeltLv` 是运输能力的唯一等级输入。生成器不得因流量大而静默升级传送带等级。
3. 自动入口数是流量规划的输出，不是新的用户配置项。超出单带运力时，生成多条并行路线/多个入口，并分配每路流量。
4. 传送带模式必须自动连接所有能够在蓝图内闭合的生产者与消费者。只有原始外部输入、最终目标输出、剩余副产物等边界仍需要玩家接入游戏中的外部物流。
5. 上下游顺序由供需图决定；空间优化以物料路线短、占地紧凑为目标，但碰撞、连通、容量和设备端口规则是硬约束。
6. 前端画板的位置仅用于展示和手动查看，不作为后端蓝图坐标。画板与蓝图生成必须消费同一份确定性物料边数据，不能各自推测供需连接。
7. 球面适配、静态/动态数值预检和编码自检继续保留。数值预检不等价于完整 Unity Physics 或游戏内实际放置验收。

## 2. 当前实现基线

本方案依据仓库当前源码和 CodeGraph 索引核对，主要入口如下：

| 当前代码 | 当前职责与限制 |
|---|---|
| `helper/quant/solve.go` | 计算产线机器数和 `Production.Inputs` / `Outputs`；目前输出的是每条产线的物料净流量，没有持久化为“某生产者以多少流量供给某消费者”的明确边。 |
| `frontend/src/services/dysonSphere/factory-graph.ts` | 前端根据量化结果推导画板节点、边和视觉层级；它是展示布局，不是后端生成的物理路线计划。多来源的供需匹配按比例展开，不能直接视为精确的实体接线契约。 |
| `helper/blueprint/build/generate.go` | 普通模式逐条遍历 `Plan.Productions`、计算 `lineCounts`、调用 `buildLine`，再按 `bounds`、`BlockWidthLimit` 和固定留白移块；没有以完整生产依赖图决定顺序。 |
| `helper/blueprint/build/generate.go` 的 `planZones` | 用目标归属划分区块，多个目标的共用产线可能单独组成共用区；分区是目标分类，不是供需路线距离优化。 |
| `helper/blueprint/build/line.go` | 创建本地产线的机器、输入/输出带、分拣器和可选供电等；一条 `line` 的局部结构并不代表其上游、下游已连通。 |
| `helper/blueprint/build/primitives.go` | `builder.all` 收集建筑，建筑移动时保留指针连接；编码前统一把引用转成建筑索引。这是实现自动跨产线接线的基础，但当前全图物料边尚未进入该连接图。 |
| `helper/blueprint/build/bus.go` | mode 6 独立规划混带总线、筛选取料、原料补给与回流，并有自己的容量估算；必须纳入统一的守恒和诊断口径，不能继续成为完全独立的流量真相。 |
| `service/factory/service.go` | 生成前使用服务保存的量化快照复核 `Plan`，并取消/串行接替旧生成任务；此可信方案校验应保留。 |
| `frontend/src/composables/dysonSphere/useQuantWorkspace.ts` | 已从 `layout.beltLv` 传递用户选择的带等级；改造应沿用这一输入，不增加用户填写入口数的流程。 |

当前已存在带速相关局部约束，不能概括为“完全没有带速逻辑”：`lineCounts` 会依据 `Setting.BeltSpeed` 估算机器行数；mode 6 使用带等级表估算总线和供料容量；普通模式还有输出流量告警。但这些逻辑没有共同以“每条供需边的流量 / 所选等级单带容量 / 实际并行路线数”为核心，因此无法保证整张蓝图的供需守恒和运输能力。

普通模式还按固定默认 `LocalStationHitRadius` 为相邻产线块留白，并按目标分区继续留白；若只降低这些间距，虽然包围盒可能缩小，却可能挤占带路、塔端口、建筑碰撞净空或球面重排空间，不能作为单独修复。

## 3. 本次改造的范围与不变量

### 必须完成

- 普通传送带模式（mode 1）按量化供需边自动铺设所有内部物料带路，不再要求用户手工将上游输出接到下游输入。
- 统一按用户选择的带等级核算运输容量，逐物料、逐边、逐路线检查流量；需要时自动拆为多带、多入口或多消费组。
- 按上游到下游的逻辑依赖决定产线主布局顺序；多目标共享产线只生成一份并在图中表示多个供需方向。
- 将产线块间留白改为基于真实碰撞外形和路线走廊的最小可行净空；在安全约束内压缩空白和总占地。
- 把物流规划、布局、路线生成、球面适配和最终校验串成单次完整生成流程。任何硬约束失败不得返回看似成功的部分蓝图。
- 在生成结果中提供足够的物流诊断，使用户能看到自动入口数、各入口流量、使用带等级、容量占用、外部接入点和失败原因。

### 不得改变

- 不改量化器选中的配方、设备、喷涂配置、产量、原料需求、机器数量和多目标结果。
- 不把空间优化变成新的配方/机器成本求解器；`SpaceWeight` 仍属于量化阶段，不作为带路成本权重的替代品。
- 不把“增加入口”实现成没有来源、没有过滤配置、没有流量分配的装饰带；入口的总流量必须与外部需求完全一致。
- 不允许生成器因线路困难而静默丢弃副产物、缩减供需、改用更高级传送带或漏掉 SCC 内的循环边。
- 不把生成出来的数值预检、蓝图解码成功或前端预览成功宣称为游戏内可放置证明。
- 不更改蓝图格式协议和现有导入蓝图的只读回放语义。

## 4. 统一物料流模型

### 4.1 节点类型

生成前建立一份与几何坐标无关的有向物料流图。至少需要以下节点：

| 节点类型 | 含义 |
|---|---|
| `raw-source` | `Plan.RawInputs` 对应的外部原料入口。它是蓝图边界，不伪造矿物来源或玩家已有物流。 |
| `production` | 一条量化产线，含 recipe、设备、机器数和每种输入/输出速率。 |
| `target-sink` | 用户要求的目标物品输出。它表示生产设施之外的交付端口。 |
| `leftover-sink` | 量化得到的剩余副产物出口。不能为减少建筑而省略。 |
| `external-source` | 用户在画板中明确设为外部供应的物品。语义与 raw source 类似，但必须保留来源类型以供诊断。 |

每个节点用稳定键标识，例如 `production:<productionIndex>`、`source:<itemId>`、`target:<itemId>`。同一主产物的多条 `Production` 是不同节点，不能只用物品 ID 当产线节点 ID。

### 4.2 物料边

每条边至少带有：

```text
edgeId
itemId
sourceNodeId
targetNodeId
ratePerMinute
flowKind: internal | external-input | target-output | leftover
```

`ratePerMinute` 是唯一流量单位。量化输出中的输入/输出是每条产线的物料净流量；对于同一设备内部可抵消的同物品输入/输出不另造外部物流边。对于确实流经不同生产节点的物料，必须明确供给者和消费者，以及每个供需配对的流量。

多来源、多消费者的分配必须满足每个 item 的供需总量，且结果确定、可重现。允许按稳定规则贪心分配，也允许用最小成本流；优先减少实际路线长度、交叉和独立接线数，但不能产生 all-to-all 的无意义细碎接线，也不能因排序差异改变总量。

建议在量化结果中加入后端生成的规范 `FlowEdges`，或提供等价的可重算规范化函数；前端画板和蓝图生成共用同一套边和流量分配。前端不得把 VueFlow 节点坐标回传作为布局输入。若旧版工作区没有流边数据，后端应基于可信量化字段确定性重建，不得信任用户修改的任意边数据。

### 4.3 按物品做守恒校验

对于每种物品 `i`，在容差内满足：

```text
外部供应(i) + 所有产线产出(i)
  = 所有产线消耗(i) + 目标交付(i) + 剩余副产物(i)
```

一个建议的浮点容差为：

```text
abs(supply - demand) <= max(1e-6, max(supply, demand) * 1e-8)
```

容差只处理浮点误差，不得隐藏真实的欠供或超供。缺供、超供、无效物品 ID、重复边或负流量都属于生成前硬错误，并指出物品名称、缺口/盈余速率和关联产线。

## 5. 带速、入口和分拣能力

### 5.1 等级与容量

带等级继续使用现有 `Setting.BeltLv`，前端选择保持不变。按当前项目已使用的游戏基础额定速率，容量表统一为**单条带**：

| `BeltLv` | 游戏额定速率 | 统一计算单位 |
|---:|---:|---:|
| 1 | 6 件/秒 | 360 件/分钟 |
| 2 | 12 件/秒 | 720 件/分钟 |
| 3 | 30 件/秒 | 1800 件/分钟 |

容量常量应由唯一的 helper/纯函数提供，普通模式、物流模式、mode 6、预检和 UI 诊断均调用同一来源。秒与分钟只能在该边界换算，内部不得混用单位。除非确认真实存在并实际创建了多条独立带，否则不得将单带容量乘以 4 或其它固定倍数。

用户选择的等级是硬约束；高流量不能让生成器静默提升等级。若未来增加科技、堆叠或 Mod 对带速的影响，必须由明确版本化数据输入，不可推测。

### 5.2 入口与并行带数量由生成器自动决定

对于一条总需求为 `R` 的物料流，所选等级单带容量为 `C(BeltLv)`。理论最少并行带数为：

```text
laneCount = ceil(R / C(BeltLv))
```

这只是带本身的下界；机器端口数量、分拣器吞吐、配方机器行拆分、路线可达性和目标区域边界可能要求更多路线。入口数由完整规划器结合这些限制自动确定。生成器应均匀分配实际流量，保证每条带 `laneRate <= C(BeltLv)`，并尽量让每条线服务明确的一组产线或外部端口。

示例：单一物料流量为 4200 件/分钟时，Mk.III 每条带 1800 件/分钟，至少规划 3 路；Mk.II 至少 6 路；Mk.I 至少 12 路。生成器不得要求用户输入“入口数”，也不能只显示一条入口再把超出的流量留给用户手工补救。

入口数不等于机器行数：一条机器行可能有多个输入/输出物料，一种高流量物料也可能需要跨多行分流。规划器先按流量推导 lane 数，再将 lane 绑定到可实现的实际机器端口、物流塔端口或外部蓝图边界接口。

### 5.3 设备端口和分拣器是独立瓶颈

传送带容量足够不等于整条供料链足够。必须分层核算：

1. 传送带每分钟额定运力。
2. 每条机器行的输入/输出口数及其实际连接带。
3. 当前 `InserterLv`、分拣器距离、方向、槽位和已核实的单臂吞吐上限。
4. 物流塔/物流配送器/分流器等模式设施的物品槽、端口数和对应拓扑容量。
5. 多产物配方和副产物的筛选、分带或混带能力。

没有经核实的设备吞吐数据时，不得用带容量替代设备能力并报“可满足产能”。可以使用已知硬边界拒绝或明确标注“未校验”，但不能把未校验项默认为无限容量。

### 5.4 多产物、副产物与混带

输出同一物品的多个生产者可以通过独立并行带供给不同消费者，也可以在确认合流合法且合流后总流量不超容量的情况下合并。不同物品不得因为共享一条 `output` 带就被误认为可分别交付；必须由模式支持的过滤/分流设施区分物品，否则应保留为明确的混合外部出口或返回不可生成错误。

所有副产物都必须进入它对应的消费者、目标端口或 leftover 外部端口。自动接线不能只覆盖每条配方的主产物。

## 6. 上下游顺序与循环依赖

### 6.1 方向约定

有向边统一为 `producer -> consumer`。原料源在上游，产线按依赖层次由上游到下游排列，目标/剩余出口在下游。多个目标场景中，共用中间产物的生产节点在图中只保留一份，消费边分别指向各目标相关产线。

绘制和蓝图空间布局应采用相同的方向约定，修复当前“最终产物区域出现在最前、先接入的反而在后”的反向排序体验。稳定排序可使用：拓扑层级、被服务目标顺序、物品 ID、`Production` 原始索引作为最终 tie-breaker，不依赖 Go map 遍历顺序。

### 6.2 循环配方和关键物品

不能把有向图假定为严格 DAG。通过 Tarjan/Kosaraju 等算法求强连通分量（SCC），把 SCC 缩并成布局节点后，对缩并 DAG 拓扑排序：

- SCC 之间按正常上游到下游排序。
- SCC 内保持循环边并真实铺设对应路线；循环不允许因排序算法发现回边而被删除。
- SCC 内使用稳定顺序紧凑排布，并将循环路线作为独立路由约束处理。
- 不能仅因 `KeyItems` 标记或视觉画板的 cycle 标记就猜测实际运输流量；流边仍由守恒分配结果确定。

### 6.3 多目标布局

`TargetItemIDs` 继续用于目标归属和预览联动，但不再用它作为唯一布局顺序。多目标共用中间产物应根据消费边把供给节点靠近主要消费者；目标分区只作为轻量分组/颜色标注，不应把共用区整体推离所有消费区，也不应为每个目标复制共享产线。

若两个目标的最终区域必须分开，物料边的长度与跨区连接成本仍要参与排布。不能为了目标色块清晰而把高流量共享链路拉长到全图另一端。

## 7. 紧凑布局与自动带路

### 7.1 分离拓扑、局部结构与全局布局

统一生成器分为以下逻辑责任，但作为一个整体一次执行：

1. **流图构建**：校验可信量化快照，生成节点、物料供需边和边界接口。
2. **容量规划**：以 `BeltLv` 和 `InserterLv` 计算行拆分、每物料 lane 数、每端口分配和外部入口数。
3. **局部产线装配**：沿用各模式现有机器、槽位、分拣器、供电、喷涂和设施几何规则，输出带明确物料 ID、流量和方向的逻辑端口，而非只返回一堆匿名建筑。
4. **依赖布局**：按 SCC 缩并后的 DAG 分层；让物料相关的生产单元靠近，优先把高流量边置为短连接。
5. **路线寻路**：在机器 footprint、塔、其他建筑、禁占空间和已分配路线之外，规划带路；所有连接路线都写入 `placed` 指针图。
6. **紧凑化**：在不改变内部连接、区域归属和路线可达的前提下，尝试相邻块靠拢、减少列间/区间空白；每次移动后更新占位索引并重验受影响路线。
7. **坐标/Area 适配**：平面布局完成后按当前 `SurfaceLayout` 映射到球面 Area；跨 Area 原边必须被保留或按已验证机制重接，不能丢边或变成开放带。
8. **全图终检和编码**：检查守恒、容量、端口连接、索引闭合、碰撞/路线预检后，统一编号并调用严格蓝图编码器。

`builder.all` 可以继续作为最终建筑收集器，但不应继续作为唯一的布局模型。规划层必须保留生产节点、物料边、端口、lane、路线及区域的显式关联，以便在压缩布局、跨 Area 重接和诊断时不丢失语义。

### 7.2 间距优化准则

删除或替代“所有产线块之间一律空出固定 7 格、目标区之间一律空出两倍”的单一全局间距策略。新准则是：

- 机器、站点、分拣器、供电和静态/动态碰撞几何必须符合已核实安全净空；未知几何不能按零占地处理。
- 带路要占据实际网格或高度通道，不能穿过禁用碰撞体，也不能与不兼容路线交叉。
- 区块之间只留当前设施/路线实际所需的最小安全余量。塔端口、桥接、喷涂网络和供电覆盖等需要的特定间距由对应局部约束决定，不使用一个魔法半径包办。
- 在以上硬约束通过后，确定性地最小化总占地和内部带路长度；其次减少路线交叉、独立入口数量和无效回绕。
- 评估“紧凑”不能只看 `bounds` 面积。还应统计建筑 footprint 并集面积、空白率、总带长、跨层/跨 Area 接驳数和碰撞预检结果。

可以采用启发式候选排布，不要求求得数学上的全局最优；但必须确定性、可取消、受当前 4 分钟生成期限约束，并在无可行路径时失败而非接受碰撞或断路布局。

### 7.3 mode 1 自动传送带接线

mode 1 是本次“内部节点间自动布线”的明确验收对象：

- 每条 `production -> production` 物料边都从正确生产者输出端连接到正确消费者输入端。
- 每条带在蓝图数据中有连续方向连接，最终 `InputObjIdx` / `OutputObjIdx` 指向本蓝图内有效建筑，不能要求玩家补接内部节点。
- 多入口按流量拆分后分别服务一组输入行；多出口按产物 ID 和消费分配分开，避免同一带超载或错误混料。
- 原料入口、目标产物出口、剩余副产物和增产剂等外部边界使用明示的蓝图端口标记和流量诊断；生成器只负责形成可继续连接的外部端点，不伪造其外部供给已经存在。
- 遇到没有可行路线、正确过滤结构或端口能力不足时，返回有物品/产线/流量信息的失败，不输出一张仍要求人工拼内部带的“成功”蓝图。

### 7.4 其它布局模式

统一流图与带容量规则为所有模式提供相同的供需真相、顺序和结果诊断。现有模式继续保留其运输拓扑特征：

| 模式 | 本方案中的责任 |
|---|---|
| 1：机器直连带 | 按每条内部物料边直接自动接带；必须满足第 7.3 节全部验收。 |
| 2：物流配送器 | 以供需边决定配送输入/输出点和容量；保留已有箱体/配送器局部几何。不能把配送器存在当作物料已送达，必须显式标出边界或连接。 |
| 3/4：行星/星际物流塔 | 由物料边决定塔上物品、供/需角色、槽位分组和各产线接驳；容量不足或槽位不足时拆分塔组或失败。 |
| 5：四向分流 | 仅用于确实符合分流器物理规则的路线；不能将四向分流器误用成无限吞吐汇流器。 |
| 6：混带总线 | 保留共享环路、过滤取料和回流拓扑，但由统一 FlowEdges 校验总线分配及所有外部入口流量；不能与模式 1 的直接路线混为同一拓扑。 |

本次改造不能以“模式名带物流”替代可证明的物料边。若特定模式现有装配器不足以承载某条内部边，则必须明确报出该模式的限制和可行替代模式，不得在 UI 宣称已自动接好。

## 8. 外部入口与结果可解释性

自动入口面向两种情况：

1. **蓝图内部流**：生产者和消费者都在蓝图内，由生成器自动铺设并行带和路线，用户不手工接线。
2. **蓝图边界流**：原矿、被设成外供的物品、目标交付、剩余副产物和喷涂供给。生成器根据同一容量规划自动形成一个或多个明确端口；玩家仍需把端口接到蓝图范围外的矿机、总线、物流塔或仓储系统。

建议在 `build.Result` 增加可选诊断 DTO，至少表达：

```text
物品 ID / 名称
流向和来源/消费者
总需求或总产出 / min
用户选择的带等级
自动并行带/外部入口数量
每路分配速率和容量占比
是否为蓝图外部接口
是否经过塔、分流、桥接或跨 Area
状态：已生成 / 有警告 / 硬失败
```

前端可以将这些数据用于画板边的流量标签、蓝图预览旁的物流摘要和错误提示。用户不得编辑入口数量；需要改变容量时，调整现有带等级并重新生成。前端显示的物流流边、后端生成的连接和最终诊断必须来自同一套规范分配。

## 9. 错误和警告策略

**硬失败（不得返回成功蓝图）：**

- 供需不守恒、无法构造合法流边、负流量、未知的必须连接物品。
- 任一边超额且没有自动并行带/端口方案可分担。
- 分拣器、塔槽、配送器或机器物流接口的容量/数量不足。
- 内部带路无路可走、端点不匹配、存在未接边、非法回环或路径交叉违反规则。
- 球面 Area 容量、坐标、连接重接、静态/动态数值碰撞检查失败。
- 蓝图编码和解码自检失败、索引引用越界或出现建筑不在文档内的连接。

**非阻断提示：**

- 生成了几条外部原料/目标出口，需要玩家在蓝图外接入。
- 多目标共享中间产物、剩余副产物和增产剂入口的用途说明。
- 数值预检覆盖边界仍为 `partial`，例如未覆盖的游戏场景/现有建筑/Unity Physics。
- 路线长度、占地、总建筑量较大等性能提示。

提示不能掩盖硬失败。尤其“超额流量请自行确认”不能继续作为普通成功告警来代替生成并行带或拒绝生成。

## 10. 兼容、性能与职责边界

- `BeltLv` 保持现有前端字段、范围和用户体验；自动入口数及 lane 数由生成器计算，作为结果诊断返回，不成为请求必填字段。
- 统一容量函数由 `BeltLv` 派生实际额定运力；`Setting.BeltSpeed` 不得继续与等级表形成两套相互矛盾的带速真相。旧工作区读取时以明确存在的 `BeltLv` 为准；若遇到缺失等级的旧数据，使用兼容默认等级并给出诊断，不从任意自定义 `BeltSpeed` 推导一个未支持的等级。
- 不修改已保存蓝图编码结构。生成请求仅有必要时增加可选字段，结果 DTO 新字段应向后兼容；需要变更绑定时用 `wails generate module` 更新生成代码，不手改 `frontend/wailsjs/**`。
- 生成仍由 `service/factory.Service.Generate` 校验量化快照并串行执行，`helper/blueprint/build` 实现纯内存物流规划和几何装配；不要把布局业务搬进 `service`、`core` 或前端画板。
- 复用当前 `placed` 指针关系、路径、占位、碰撞目录和 surface 编码工具。新逻辑可以拆分 `helper/blueprint/build` 内的 graph/flow、routing、layout 等职责，不应另造一套平行生成器后再把两份建筑数组拼起来。
- 所有图遍历、流量分配、排布和寻路均使用稳定顺序，避免依赖 map 顺序。流程响应生成 context 取消，维持总建筑 20 万上限与单次 4 分钟限制；路由算法应具备节点展开/尝试次数上限。
- 量化流图和生成摘要都不写数据库；它们是单次请求计算结果。生成日志仍由服务层决定并沿用通用 operation log 元数据规范。

## 11. 一次性交付验收

以下为同一改造交付的验收条件，不表示按清单拆成多期上线。

### 11.1 量化流图与守恒

- 单条生产链正确排列为外部原料 → 上游制造 → 下游制造 → 目标出口。
- 随机打乱 `Plan.Productions` 数组后，同一量化方案的布局仍按依赖关系排列，结果确定。
- 多来源、多消费者时各边流量之和与 `Production.Inputs/Outputs` 完全守恒；不出现流量负值、重复支付或消费者被过量分配。
- 多目标共享生产节点只生成一次，各目标流量正确分配；同一 recipe 多产物及副产物都有消费者或出口。
- SCC/循环配方保留所有循环物料边，SCC 间仍按拓扑顺序排布。

### 11.2 带速与自动入口

- 三个带等级分别验证 360、720、1800 件/分钟的单带上限和上限边界；不同模式调用同一容量来源。
- 4200 件/分钟的单物料流量分别自动得到 Mk.I 至少 12 路、Mk.II 至少 6 路、Mk.III 至少 3 路；每路流量均不超单带容量。
- 用户改变 `BeltLv` 后入口数和线路容量重新计算；用户不改变时生成器不能静默换级。
- 对机器端口、分拣器、物流塔槽位等额外约束实施至少一个带速充足但设备端口不足的反例，确认规划会增加接口、切分或明确失败。
- 验证多产物输出不因共用一条 belt 而把不同物品误认为分别送达。

### 11.3 蓝图连接与紧凑布局

- mode 1 多层生产链生成后，逐条检查内部供需边在建筑索引图中端到端连通，用户不需要手工连接任意内部节点。
- 外部原料/目标出口数量、物品 ID、分配速率与 `LogisticsSummary` 一致，并以清楚标记留在蓝图边界。
- 以当前布局作为同输入基线，报告新旧包围面积、建筑 footprint 空白率、内部带总长、交叉/碰撞数。新布局不得以增加非法碰撞或断路换面积下降；同一代表样本的有效占地应有可重复的下降证据。
- 产线顺序不再由求解数组顺序或目标分区顺序偶然决定；高流量关系优先靠近，跨区共享链路不被拉远。
- 无合法路径、端口或容量时，返回具体物品、流量、模式、端点及失败原因，不输出部分成功串。

### 11.4 球面、编码和运行边界

- 旧平面请求和旧工作区缺省等级仍按兼容规则生成；现有 mode 6、mode 3/4、混带、喷涂和多 Area 逻辑不因公共规划器接入而漏掉建筑或连接。
- 新增路线在球面 Area 切分/重排后仍连接到原消费端；每条跨区原边必须保留或有明确逐边重接证明。
- 全部最终建筑经过现有静态/动态和球面路线数值预检、索引闭合校验及 `blueprint.Encode` 严格往返检查。
- 规模样本遵守 20 万建筑和 4 分钟边界，取消生成不留下可被前端误认成新成功结果的旧串。
- 检查结果如未运行 Unity 场景，只能表述为代码级数值预检/蓝图协议自检；不得宣称完整游戏内碰撞和粘贴已验收。

### 11.5 自动化验证建议

为该单期改造新增后端 Go 测试覆盖上述纯数据与生成不变量，重点测试流量守恒、等级容量边界、自动入口数、稳定拓扑排序、SCC 保边、无路失败、mode 1 内部完整连通、multi-target 与副产物、sphere 重排后的边闭合和旧请求兼容。对比布局面积时使用固定输入、确定性布局和可审核的基线指标，不以人工观察截图替代断言。

按项目约定运行 `go test` 相关包、`go vet`、`go build ./...`、`wails generate module`（若 DTO/绑定签名变化）、前端 `npm run build` 和 `git diff --check`。最后仍需用目标游戏构建进行人工导入/粘贴回归；这属于数值预检之外的独立证据。

### 11.6 真实量化产物端到端验收样本

验收必须使用可复现的真实配方和目标产量，不能只用手写 `Production` 假数据证明算法通过。首批固定采用 `Vanilla` 数据集中的以下目标（物品 ID 与配方 ID 来自当前 `helper/quant/data/Vanilla.json`）：

| 目标产物 | 物品 ID | 配方 ID | 验收目标 |
|---|---:|---:|---:|
| 极速传送带 | 2003 | 92 | 120 件/分钟 |
| 火力发电厂 | 2204 | 64 | 120 件/分钟 |
| 结构矩阵 | 6003 | 27 | 120 件/分钟 |
| 攻击无人机 | 5103 | 149 | 120 件/分钟 |

验收设置和结果要求：

- 建立四个单目标样本，每个样本只设置表中的一个目标、目标产量 120/min；再建立一个综合样本，同时设置四种目标各 120/min。综合样本用于验证多目标共享上游产线只生成一份，并按实际流量分配给各消费者。
- 数据集版本、配方选择、制造设备、喷涂模式/点数、研究堆叠、生成模式、`BeltLv`、`InserterLv`、供电和纬圈配置必须固定并写入 fixture 元数据；测试不得依赖界面上未记录的默认值。
- `quant.Solve` 的目标账必须准确包含四个目标各 120/min。生成时所有机器数量和 `ProductionBinding` 必须与可信量化结果对应；机器取整造成的能力余量必须如实记录并进入物料守恒，不能静默丢失或让带路超载。
- 逐物品核对 RawInputs、所有产线输入/输出、四个目标出口和 leftovers 的供需守恒；每一种配方原料必须有内部生产者、明确的外部输入端口，或作为不支持项明确失败。
- 在每个 mode 1–6 下使用同一份综合量化计划进行生成验证。不同模式可以产生不同的实体运输拓扑，但消费的规范 FlowGraph、目标速率、生产节点集合和物料流量账必须一致；任何模式无法承载时必须明确失败，不得悄悄改成未连通的成功蓝图。
- `BeltLv=3` 作为主综合 fixture 的固定值；再将同一物料计划分别用 `BeltLv=1`、`BeltLv=2` 重跑容量矩阵，确认 lane/入口数量随等级自动变化、每条路不超额、生成器不偷偷升级带等级。极速传送带作为被生产物品，与 `BeltLv` 作为蓝图运输带等级是两个独立概念，测试不得混为一谈。
- 四个单目标和综合目标都必须通过严格蓝图编码/解码、建筑计数/产线绑定/流边连通检查及抽象行星规则校验。mode 1 综合样本必须不存在任何需要玩家手工补接的内部生产边。
- 实际游戏校准在隔离的临时测试世界进行，不加载或覆盖个人存档。为目标外部输入提供连续供料；经过启动缓冲后至少观察 10 分钟游戏时间，按游戏计时折算的四个目标出口各不低于 120/min（窗口内各至少 1200 件）。如果机器取整使产量高于目标，超出部分必须进入显式出口或在流量账中有归属，不得造成带堵塞、下游断料或隐形吞吐缺口。

配方、量化 fixture 或游戏数据版本变化时，不直接覆盖基线。更新者必须记录数据集指纹、变更原因、量化输入输出差异以及新生成结果的物流/空间指标，并重新运行完整验收。

### 11.7 全局统一性、空间压缩和线路可用性

- **全局规划统一性：**同一目标输入无论 `Plan.Productions` 顺序如何变化，都产生同一个规范 FlowGraph digest、相同供需守恒账和稳定的拓扑/SCC 结果。mode 1–6 只能改变运输实现方式，不能改变目标产量、生产节点、依赖边或漏掉副产物。
- **空间压缩目标：**先排除任何碰撞、断路、超容量、端口违规或特殊规则违规的候选，再在固定搜索预算内，从全部已检查可行候选中选择总占用面积最小者；同面积时依次选择内部带总长更短、额外跨层/桥接更少、外部入口更少的候选，最后用稳定键打破平局。不能通过缩小碰撞体、跳过净空或删除必要物流换取面积下降。
- **压缩度量：**至少记录所有 Area 的总包络面积、实际建筑和路线 footprint 并集面积、空白率/占用率、内部带长、路线交叉数、跨 Area 接驳数、lane 数、入口数及特殊规则安全余量。按同一 fixture 比较旧布局基线与新布局；新方案必须给出可重复的占地改进，或证明旧方案已是候选集合中更优的可行解。
- **最优性表述：**空间问题是组合优化，不把有界启发式误称为数学上的全局最优。结果应表述为“固定候选预算和规则覆盖内的最优可行方案”，记录搜索预算、已评估候选数、被拒绝原因和最终 objective 指标；同一输入必须稳定选出同一方案。
- **路线正常使用：**内部每条物料边必须有具体起点/终点端口、物品 ID、目标流量、lane 分配和完整带记录链。通过逐带连接图检查、物料流量仿真/守恒检查，以及隔离游戏世界的端到端运行抽查；游戏运行窗口内目标产出达到 120/min，不出现端口错接、卡带、带路断点、错误混料或未解释的副产物。
- **抽象特殊规则矩阵：**对每项特殊规则做“安全侧、刚好边界、违规侧”正反样本，至少包含电力塔/电力节点最小间距和覆盖、行星内物流塔与星际物流塔的占地间距/可达端口/槽位限制、分拣器端口与摆臂范围、传送带接线距离和交叉、桥接高度、喷涂/附加区域占位。错误时报告规则 ID、阈值、实际距离/净空、冲突对象索引和游戏构建配置。
- **碰撞/路径失败关闭：**抽象环境对未覆盖的物品原型、未知朝向、未注册特殊规则或不支持的 Area 拓扑返回 `unverified` 或阻断错误，不能默认安全。只有规定的规则覆盖集合内通过，才可标为“抽象规则检查通过”。

## 12. 当前算法成熟度与完成边界

### 12.1 当前已经具备的能力

当前系统不是无法工作的原型，而是**局部生成能力较完整、全局工厂规划能力未完成**。以下能力可以作为本次改造的稳定基础：

- `helper/quant` 能根据目标、配方和设备选择计算机器数量、产线输入输出速率、原料、目标和剩余副产物。
- `helper/blueprint/build` 已按六种模式拥有机器行、传送带、分拣器、物流塔、配送器、混带、供电和喷涂等局部装配规则。
- `builder.all`、`placed.input`、`placed.output` 和 `records` 已能在最终编码前保留建筑连接关系并统一转换为蓝图索引。
- `service/factory.Service.Generate` 会复核后端可信量化快照，并取消/串行接替旧生成任务，避免前端任意改写量化方案。
- `surfaceEncoding`、游戏版本碰撞目录、球面位置、静态建造盒、部分动态设施、带距离和带交叉检查已经存在，可以继续扩展为统一虚拟环境。
- `blueprint.Encode` 会编码后严格解码并比较二进制内容，蓝图协议层不需要另造一套编码器。

### 12.2 当前尚未完成的核心算法

下列缺口正是本方案要一次性补齐的内容：

- 量化输入输出还没有被统一固化为“生产者、消费者、物品、流量、路线”的全局物流图。
- `Generate` 仍主要按 `Plan.Productions` 和目标分区顺序逐条装配，尚不是基于供需依赖的拓扑布局。
- `lineCounts`、`Setting.BeltSpeed`、普通模式容量告警和 mode 6 的 `6/12/30` 容量判断不是同一套传送带容量真相。
- `buildLine` 主要生成产线内部物流，mode 1 缺少按物料流边从上游输出端到下游输入端的全局自动接带。
- 区块之间的固定留白并没有结合实际路线走廊、碰撞外形和端口方向做最小化。
- 当前已有球面坐标、静态/部分动态碰撞和路线数值预检，但抽象环境仍需补齐统一的寻路占位、特殊规则矩阵和版本化规则覆盖；它不以完整 Unity Physics、地形、已有实体或 Mod 状态为目标。

因此，当前算法可描述为：

```text
局部建筑生成：较完整
蓝图编码与索引闭合：较完整
局部碰撞/球面数值预检：已有基础
全局物料流规划：未完成
全局带速与多入口规划：未完成
产线间自动带路：未完成
全局紧凑布局：未完成
完整游戏内可放置保证：未完成
```

### 12.3 能否完成

可以完成，但必须按本方案重构生成主链，而不是只修改 `LocalStationHitRadius`、增加几条固定传送带或补充告警。目标实现应一次贯通以下模块：

```text
FlowGraph
  => TransportCapacity
  => ProductionTopology
  => PortAwareLayout
  => BeltRouter
  => PlanetRuleValidator
  => BlueprintEncoder
```

其中：

- `FlowGraph` 负责守恒供需边、稳定拓扑顺序和 SCC 循环组。
- `TransportCapacity` 负责用户选定带等级下的带容量、分拣器/塔槽位容量和自动 lane/入口数量。
- `ProductionTopology` 负责把每条量化产线拆成可连接的机器行组和逻辑端口。
- `PortAwareLayout` 负责让高流量上下游靠近，并以实际占地、路线走廊和碰撞净空压缩布局。
- `BeltRouter` 负责 mode 1 内部带路、分流/合流、端点方向、路线占位和建筑索引连接。
- `PlanetRuleValidator` 负责平面和球面网格、Area、碰撞、路线、端口和跨区边闭合检查。
- `BlueprintEncoder` 继续复用现有严格编码和自解码自检，不改变蓝图协议。

这是一项可以在当前代码库中完成的核心架构升级，但不应被承诺为“改几个参数即可完成”。必须以固定输入、确定性结果和完整测试矩阵证明：流量不丢、带不超载、内部边不缺失、建筑不碰撞、路线可达，失败时不返回半成品。

## 13. 抽象行星规则验证环境

### 13.1 建设目标

可以构建一个**抽象的行星几何与规则验证环境**，用于校验蓝图生成逻辑、算法寻路、线路占位、体积碰撞以及电力塔/物流塔间距等特殊规则。它只表达生成器需要检查的坐标、占位与规则，不创建或渲染完整的真实游戏世界，也不加载玩家存档。

该环境不是在 Go 中重造整个 Unity 游戏，更不能在没有证据时宣称等价于 PhysX。它应被定义为一个快速、可确定、可重复的算法验证沙盒：

```text
版本化游戏几何/规则 + 离散行星坐标变换 + 建筑/端口/路线占位
  + 特殊规则检查器 + 物流容量校验 + 可解释的离线校验器
```

### 13.2 虚拟环境的组成

1. **行星网格层**：以抽象数据复刻纬圈、经度分段、环向接缝、Area 父链、锚点和局部坐标到球面世界坐标的映射；不生成 terrain mesh、海洋、水面或行星渲染。当前实现只承诺已核对的原版 `GridSegment=200`，其它分段数必须拒绝或标记未验证。
2. **静态实体层**：从固定游戏构建提取并版本锁定建筑建造盒、模型映射、朝向和碰撞外形；未知物品/模型不能以零尺寸放行。
3. **动态端口层**：复刻建筑端口、分拣器 `slotPoses`、附加区域、带端点和分拣器扫掠体。静态建筑和动态物流对象按游戏规则分别检查，不能把所有几何粗暴合并成一种碰撞。
4. **路线占位层**：传送带段、转弯、坡道、高架、桥接和跨 Area 接驳都占据空间；路由规划产生的占位必须进入碰撞索引，不能只保留一组绘制点。
5. **物流容量层**：把带等级、有效带容量、分拣器距离/等级、物流塔槽位和分流/合流能力挂到具体路线或端口上，容量失败是硬失败。
6. **特殊规则层**：按实体原型、朝向、模式和版本应用电力节点最小间距/供电覆盖、行星塔/星际塔占地与安全间距、塔端口/槽位可达、分拣器跨距及其它专属建造限制。`LocalStationHitRadius` 是布局配置，不得直接冒充游戏真实塔间距常数；两者必须分开建模。
7. **规则配置层**：记录游戏 build、碰撞目录来源哈希、网格分段、规则目录版本和各检查器覆盖状态。为算法单测需要的障碍可使用合成占位体；环境不读取个人存档，不推断玩家已有建筑、terrain、Mod 或科技状态。

### 13.3 在虚拟环境中运行生成

生成流程应变为：

```text
创建版本化抽象行星/规则快照
  => 放置生产节点与物流端口
  => 预留外部入口和目标出口
  => 在离散行星网格上分层排布
  => 逐条分配物料 lane 和路线
  => 路线占位登记到空间索引
  => 静态 OBB / 动态扫掠体 / 带交叉 / 端口距离检查
  => 守恒、容量、连通、Area 和索引闭合检查
  => 输出蓝图与可解释诊断
```

任何一条内部物流边没有路线、容量不足、碰撞未定义或连接索引不闭合，都必须返回明确失败。`partial` 只能表示“已知规则覆盖范围内通过、仍有真实游戏规则未覆盖”，不能表示“算法暂时没检查但可以放置”。

### 13.4 抽象环境的职责边界

抽象环境的职责是尽可能准确、快速、可重复地验证生成算法，不模拟完整游戏运行：

- **负责检查：**全局规划结果是否守恒、带路是否可达、路线空间是否占位正确、体积碰撞是否命中、分拣器端口是否有效、电力节点是否满足间距/覆盖、行星塔/星际塔是否满足间距/端口/槽位限制，以及 Area/接缝和跨区连接是否闭合。
- **不负责模拟：**游戏画面、terrain 高度图、水面/地形改造、完整 Unity Physics、玩家真实存档中的既有建筑/预建筑、实时 Mod/科技状态和游戏运行中的流动动画。
- **校准方式：**若规则来自游戏 DLL/资源，应记录固定构建和哈希，并用独立提取样本校验。真实游戏的预览/放置回归可以用来校准抽象规则，但不是抽象环境自身伪造出的检查结果。
- **版本边界：**游戏更新导致碰撞、端口、带速或 Area 规则改变时，必须更新版本化事实目录和边界样本；未知 build、物品或规则应标记 `unverified`，不能继续沿用旧数据声称通过。

## 14. 计算效率与可扩展性

虚拟环境不会天然让算法更快；如果每次尝试都全量重建路线和两两检查，可能比当前实现更慢。效率必须随环境一起设计：

### 14.1 分层求解，避免搜索无效细节

先做低成本硬校验，再进入昂贵几何：

1. 量化快照、物品 ID、供需守恒和 SCC 检查。
2. 带等级容量、lane 数和端口/塔槽位下界检查。
3. 拓扑分层和粗粒度矩形/环带容量检查。
4. 仅对候选位置执行精确路线寻路和碰撞窄相位。
5. 仅对最终候选执行完整 Area、动态设施和编码自检。

这样可以在进入 OBB、扫掠体和球面路线计算前，尽早淘汰明显超载或无供需解的方案。

### 14.2 必须采用的性能技术

- **空间哈希/BVH**：复用当前空间索引思路，按静态建筑、路线段、动态端口分层索引，避免全量两两碰撞。
- **局部重算**：移动一个生产块时，只重算受影响的供需边、路线走廊和相邻空间单元，不重新规划整座工厂。
- **路线缓存**：以起点端口、终点端口、环境占用版本、带等级和允许高度为键缓存可复用路径；占用发生变化时按版本失效。
- **增量占位**：每放置一条路线立即登记占位和容量，后续候选只查询受影响区域；失败时回滚本次候选而不是清空全部环境。
- **候选上限与取消**：所有 A*、装箱、候选锚点和局部重排都设置展开次数/候选数量上限，响应现有生成 context 的取消和 4 分钟总截止时间。
- **确定性优先**：固定邻居顺序、tie-breaker 和候选排序，保证同一输入同一游戏事实目录得到同一结果，便于缓存和回归。
- **先拓扑、后几何**：拓扑排序、流量分配和 lane 数计算不依赖坐标；只有端口落点确定后才进入几何寻路，避免反复把同一物料图转换成坐标。

### 14.3 效率验收指标

除最终蓝图是否成功外，测试应记录：

- 流图节点/边数量、SCC 数量和 lane 数。
- 候选布局数量、路线寻路次数、平均/最大 A* 展开数和缓存命中率。
- 空间索引候选对数量与精确碰撞检查数量。
- 生成总耗时、各阶段耗时、取消响应时间和峰值内存。
- 建筑数量、内部带总长、跨层/跨 Area 接驳数、外部入口数和包围面积。

性能优化不能通过减少必要建筑、跳过路线、关闭碰撞检查或放宽容量约束取得。有效的优化应表现为：在相同守恒、带等级和验证覆盖下，减少无效候选、重复计算和路线回溯。

## 15. 方案最终判断

本方案可以有效解决当前的四类算法问题，也有机会提高计算效率，但前提是按“全局物料流 + 传输容量 + 端口级布局 + 抽象行星规则验证环境 + 增量验证”整体实现。单独构建一个抽象行星，或只增加一层碰撞检测，都不能解决产线排序、带速超载和内部断带。

最终交付应满足以下判断：

```text
当前系统：局部生成可用，全局规划未完成
本方案实现后：抽象规则范围内可统一规划和验证
真实游戏保证：必须按版本、模式、建筑、地形和世界状态另行验收
```

因此，文档中的“完成”定义为：在已声明的游戏版本和抽象规则覆盖范围内，算法对供需、容量、连通、空间、碰撞和特殊规则给出确定结果，成功时不需要手工拼接蓝图内部产线，失败时给出可操作诊断；不把未运行的 Unity Physics 或未知世界状态伪装成放置保证。

## 16. 最终用户行为

完成后，用户仍像现在一样选择传送带等级及生成模式，然后点击生成。生成器自动决定：

- 哪些生产节点在上游、哪些在下游；
- 哪些生产线共享同一份中间产物，哪些需要分开供料；
- 每种物料需要几条并行带、多少个边界入口和各路流量；
- 如何把所有蓝图内部上下游自动接起来；
- 在不破坏净空、端口容量和球面规则的前提下如何压缩产线区域和带路距离。

用户仍需在游戏里接入蓝图范围以外的原料、目标产品出口或其它外部基础设施，但不再需要手工拼接蓝图内部的生产节点。若当前带等级或模式无法通过流量、设备端口、寻路或球面预检，生成器明确指出瓶颈和可选操作，而不是返回一份内部链路不完整的蓝图。
