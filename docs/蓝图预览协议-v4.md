# 蓝图预览协议 v4（JSON 对接说明）

核对日期：2026-11-09，依据当前工作区实现。本文以请求和事件 JSON 为主；标为 `jsonc` 的代码块附有中文字段注释，实际传输时不含注释。示例 ID 与建筑数据用于说明结构，不是固定业务值。

## 1. 开启 v4 预览

将以下选项合并到完整的生成请求；仍须提供 `plan`、模式和布局配置等业务输入。

```jsonc
{
  "emitPreviewDeltas": true,      // 开启实时建筑差量
  "previewProtocolVersion": 4,   // 显式请求最新多候选协议；旧单场景沿用 v3
  "emitBlueprintProgress": false // 关闭旧 building-batch 最终建筑分块
}
```

调用入口为 `generateFactory(request, onProgress?, signal?, onTask?)`，位于 `frontend/src/pages/services/dysonSphere/factory.ts`。封装自动生成新的 `taskId`，先订阅再调用 Wails；传入请求的旧任务 ID 会被覆盖。

后端通过 Wails 事件 `factory:generationProgress` 直接发送下面的事件对象。

## 2. 开始搜索：search-start

```jsonc
{
  "taskId": "task-demo",      // 本次任务身份，用于过滤其他任务及迟到事件
  "protocolVersion": 4,      // 本事件的协议版本
  "kind": "search-start",    // 初始化多候选舞台，清理旧镜像和快照缓存
  "sequence": 1,             // 任务级序号，从 1 开始；所有阶段和候选共享计数
  "stage": "preview",        // 当前实际阶段，不用于推断任务成功
  "message": "开始候选方案搜索",
  "current": 0,              // 当前阶段计数，不是整个生成任务的百分比
  "total": 0                 // current、total 非负，且 current <= total
}
```

事件中的 `message` 可以为空字符串。后端在发布锁内分配全局序号并同步通知观察者，保持发布顺序。

## 3. 声明候选组：candidate-plan

```jsonc
{
  "taskId": "task-demo",
  "protocolVersion": 4,
  "kind": "candidate-plan",
  "sequence": 2,
  "stage": "preview",
  "message": "",
  "current": 0,
  "total": 0,
  "candidates": [
    {
      "id": "candidate-1", // 任务内稳定的候选身份
      "ordinal": 1        // 稳定顺序，从 1 开始；不按计算完成先后编号
    },
    {
      "id": "candidate-2",
      "ordinal": 2
    }
  ]
}
```

收到计划后即可铺开对应平台。每个实际启用的候选组可以各发一条计划；条件回退组在真正启用时追加。计划中的字段为 `ordinal`，单个候选事件中的字段为 `candidateOrdinal`。

## 4. 候选开始：candidate-start

```jsonc
{
  "taskId": "task-demo",
  "protocolVersion": 4,
  "kind": "candidate-start",
  "sequence": 3,
  "stage": "preview",
  "message": "候选方案开始生成",
  "current": 0,
  "total": 0,
  "candidateId": "candidate-1",
  "candidateOrdinal": 1,
  "candidateSequence": 1 // 此候选独立的连续序号，从 1 开始
}
```

对象和连接身份按 `(taskId, candidateId, objectId)` 隔离。不同候选可以交错发送，所以某个候选的全局 `sequence` 可以跳跃，候选内 `candidateSequence` 必须连续。开始、差量、候选结束、正式快照及预览完成均计入候选序号。

下面各节为独立结构示例；序号只示意合法取值，不构成一份可直接连续重放的完整日志。

## 5. 新增建筑：preview-delta / add

```jsonc
{
  "taskId": "task-demo",
  "protocolVersion": 4,
  "kind": "preview-delta",
  "sequence": 5,
  "stage": "assembly", // 还可能是 layout、routing、preview 等实际阶段
  "message": "",
  "current": 0,
  "total": 0,
  "candidateId": "candidate-1",
  "candidateOrdinal": 1,
  "candidateSequence": 2,
  "coordinateSystem": "layout-grid-v1", // 生成中的平面装配格
  "operations": [
    {
      "type": "add",                // 创建对象；当前候选镜像中不应已存在
      "objectId": "building-1",      // 稳定对象身份，不能用 building.index 代替
      "building": {
        "index": -1,                // 临时对象固定 -1，正式记录为非负索引
        "isTemporary": true,        // layout-grid-v1 必须为 true
        "itemId": 2001,             // 建筑物品原型 ID，正整数
        "modelIndex": 35,           // 模型原型索引，正整数
        "areaIndex": 0,             // 临时对象固定 0
        "localOffset": {
          "x": 14,                  // 平面横向坐标
          "y": 5,                   // 平面纵向坐标
          "z": 0                    // 高度
        },
        "localOffset2": {           // 同一建筑的另一端，不是第二座建筑
          "x": 14,
          "y": 5,
          "z": 0
        },
        "yaw": 90,                  // 首端朝向角
        "yaw2": 90,                 // 次端朝向角
        "tilt": 0,                  // 首端附加姿态
        "tilt2": 0,                 // 次端附加姿态
        "pitch": 0,                 // 首端附加姿态
        "pitch2": 0,                // 次端附加姿态
        "outputObjectId": "building-2", // 可选；同候选输出对象，允许后续才到达
        "inputFromSlot": -1,        // 输入来源槽位，至少 -1
        "outputToSlot": 1,          // 输出目标槽位，至少 -1
        "productionIndex": -1       // 原量化产线下标；-1 为共享设施
      }
    }
  ]
}
```

`inputObjectId` 与 `outputObjectId` 都是可选字符串，未提供的连接不能仅凭槽位绘制。位置和姿态各分量必须为有限数值。每条差量包含 1–128 项操作，按数组顺序处理，不含蓝图串、配方参数大数组或失败诊断。

## 6. 替换与删除：replace / remove

下面展示 `operations` 内的完整操作对象；外层沿用上一节的 `preview-delta` 结构。

```jsonc
{
  "type": "replace",
  "objectId": "building-1", // 必须已存在，身份保持不变
  "building": {            // 完整替换值，不是局部字段补丁
    "index": -1,
    "isTemporary": true,
    "itemId": 2001,
    "modelIndex": 35,
    "areaIndex": 0,
    "localOffset": {"x": 18, "y": 5, "z": 0},
    "localOffset2": {"x": 18, "y": 5, "z": 0},
    "yaw": 90,
    "yaw2": 90,
    "tilt": 0,
    "tilt2": 0,
    "pitch": 0,
    "pitch2": 0,
    "inputFromSlot": -1,
    "outputToSlot": -1,
    "productionIndex": -1
  }
}
```

```jsonc
{
  "type": "remove",
  "objectId": "building-1" // 必须已存在；删除不携带 building
}
```

重复新增、替换或删除未知对象会破坏镜像连续性。当前适配器停止实时过程，提示等待正式结果回放，不自行补造中间对象。

## 7. 普通阶段事件：phase（v1）

即使请求 v4，普通阶段通知仍可使用 v1，不能将整个回调限制为只接受 v4。

```jsonc
{
  "taskId": "task-demo",
  "protocolVersion": 1,
  "kind": "phase",
  "sequence": 4, // 和 v4 候选事件共享任务级序号
  "stage": "assembly",
  "message": "正在装配生产设备",
  "current": 1,
  "total": 3
}
```

阶段事件只更新文案，不修改建筑镜像。任务级消息不要求 `candidateId` 或 `candidateSequence`。

## 8. 候选结束：candidate-finish

```jsonc
{
  "taskId": "task-demo",
  "protocolVersion": 4,
  "kind": "candidate-finish",
  "sequence": 8,
  "stage": "routing",
  "message": "",
  "current": 0,
  "total": 0,
  "candidateId": "candidate-1",
  "candidateOrdinal": 1,
  "candidateSequence": 5,
  "candidateStatus": "valid" // 可选值 valid、rejected、pruned；不是字段名 status
}
```

`valid` 只表示候选可行，仍需等待选优。`rejected` 或 `pruned` 在自身已排队过程播完后独立退场；不能收到结束事件就跳过此前动画。

## 9. 正式快照：preview-snapshot

获选候选以正式 Area 坐标发送完整快照。下面为只有一个建筑、一个分块的示例。

```jsonc
{
  "taskId": "task-demo",
  "protocolVersion": 4,
  "kind": "preview-snapshot",
  "sequence": 9,
  "stage": "routing",
  "message": "",
  "current": 0,
  "total": 0,
  "candidateId": "candidate-1",
  "candidateOrdinal": 1,
  "candidateSequence": 6,
  "snapshotRevision": 1, // 当前每任务提交一次获选快照，版本为 1
  "chunkIndex": 0,       // 从 0 开始；零值可能省略，消费端默认 0
  "chunkCount": 1,       // 正整数，同一快照各块一致
  "coordinateSystem": "blueprint-area-local-v1",
  "primaryAreaIndex": 0, // 零值可能省略，消费端默认 0
  "areas": [
    {
      "index": 0,
      "parentIndex": -1, // -1 表示无父区域
      "tropicAnchor": 0,
      "areaSegments": 200,
      "anchorLocalOffset": {"x": 0, "y": 0},
      "size": {"x": 52, "y": 32}
    }
  ],
  "operations": [
    {
      "type": "add", // 快照每块 1–128 项，只允许 add
      "objectId": "building-1",
      "building": {
        "index": 0,           // 正式蓝图记录索引，非负
        "isTemporary": false, // 正式坐标记录，不代表游戏内放置已验收
        "itemId": 2001,
        "modelIndex": 35,
        "areaIndex": 0,
        "localOffset": {"x": 18, "y": 5, "z": 0},
        "localOffset2": {"x": 18, "y": 5, "z": 0},
        "yaw": 90,
        "yaw2": 90,
        "tilt": 0,
        "tilt2": 0,
        "pitch": 0,
        "pitch2": 0,
        "inputFromSlot": -1,
        "outputToSlot": -1,
        "productionIndex": -1
      }
    }
  ]
}
```

正式区域数组为 1–64 项，须包含主区域；后端在每块附带区域信息。预览 Area 使用嵌套的 `anchorLocalOffset`、`size`，蓝图编解码的原始 Area 仍是扁平字段。

临时 `layout-grid-v1` 的 `areas` 可以缺省或为空；正式 `blueprint-area-local-v1` 必须结合区域解释坐标。平台展示偏移仅属于前端，不写回建筑坐标或导出蓝图。

快照块先缓存，不作为普通新增逐块叠加到临时镜像。收到完成事件后，校验版本、总块数、块下标覆盖、无重复块、对象 ID 唯一和总建筑数，再原子提交。正式快照排在获选候选已有过程之后播放。

## 10. 预览完成：preview-complete

```jsonc
{
  "taskId": "task-demo",
  "protocolVersion": 4,
  "kind": "preview-complete",
  "sequence": 10,
  "stage": "routing",
  "message": "",
  "current": 0,
  "total": 0,
  "candidateId": "candidate-1",
  "candidateOrdinal": 1,
  "candidateSequence": 7,
  "winnerCandidateId": "candidate-1", // 应与正式生成返回值同名字段一致
  "snapshotRevision": 1,             // 对应已缓存的正式快照
  "chunkCount": 1,
  "coordinateSystem": "blueprint-area-local-v1",
  "buildingCount": 1,                // 完整快照的最终对象总数
  "batchCount": 3                    // 获选候选差量批次数，不含正式快照块
}
```

最终视觉结算要求正式调用成功、快照完整、事件与返回值获选身份一致。两条数据线可以任意先后到达；复制、保存和导出采用正式生成结果，不等待动画播完。

`batchCount` 不是全部候选批数，也不是总进度。它来自获选候选的差量通知器。部分计数字段为零时，后端的 `omitempty` 可能省略字段。

## 11. 搜索失败：search-failed

```json
{
  "taskId": "task-demo",
  "protocolVersion": 4,
  "kind": "search-failed",
  "sequence": 11,
  "stage": "preview",
  "message": "候选搜索未成功",
  "current": 0,
  "total": 0
}
```

失败分支不会产生虚假的获选平台。取消后发布器停止发送，不能假定所有失败或取消都有终止事件；还需结合调用错误、页面生命周期及日志结束收尾。

## 12. 日志补发：ReadGenerationProgress

Wails 方法实际签名为 `ReadGenerationProgress(taskId, afterSequence)`，按位置传参。以下 JSON 数组表示调用参数，不是新增的请求 DTO：

```jsonc
[
  "task-demo", // taskId
  9            // 最后已连续处理的全局 sequence；首次读取传 0
]
```

每页返回后续最多 16 项原始事件。下面以读取到最后一条完成事件为例：

```jsonc
{
  "events": [
    {
      "taskId": "task-demo",
      "protocolVersion": 4,
      "kind": "preview-complete",
      "sequence": 10,
      "stage": "routing",
      "message": "",
      "current": 0,
      "total": 0,
      "candidateId": "candidate-1",
      "candidateOrdinal": 1,
      "candidateSequence": 7,
      "winnerCandidateId": "candidate-1",
      "snapshotRevision": 1,
      "chunkCount": 1,
      "coordinateSystem": "blueprint-area-local-v1",
      "buildingCount": 1,
      "batchCount": 3
    }
  ],
  "next": 10,          // 本页最后事件序号；空页保持传入值
  "complete": true,    // 生产端已结束，且本页读至日志尾部；不表示生成成功
  "incomplete": false, // true 表示过程不可完整恢复
  "message": ""
}
```

上例假设从序号 9 之后读取。发生缺口时必须从最后连续序号补起，不能直接跳至完成事件。

日志过期或不可用时：

```json
{
  "events": [],
  "next": 8,
  "complete": false,
  "incomplete": true,
  "message": "生成过程记录已过期或不可用"
}
```

日志在实时发送前归档，保留最近两次任务，每任务最多 64 MiB，从创建起十分钟过期，正常退出时清理。超限、写入失败或读取范围无效也会明确标记不完整。当前恢复入口按任务读取历史日志，没有按候选获取任意当前快照的独立 RPC。

v4 订阅封装按任务过滤、去重和全局序号连续交付；开始收到事件后每 500 ms 尝试补发，调用返回时也读取尾部。渲染队列积压时暂停交付，后续从日志接续。恢复失败时提示过程不完整并转入正式结果回放。

## 13. 前端本地状态通知

以下对象由订阅封装本地派发，不是后端 v4 事件，因此不含 `protocolVersion`、`kind` 和 `sequence`。

```json
{
  "taskId": "task-demo",
  "stage": "preview-stream-incomplete",
  "message": "过程记录恢复失败，将使用正式结果",
  "current": 0,
  "total": 0
}
```

```json
{
  "taskId": "task-demo",
  "stage": "preview-stream-end",
  "message": "生成过程记录读取完成",
  "current": 0,
  "total": 0
}
```

前者终止不完整的实时过程；后者表示正式调用已返回且日志读取结束，用于收尾缺少成功完成事件的过程。

## 14. 对接规则

v4 按候选隔离对象、连接、镜像与播放队列，使用 `pace: 'cinematic'`。暂停、调速和跳过只控制演示，不改变算法选择。`AbortSignal` 停止观察、阻止旧结果进入页面并停止后续蓝图分片读取，不直接取消已经执行的 Go 任务。新任务或卸载时清理旧订阅、镜像、快照和动画。

当前 `preview.ProtocolVersion` 基础常量仍为 3，v4 由候选发布路径显式赋值。前端同时接受 v1 阶段/兼容完成事件、v3 预览和 v4 已知事件；未知版本或类型不进入场景。旧 `building-batch` 与 v4 `preview-snapshot` 应分别处理。

历史设计中的 `search-complete`、`groupId`、`bestCandidateId`、`scheduled`、`completed`、`totalKnown` 当前未进入事件契约；成功终止事件采用 `preview-complete`。

## 15. 蓝图预览的单候选转发（前端）

同一任务会同时产生多个候选的差量，但蓝图 viewer 只有一个场景。约定：页面转发层只把**一个**候选的过程喂给 viewer，正式画面永远由 `commitPreview` 决定；算法可视化继续消费完整多候选流（见第 14 节与 [候选镜像、快照组装与播放适配](../frontend/src/composables/dysonSphere/useAlgorithmFeed.ts)）。两条链路共享同一事件流，各自维护镜像。

### 15.1 请求侧同源

- 只要本次生成需要推进蓝图过程预览（调试差量或算法可视化跟随），就请求 v4：`previewProtocolVersion = wantDeltas ? 4 : 3`。
  **v3 无法用于过程预览**——v3 的候选共用同一个预览通知器（`fork()` 在非 v4 时返回根会话），差量是"每个候选依次全量替换"的合并流，viewer 会把所有候选轮流渲染一遍。
- v4 时补 `emitBlueprintProgress: false`，关闭旧 `building-batch`，避免转发层同时面对两套格式与两套文案。
- `GEN_E_PROGRESS_PREVIEW` 降级重试以 v3、无差量重发：转发层收不到事件，停在 `idle`，成功后 `commitPreview` 照常收尾。

### 15.2 转发层状态机

三个状态：`idle`（未跟踪）、`tracking`（跟踪中）、`wait-result`（等正式结果）。

**跟踪目标固定为候选 1**（`candidateOrdinal == 1`，身份形如 `candidate-1`），不随差量到达顺序变化；其余候选的事件一律丢弃。

| 事件 | 动作 |
| --- | --- |
| v3 `preview-delta` | 不转发：v3 为多候选合并流，会把每个候选依次渲染 |
| v4 `search-start` | 清空跟踪，回 `idle` |
| v4 `candidate-plan` / `candidate-start` | 忽略：蓝图固定跟候选1，不依赖计划是否下发 |
| v4 `preview-delta`（候选1，首条） | 自举：`expected = candidateSequence + 1` |
| v4 `preview-delta`（候选1） | `candidateSequence` 必须等于 `expected`：重写后转发并 `expected++` |
| v4 `preview-delta`（其他候选） | 丢弃 |
| v4 `candidate-finish`（候选1 且状态非 `valid`） | `discardPreview()` → `wait-result` |
| v4 `candidate-finish`（其他候选） | 忽略 |
| v4 `preview-snapshot` | 忽略：快照分块属算法可视化 |
| v4 `preview-complete` | `wait-result`：不取 winner、不切换候选 |
| v4 `search-failed` | 清空跟踪回 `idle`；`discardPreview` 由 `generate` 的失败分支统一执行 |
| `preview-stream-incomplete`（本地） | `discardPreview()` → `wait-result` |
| `preview-stream-end`（本地） | 若仍 `tracking` 则 `wait-result`：不会再有过程事件 |
| `generationTaskId` 变化 | 全量重置 |

关键取舍：

1. **固定候选1，不看到达顺序**。候选1 的 `candidateSequence` 通常从 2 开始（1 被 `candidate-start` 占用），因此自举以该候选首条差量的序号为起点，不要求等于 2。
2. **候选1 被剪枝即放弃过程预览**。临时层已缺对象，继续接收会让 `replace/remove` 落到未知对象；此时 `discardPreview()` 恢复旧画面并停在 `wait-result`，等 commit。不切换其他候选。
3. **不消费 `preview-snapshot` / `preview-complete` 的建筑数据**，正式画面只来自 `commitPreview(result.blueprint)`。
4. **5 分钟无新差量**转 `wait-result` 且**不** discard：画面冻结，等 commit 原子替换；避免卡死状态无限等待。

### 15.3 对象身份重写

转发前必须把候选内身份映射到单场景：

- `objectId` → `${candidateId}:${objectId}`；`inputObjectId` / `outputObjectId` 同步加前缀。
- 剥离 `candidateId`、`candidateOrdinal`、`candidateSequence`、`protocolVersion`；保留 `kind`、`stage`、`sequence`、`operations`、`areas`、`coordinateSystem`。
- 保留全局 `sequence` 供预览库去重（库在 `sequence <= lastSequence` 时丢弃；单候选子集仍严格递增）。

实测依据（单任务 226 条 delta、8 候选、6562 个操作）：490 个 `objectId` 中 **415 个被多个候选复用**（`building-1` 出现在全部 8 个候选），不重写必然串场景；单候选逐条模拟后均无重复 `add`、无未知 `replace`、无未知 `remove`，证明"只跟 delta、按 `candidateSequence` 连续推进"成立。

### 15.4 生命周期归属

`beginPreview` / `commitPreview` / `discardPreview` 由 `useQuantWorkspace` 持有，与 `debugMode` 解耦：viewer 就绪且本次请求会推进预览（v3 差量或 v4 单候选过程）时先 `beginPreview` 保存快照，成功 `commitPreview` 原子替换，失败 `discardPreview` 恢复。降级重试前先 `discardPreview` 恢复旧画面，避免整段重试停在空场景。

`viewer-panel.applyPreviewDelta` 另有一道防御：仍带 `candidateId` 或 `protocolVersion === 4` 的事件视为转发层漏过滤，返回 `true` 但不渲染。

### 15.5 调试观测

调试侧栏"生成事件"面板提供"预览转发"区块：阶段、目标候选（固定 `candidate-1`）、已跟踪身份、下一序号、应用/放弃计数，以及预览库的摄入计数（事件、操作、存活、丢弃、未知删、未知换、节流、最近/峰值耗时）。判据：

- 事件数应等于**候选1** 的 delta 数，而不是全部候选之和；
- 未知删、未知换应为 0（ID 重写正确性的直接判据）；
- 丢弃应为 0（`candidateSequence` 推进假设成立）。

一次实测（v4，8 候选）：226 条 delta / 6562 个操作，viewer 只摄入候选1 的 29 条事件、853 个操作、486 个存活对象，异常与丢弃均为 0。同一轮若误用 v3 请求，日志会是 252–326 条无 `candidateId` 的合并差量，viewer 将轮流渲染全部候选。

### 15.6 边界

蓝图侧不做候选切换、不铺多候选平台、不做快照分块重组、不依赖 `candidate-plan`；这些属于算法可视化职责。复制、保存、导出始终以正式生成返回值为准，与过程预览成败无关。
