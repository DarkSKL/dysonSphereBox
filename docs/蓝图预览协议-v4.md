# 蓝图预览协议 v4（JSON 对接说明）

核对日期：2026-11-16，依据当前工作区实现。本文以请求和事件 JSON 为主；标为 `jsonc` 的代码块附有中文字段注释，实际传输时不含注释。示例 ID 与建筑数据用于说明结构，不是固定业务值。

## 1. 开启 v4 预览

将以下选项合并到完整的生成请求；仍须提供 `plan`、模式和布局配置等业务输入。

```jsonc
{
  "emitPreviewDeltas": true,      // 开启实时建筑差量
  "previewProtocolVersion": 4,   // 显式请求最新多候选协议；旧单场景沿用 v3
  "emitBlueprintProgress": false // 关闭旧 building-batch 最终建筑分块
}
```

调用入口为 `generateFactory(request, onProgress?, signal?, onTask?)`，位于 `frontend/src/pages/services/dysonSphere/factory.ts`。封装自动生成新的 `taskId`，先订阅再调用 Wails；传入请求的旧任务 ID 会被覆盖。

后端通过 Wails 事件 `factory:generationProgress` 直接发送下面的事件对象。

## 2. 开始搜索：search-start

```jsonc
{
  "taskId": "task-demo",      // 本次任务身份，用于过滤其他任务及迟到事件
  "protocolVersion": 4,      // 本事件的协议版本
  "kind": "search-start",    // 初始化多候选舞台，清理旧镜像和快照缓存
  "sequence": 1,             // 任务级序号，从 1 开始；所有阶段和候选共享计数
  "stage": "preview",        // 当前实际阶段，不用于推断任务成功
  "message": "开始候选方案搜索",
  "current": 0,              // 当前阶段计数，不是整个生成任务的百分比
  "total": 0                 // current、total 非负，且 current <= total
}
```

事件中的 `message` 可以为空字符串。后端在发布锁内分配全局序号并同步通知观察者，保持发布顺序。

## 3. 声明候选组：candidate-plan

```jsonc
{
  "taskId": "task-demo",
  "protocolVersion": 4,
  "kind": "candidate-plan",
  "sequence": 2,
  "stage": "preview",
  "message": "",
  "current": 0,
  "total": 0,
  "candidates": [
    {
      "id": "candidate-1", // 任务内稳定的候选身份
      "ordinal": 1        // 稳定顺序，从 1 开始；不按计算完成先后编号
    },
    {
      "id": "candidate-2",
      "ordinal": 2
    }
  ]
}
```

计划仅声明身份，收到 candidate-start 后才占用显示槽。每个实际启用的候选组可以各发一条计划；条件回退组在真正启用时追加。计划中的字段为 `ordinal`，单个候选事件中的字段为 `candidateOrdinal`。

## 4. 候选开始：candidate-start

```jsonc
{
  "taskId": "task-demo",
  "protocolVersion": 4,
  "kind": "candidate-start",
  "sequence": 3,
  "stage": "preview",
  "message": "候选方案开始生成",
  "current": 0,
  "total": 0,
  "candidateId": "candidate-1",
  "candidateOrdinal": 1,
  "candidateSequence": 1 // 此候选独立的连续序号，从 1 开始
}
```

对象和连接身份按 `(taskId, candidateId, objectId)` 隔离。不同候选可以交错发送，所以某个候选的全局 `sequence` 可以跳跃，候选内 `candidateSequence` 必须连续。开始、差量、候选结束、正式快照、当前最佳及预览完成均计入候选序号。

下面各节为独立结构示例；序号只示意合法取值，不构成一份可直接连续重放的完整日志。

## 5. 新增建筑：preview-delta / add

```jsonc
{
  "taskId": "task-demo",
  "protocolVersion": 4,
  "kind": "preview-delta",
  "sequence": 5,
  "stage": "assembly", // 还可能是 layout、routing、preview 等实际阶段
  "message": "",
  "current": 0,
  "total": 0,
  "candidateId": "candidate-1",
  "candidateOrdinal": 1,
  "candidateSequence": 2,
  "coordinateSystem": "layout-grid-v1", // 生成中的平面装配格
  "operations": [
    {
      "type": "add",                // 创建对象；当前候选镜像中不应已存在
      "objectId": "building-1",      // 稳定对象身份，不能用 building.index 代替
      "building": {
        "index": -1,                // 临时对象固定 -1，正式记录为非负索引
        "isTemporary": true,        // layout-grid-v1 必须为 true
        "itemId": 2001,             // 建筑物品原型 ID，正整数
        "modelIndex": 35,           // 模型原型索引，正整数
        "areaIndex": 0,             // 临时对象固定 0
        "localOffset": {
          "x": 14,                  // 平面横向坐标
          "y": 5,                   // 平面纵向坐标
          "z": 0                    // 高度
        },
        "localOffset2": {           // 同一建筑的另一端，不是第二座建筑
          "x": 14,
          "y": 5,
          "z": 0
        },
        "yaw": 90,                  // 首端朝向角
        "yaw2": 90,                 // 次端朝向角
        "tilt": 0,                  // 首端附加姿态
        "tilt2": 0,                 // 次端附加姿态
        "pitch": 0,                 // 首端附加姿态
        "pitch2": 0,                // 次端附加姿态
        "outputObjectId": "building-2", // 可选；同候选输出对象，允许后续才到达
        "inputFromSlot": -1,        // 输入来源槽位，至少 -1
        "outputToSlot": 1,          // 输出目标槽位，至少 -1
        "productionIndex": -1,      // 原量化产线下标；-1 为共享设施
        "recipeId": 6,              // 可选；机器配方原型 ID，零值省略，仅用于建筑上方的配方图标
        "iconItemId": 1101          // 可选；传送带标记物品 ID（原料入口、成品出口），零值省略，仅用于带上方的物品图标
      }
    }
  ]
}
```

`recipeId` 与 `iconItemId` 是纯展示字段：缺失、为零或前端找不到对应图标时只是不显示图标，不影响对象身份、连接、碰撞或任何生成决策；出现时必须是非负整数。

`inputObjectId` 与 `outputObjectId` 都是可选字符串，未提供的连接不能仅凭槽位绘制。位置和姿态各分量必须为有限数值。每条差量包含 1–128 项操作，按数组顺序处理，不含蓝图串、配方参数大数组或失败诊断。

## 6. 替换与删除：replace / remove

下面展示 `operations` 内的完整操作对象；外层沿用上一节的 `preview-delta` 结构。

```jsonc
{
  "type": "replace",
  "objectId": "building-1", // 必须已存在，身份保持不变
  "building": {            // 完整替换值，不是局部字段补丁
    "index": -1,
    "isTemporary": true,
    "itemId": 2001,
    "modelIndex": 35,
    "areaIndex": 0,
    "localOffset": {"x": 18, "y": 5, "z": 0},
    "localOffset2": {"x": 18, "y": 5, "z": 0},
    "yaw": 90,
    "yaw2": 90,
    "tilt": 0,
    "tilt2": 0,
    "pitch": 0,
    "pitch2": 0,
    "inputFromSlot": -1,
    "outputToSlot": -1,
    "productionIndex": -1
  }
}
```

```jsonc
{
  "type": "remove",
  "objectId": "building-1" // 必须已存在；删除不携带 building
}
```

重复新增、替换或删除未知对象会破坏镜像连续性。当前适配器停止实时过程，提示等待正式结果回放，不自行补造中间对象。

## 7. 普通阶段事件：phase（v1）

即使请求 v4，普通阶段通知仍可使用 v1，不能将整个回调限制为只接受 v4。

```jsonc
{
  "taskId": "task-demo",
  "protocolVersion": 1,
  "kind": "phase",
  "sequence": 4, // 和 v4 候选事件共享任务级序号
  "stage": "assembly",
  "message": "正在装配生产设备",
  "current": 1,
  "total": 3
}
```

阶段事件只更新文案，不修改建筑镜像。任务级消息不要求 `candidateId` 或 `candidateSequence`。

## 8. 候选结束：candidate-finish

```jsonc
{
  "taskId": "task-demo",
  "protocolVersion": 4,
  "kind": "candidate-finish",
  "sequence": 8,
  "stage": "routing",
  "message": "",
  "current": 0,
  "total": 0,
  "candidateId": "candidate-1",
  "candidateOrdinal": 1,
  "candidateSequence": 5,
  "candidateStatus": "valid" // 可选值 valid、rejected、pruned；不是字段名 status
}
```

`valid` 只表示候选可行，仍需等待选优。实时舞台只保留正在计算的候选和后台当前最佳；收到结束事件后，非最佳候选立即停止补播，现有平台变红并下坠，其 GPU 对象按帧预算回收。后台历史记录不会因此删除。当前最佳被 rejected/pruned 时也执行相同退场。

## 9. 正式快照：preview-snapshot

获选候选以正式 Area 坐标发送完整快照。下面为只有一个建筑、一个分块的示例。

```jsonc
{
  "taskId": "task-demo",
  "protocolVersion": 4,
  "kind": "preview-snapshot",
  "sequence": 9,
  "stage": "routing",
  "message": "",
  "current": 0,
  "total": 0,
  "candidateId": "candidate-1",
  "candidateOrdinal": 1,
  "candidateSequence": 6,
  "snapshotRevision": 1, // 候选内每次完整快照递增；最佳与最终获选使用独立版本
  "chunkIndex": 0,       // 从 0 开始；零值可能省略，消费端默认 0
  "chunkCount": 1,       // 正整数，同一快照各块一致
  "coordinateSystem": "blueprint-area-local-v1",
  "primaryAreaIndex": 0, // 零值可能省略，消费端默认 0
  "areas": [
    {
      "index": 0,
      "parentIndex": -1, // -1 表示无父区域
      "tropicAnchor": 0,
      "areaSegments": 200,
      "anchorLocalOffset": {"x": 0, "y": 0},
      "size": {"x": 52, "y": 32}
    }
  ],
  "operations": [
    {
      "type": "add", // 快照每块 1–128 项，只允许 add
      "objectId": "building-1",
      "building": {
        "index": 0,           // 正式蓝图记录索引，非负
        "isTemporary": false, // 正式坐标记录，不代表游戏内放置已验收
        "itemId": 2001,
        "modelIndex": 35,
        "areaIndex": 0,
        "localOffset": {"x": 18, "y": 5, "z": 0},
        "localOffset2": {"x": 18, "y": 5, "z": 0},
        "yaw": 90,
        "yaw2": 90,
        "tilt": 0,
        "tilt2": 0,
        "pitch": 0,
        "pitch2": 0,
        "inputFromSlot": -1,
        "outputToSlot": -1,
        "productionIndex": -1
      }
    }
  ]
}
```

正式区域数组为 1–64 项，须包含主区域；后端在每块附带区域信息。预览 Area 使用嵌套的 `anchorLocalOffset`、`size`，蓝图编解码的原始 Area 仍是扁平字段。

临时 `layout-grid-v1` 的 `areas` 可以缺省或为空；正式 `blueprint-area-local-v1` 必须结合区域解释坐标。平台展示偏移仅属于前端，不写回建筑坐标或导出蓝图。

快照块先缓存，不作为普通新增逐块叠加到临时镜像。收到完成事件后，校验版本、总块数、块下标覆盖、无重复块、对象 ID 唯一和总建筑数，再原子提交。完整快照取代该候选尚未播放的历史队列；缺失对象先撤销，再按帧预算应用全部正式记录，不截断建筑。

## 10. 预览完成：preview-complete

```jsonc
{
  "taskId": "task-demo",
  "protocolVersion": 4,
  "kind": "preview-complete",
  "sequence": 10,
  "stage": "routing",
  "message": "",
  "current": 0,
  "total": 0,
  "candidateId": "candidate-1",
  "candidateOrdinal": 1,
  "candidateSequence": 7,
  "winnerCandidateId": "candidate-1", // 应与正式生成返回值同名字段一致
  "snapshotRevision": 1,             // 对应已缓存的正式快照
  "chunkCount": 1,
  "coordinateSystem": "blueprint-area-local-v1",
  "buildingCount": 1,                // 完整快照的最终对象总数
  "batchCount": 3                    // 获选候选差量批次数，不含正式快照块
}
```

最终视觉结算要求正式调用成功、快照完整、事件与返回值获选身份一致。两条数据线可以任意先后到达；复制、保存和导出采用正式生成结果，不等待动画播完。

`batchCount` 不是全部候选批数，也不是总进度。它来自获选候选的差量通知器。部分计数字段为零时，后端的 `omitempty` 可能省略字段。

## 11. 搜索失败：search-failed

```json
{
  "taskId": "task-demo",
  "protocolVersion": 4,
  "kind": "search-failed",
  "sequence": 11,
  "stage": "preview",
  "message": "候选搜索未成功",
  "current": 0,
  "total": 0
}
```

失败分支不会产生虚假的获选平台。取消后发布器停止发送，不能假定所有失败或取消都有终止事件；还需结合调用错误、页面生命周期及日志结束收尾。

## 12. 日志补发：ReadGenerationProgress

Wails 方法实际签名为 `ReadGenerationProgress(taskId, afterSequence)`，按位置传参。以下 JSON 数组表示调用参数，不是新增的请求 DTO：

```jsonc
[
  "task-demo", // taskId
  9            // 最后已连续处理的全局 sequence；首次读取传 0
]
```

每页返回后续最多 16 项原始事件。下面以读取到最后一条完成事件为例：

```jsonc
{
  "events": [
    {
      "taskId": "task-demo",
      "protocolVersion": 4,
      "kind": "preview-complete",
      "sequence": 10,
      "stage": "routing",
      "message": "",
      "current": 0,
      "total": 0,
      "candidateId": "candidate-1",
      "candidateOrdinal": 1,
      "candidateSequence": 7,
      "winnerCandidateId": "candidate-1",
      "snapshotRevision": 1,
      "chunkCount": 1,
      "coordinateSystem": "blueprint-area-local-v1",
      "buildingCount": 1,
      "batchCount": 3
    }
  ],
  "next": 10,          // 本页最后事件序号；空页保持传入值
  "complete": true,    // 生产端已结束，且本页读至日志尾部；不表示生成成功
  "incomplete": false, // true 表示过程不可完整恢复
  "message": ""
}
```

上例假设从序号 9 之后读取。发生缺口时必须从最后连续序号补起，不能直接跳至完成事件。

日志过期或不可用时：

```json
{
  "events": [],
  "next": 8,
  "complete": false,
  "incomplete": true,
  "message": "生成过程记录已过期或不可用"
}
```

日志在实时发送前归档，保留最近两次任务，每任务最多 64 MiB，从创建起十分钟过期，正常退出时清理。超限、写入失败或读取范围无效也会明确标记不完整。当前恢复入口按任务读取历史日志，没有按候选获取任意当前快照的独立 RPC。

v4 订阅封装按任务过滤、去重和全局序号连续交付；开始收到事件后每 500 ms 尝试补发，调用返回时也读取尾部。渲染队列积压不暂停控制事件交付；实时同对象状态合并，候选结束及时撤销显示，日志仍按连续游标恢复。恢复失败时提示过程不完整并转入正式结果回放。

## 13. 前端本地状态通知

以下对象由订阅封装本地派发，不是后端 v4 事件，因此不含 `protocolVersion`、`kind` 和 `sequence`。

```json
{
  "taskId": "task-demo",
  "stage": "preview-stream-incomplete",
  "message": "过程记录恢复失败，将使用正式结果",
  "current": 0,
  "total": 0
}
```

```json
{
  "taskId": "task-demo",
  "stage": "preview-stream-end",
  "message": "生成过程记录读取完成",
  "current": 0,
  "total": 0
}
```

前者终止不完整的实时过程；后者表示正式调用已返回且日志读取结束，用于收尾缺少成功完成事件的过程。

## 14. 对接规则

v4 按候选隔离对象、连接、镜像与播放队列，实时使用 `pace: 'follow'`，结果回放保留独立回放节奏。暂停、调速和跳过只控制演示，不改变算法选择。`AbortSignal` 停止观察、阻止旧结果进入页面并停止后续蓝图分片读取，不直接取消已经执行的 Go 任务。新任务或卸载时清理旧订阅、镜像、快照和动画。

当前 `preview.ProtocolVersion` 基础常量仍为 3，v4 由候选发布路径显式赋值。前端同时接受 v1 阶段/兼容完成事件、v3 预览和 v4 已知事件；未知版本或类型不进入场景。旧 `building-batch` 与 v4 `preview-snapshot` 应分别处理。

历史设计中的 `search-complete`、`groupId`、`bestCandidateId`、`scheduled`、`completed`、`totalKnown` 当前未进入事件契约；成功终止事件采用 `preview-complete`。

### 14.1 当前显示与资源策略

2026-11-16 用户确认“正在计算的候选＋当前最佳方案”，本节取代旧的全历史候选补播/统一下坠方案。

- 保留原生模型材质、2.5D正交视角、真实建筑与带连接；只改变展示集合和资源调度，不截断获选方案。
- candidate-start 为真实计算开始，分配可复用显示槽；不按历史 ordinal 留出大量空位。显示固定3×3槽位，总数最多9，包含当前最佳与正在退场的平台；后台计算并发独立。没有空槽的在算候选只维护最新队列，等待期间结束且未成为最佳的候选不再展示。
- candidate-best 仅由后台共同布局评分和完整验证结果产生，不按完成先后或平台位置猜测。当前最佳单独标注；切换时上一个最佳退出，新最佳通过正式完整快照恢复。
- 已结束的非最佳候选停止排队补播，现有平台先变红再下坠；原槽完全回收后，新的真实候选才从同槽向上升起。显示中的建筑保留入场动画；只有明确跳过或减少运动时立即落位。取消和暂停不会阻止已失效资源回收；共享模型缓存按原代次策略保留。
- 平台地板按实际建筑包络增加留白，使长宽比接近1且目标不超过1.35；不缩放或挪动真实建筑来凑方形。
- 平台整体平移复用建筑局部矩阵，不重新构造传送带截面；建筑姿态、连接、模型变化仍使局部几何失效。
- 选中、暂停、跳过、主题、模型加载、KeepAlive和已有最终蓝图回放沿用公开接口。最终调用返回、完整快照及winnerCandidateId必须一致才能宣布获选；保存、复制和导出使用正式结果，不等待动画。
- 不承诺实时逐个看完所有历史候选动作；后台跟踪/日志保留真实过程。这项显示策略不减少后台搜索能力，后台候选去重必须根据真实有效输入单独证明。

### 14.2 当前最佳事务

`preview-snapshot` 的格式不变。完整块发送之后，后台发送如下提交标记，再发送该候选的 `candidate-finish/valid`：

```json
{
  "taskId": "task-demo", "protocolVersion": 4,
  "kind": "candidate-best", "sequence": 10,
  "stage": "rules", "message": "当前最佳方案已更新", "current": 0, "total": 0,
  "candidateId": "candidate-1", "candidateOrdinal": 1, "candidateSequence": 7,
  "snapshotRevision": 1, "chunkCount": 1, "buildingCount": 1,
  "coordinateSystem": "blueprint-area-local-v1"
}
```

消费端先核对全部块、版本、对象唯一性和建筑数，再设置当前最佳。每个候选的 snapshotRevision 单调递增，最终 preview-complete 不能复用已经提交的最佳版本。已释放的平台允许通过该完整快照恢复；已 rejected/pruned 的候选不能被重复开始事件复活。

父作用域撤销、取消或失败使最佳失效时，后台先发送替代最佳事务，或发送任务级 `candidate-best-cleared`：

```json
{
  "taskId": "task-demo", "protocolVersion": 4,
  "kind": "candidate-best-cleared", "sequence": 11,
  "stage": "preview", "message": "当前最佳方案已撤销", "current": 0, "total": 0
}
```

该清空事件没有 candidateId/candidateSequence，仅推进任务级序号；重复清空不再发送。后台只保留一个最佳渲染快照与评分，不持有全部候选实体。v3不发送这两类事件，仍使用原单场景契约。


### 14.3 立体蓝图预览

立体预览在 viewer 就绪时请求 v4，按候选缓存增量并释放已淘汰候选。收到 `preview-complete` 后，按 `winnerCandidateId` 选出获选序列，重写对象和连接 ID，再在单个场景中回放。缓存超过 50,000 次操作、事件缺失或预览不可用时，直接显示正式生成结果。复制、保存与导出始终使用生成器返回的完整蓝图。
