# 戴森球球面纬圈布局生成方案

> 清理说明：量化与蓝图相关的测试文件、测试夹具、隔离验证入口和验收探针已按要求移除。本文保留历史验证记录，其中的测试名称、脚本路径与复核命令不再代表当前仓库可执行入口；产品运行所需的数据及碰撞体数据提取脚本保留。

> 状态：球面纬圈首个实现切片已落地，仍是实验性、未完成游戏内放置验收的功能。本文同时记录当前实现、验证证据与后续阶段。首要目标仍是实际放置时不因建筑体积、路线或碰撞失败；用户可指定纬圈，容量不足时可扩展到相邻纬圈，但这些选项目前不代表已获游戏内安全保证。

## 1. 结论

目标是把现有平面策略扩展为**以完整产线块为内容、按实际容量跨纬带编码的球面策略**。当前 mode 1–5 优先保留完整矩形；容量不足或整块锚点几何不通过时，将连接闭合的产线块重新装箱到一个或多个原生 Area，自动模式允许邻纬带扩展。建筑顺序、连接关系和各配方机器数不得丢失；旧平面请求不改变。新增带段交叉、分拣器 slotPoses 端点修正、距离/偏斜和拉伸建造盒检查，但完整 Unity Physics、通道设施、地形及已有实体仍未覆盖，结果保持 `partial`。mode 6 的跨块总线尚不能按此方式直接切开。复制、导出或保存不改变放置验证状态。

首要技术决策不是直接套用球体经纬度公式，而是先确认《戴森球计划》蓝图 `Area` 的 `TropicAnchor`、`AreaSegments` 与建筑局部坐标怎样映射到行星表面。生成结果应优先使用游戏原生纬圈网格/区域规则；只有游戏内导入实验确认连续球面投影与网格一致后，才采用连续几何近似。预览器能解析并绘制建筑坐标，但不能证明游戏会把它们放在目标纬圈，也不能替代游戏碰撞校验。

## 2. 当前行为与问题定位

当前后端已能生成经过 Go 编码器自检的 `BLUEPRINT:` 文本。量化与布局分别在 `helper/quant` 和 `helper/blueprint/build`，布局结果再交给 `helper/blueprint` 编码。

- 普通模式 1–5 共用 `Generate`。`lineCounts` 按带运力和每列机器数拆分产线；`buildLine` 将机器沿一个平面轴排列，并创建逐格传送带、分拣器及可选供电等对象。生成器通过 `bounds` 求轴对齐 XY 包围盒、平移块、按 `BlockWidthLimit` 换列，再按区块横向排开。见 `helper/blueprint/build/generate.go`、`line.go`、`primitives.go`。
- mode 6 独立执行 `generateBus`，产线块沿平面 y 方向排列，再建立最多三条首尾相连的矩形总线。`ring` 的坐标在 z=0 平面上按矩形四边逐格生成。见 `helper/blueprint/build/bus.go`。
- 当前坐标平移 `shift` 不做旋转/投影；`bounds` 用固定 XY footprint 估算占地；物流塔寻路主要是平面格点 A*，复杂路线另有离散高度桥接。它们目前没有行星纬度、纬圈容量、环向接缝或球面占地概念。
- 建筑总数包括机器以外的传送带格、每台机器的输入/输出分拣器、供电建筑、物流塔、站点接驳和回流设施。应先提供按原型/功能分类的建筑账单，才能判断用户感知的“过多”来自过长路线、重复分拣器、错误拆线还是必需的物流连接。
- 球面模式共同出口生成一个或多个原生 Area 及二维 `DragBoxSize`；`AreaSegments` 按候选粘贴纬圈的游戏段数设置，根 Area 的 `TropicAnchor` 和局部锚点保持游戏主区语义。目标绝对纬圈作为 `SurfacePlan` 的粘贴建议返回，不能伪造写入根 Area；`BlueprintViewer` 只显示原始平面建筑坐标。

因此，问题不能仅靠提高 `MaxMachineInALine`、加大 `BlockWidthLimit` 或末端把 XYZ 投影到球面解决。前两者可能让平面块更大，却仍没有纬圈坐标、接缝和碰撞规则；末端投影则可能使原本正确的平面连线在球面上改变长度、方向并互相穿插。

### 2.1 当前生成链路中的权重、参数与硬约束

当前代码没有一个统一的“蓝图质量分数”，也没有生成多个候选布局后择优的过程。可以把现状拆成三类：

| 层次 | 当前机制 | 实际影响 | 是否会直接减少最终蓝图建筑数 |
|---|---|---|---|
| 量化成本权重 | `CostWeight.Space`、`Power`、`BuildingCost`、`ItemExtraCost` | 在求解阶段影响设施/配方组合和 LP 目标成本；空间权重使用设施 `Space`，电力权重使用工作能耗，额外成本可惩罚特定建筑或副产物。 | 间接影响。它可能改变设施选择和机器数，但不会在生成阶段优化带、分拣器、塔和路线。 |
| 生成硬约束 | 带速、机器列上限、塔槽数量、路线可达、尺寸/建筑数量上限 | 不满足就拆列、换列、加塔、加桥或失败；例如 `lineCounts` 按带速和列上限拆分，mode 6 还受总线容量限制。 | 会改变辅助建筑数量，但不是成本最小化。 |
| 生成布局参数 | `Mode`、`MaxLays`、`MergeType`、`BlockWidthLimit`、`LocalStationHitRadius`、`NeedPower`、`UseMixed`、`NeedCoaterNet` 等 | 选择拓扑和空间打包方式；当前按确定性顺序生成，没有比较不同布局的代价。 | 会影响建筑数和路线长度，但结果由规则顺序决定。 |

量化成本的核心形式可概括为：

```text
设施成本 = 额外物品成本
         + 单位产出机器数 × (
             SpaceWeight × 设施占地 / 研究站层数
           + PowerWeight × 工作能耗
           + 指定建筑成本
           )
```

当前前端实际发送的 `SpaceWeight` 默认是 `1`，`PowerWeight` 默认是 `0`；前端工作台会暴露这两个值。后端还支持按建筑名和物品名配置成本，但当前页面没有把这些高级 map 成本作为布局选项展示。量化结果一旦生成，`factory.Service.Generate` 会校验 plan 快照并把它当作固定输入，布局阶段不会重新选择更省空间的机器或配方。

生成参数中，`BeltSpeed` 和各类列上限是容量约束；`BlockWidthLimit` 与 `LocalStationHitRadius` 是平面装箱/留白参数；`NeedPower`、`NeedCoaterNet`、`UseMixed` 会直接改变辅助网络；`Mode` 是离散拓扑选择，不是一个可连续调节的权重。当前不存在“路线长度权重”“物流塔数量权重”“跨纬圈代价权重”“目标纬圈偏差权重”或“接缝风险权重”。这正是球面布局需要新增的优化层。

## 3. 目标与边界

### 目标

1. 新工作区默认自动选择纬圈；用户可以指定纬圈并决定是否允许邻圈回退。生产路径先尝试完整矩形，再按闭合块容量及实际静态盒几何重排，自动模式允许扩展到邻纬带。旧请求不带新参数时保持平面行为；尚无 Unity 场景验证过的“安全候选”集合。
2. 用户指定纬圈后，布局优先满足该圈的可放置性；容量不足或碰撞风险不可消除时，按策略扩展到相邻纬圈，并明确记录扩展原因和范围。
3. 输送带、分拣器两端、物流塔、供电、喷涂和回流等对象共享同一个空间/占用模型，不能只让机器落在球面而让连线仍留在错误的平面坐标系。
4. 以“可正常拍出”为第一验收目标：自动硬校验无冲突、连接可达、容量足够，且通过当前游戏版本的导入放置验证。当前仍未通过游戏内导入/Physics 验收；建筑数量和路线长度只能作为次级优化目标。
5. 以可解释的建筑分类账单、冲突诊断和游戏导入回归验证布局效果，同时保持量化产能、蓝图编码自检、旧工作区 JSON 和已有生成模式的兼容性。

### 非目标

- 不改量化算法，不减少求解器给出的机器数量，也不把“少建筑”作为删除必要物流设施的理由。
- 不在第一阶段把用户手工导入的任意蓝图自动重排或改写。
- 不依赖 3D 预览截图作为游戏可放置/碰撞正确的证明。
- 不一次性重写六种布局模式或蓝图编码协议。

## 5. 方案设计

### 5.1 兼容的布局配置

当前 DTO 已落地 `planar`、`autoTropic` 和 `explicitTropic`。缺省/旧请求仍走平面模式，前端新工作区会发送球面布局配置。球面坐标适配目前只允许 `GridSegment=200`；其它分段数会失败关闭。下方概念字段中尚未实现的经度起点和独立 clearance 不能当作现有选项。

为生成请求增加版本化布局配置，建议由后端 DTO 定义并由前端 Wails 绑定生成，不手改生成文件。概念字段：

```text
surfaceMode: planar | autoTropic | explicitTropic
latitudeBand: 游戏 Area/TropicAnchor 可表达的纬圈标识（explicitTropic 时使用）
longitudeOrigin: 环向起始网格索引（可选）
bandPolicy: selectedOnly | spillToAdjacent | splitBlueprint（默认 spillToAdjacent）
clearance: 最小安全间距/占位膨胀策略
```

新工作区默认值为 `autoTropic`；当前自动候选来自游戏网格段表与离散纬带容量规则，不是已通过 Unity 场景碰撞验收的“安全纬圈集合”。用户指定纬圈时使用 `explicitTropic`，可按请求允许扩展到邻圈；不允许扩展且容量不足时直接失败。历史请求/JSON 缺少布局配置时仍按 `planar` 处理。UI 以纬向细格索引表示纬线，不把十进制度数直接写进 `TropicAnchor`。当前面积编码规则通过本机游戏 DLL 的 Area 条件函数和固定样本核对，但真实粘贴锚点、旋转及 Physics 仍待游戏内验证。

### 5.2 分层架构

将当前生成流程拆成“生产拓扑 → 布局策略 → 游戏坐标适配 → 全局校验 → 编码”：

1. **生产拓扑**：保留现有量化结果、产线依赖、机器数和物流需求；输出机器/带/分拣器/站点连接图，不含目标星球坐标。
2. **平面布局策略**：保留现有 mode 1–6 算法，作为兼容策略。
3. **纬圈布局策略**：在局部整数网格里放置拓扑块，使用选定纬圈的可用网格容量和环向邻接关系；管理跨缝、邻纬圈扩展和拆分。
4. **游戏坐标适配器**：把局部网格、旋转方向、建筑端点和 Area 元数据转成经验证的蓝图记录。集中处理 `AreaSegments`、`TropicAnchor`、锚点和纬圈格距，避免在每个建筑构造函数散落球面公式。
5. **全局占位/路线校验**：所有对象按占地、方向、高度、端点纳入同一空间索引。路径先规划再写入；不能找到无碰撞路线就返回可读布局错误或建议拆分，不输出部分蓝图。
6. **编码与自检**：继续调用严格 Go `blueprint.Encode`；额外校验业务布局不变量。编码自检只证明序列化往返一致，不证明游戏内放置合法。

建议的窄接口概念如下，具体类型待坐标契约确认后设计：

```text
LayoutStrategy.Place(topology, layoutConfig) -> PlacedGraph
SurfaceAdapter.ToBlueprint(PlacedGraph, surfaceConfig) -> BlueprintDocument
LayoutValidator.Validate(PlacedGraph, surfaceConfig) -> diagnostics
```

普通模式的平面 AABB 可以继续用于平面策略；纬圈策略需要环向区间/接缝感知的占位表示，以及对建筑朝向后真实 footprint 的变换。不要将旧 `bounds` 直接复用为球面碰撞判定。

### 5.3 纬圈容量与环向排布

- 使用游戏纬圈网格的实际格点数和邻接关系确定可用长度；球面公式只用于预估/解释，不能代替游戏网格。
- 将工厂块作为不可拆或受约束可拆的 footprint 放进有界环带；每块含机器、带、分拣器及它的必要局部接驳。路由也占位。
- 对每个块记录环向起止格。越过起点/终点时必须切成环上两个区间参与冲突检查；“取模”只能表示拓扑邻接，不能让空间上冲突的两个块被接受。
- 优先采用有限长度的纬圈弧段，不默认闭合成整圈。若布局必须闭环，接缝要作为明确的边处理并预留连接净空。
- 当前生产路径会按配置搜索邻圈锚点，但仍把完整矩形放在同一个恒定经度段纬带，不逐块扩展。独立装箱算法的边缘/环向余量尚未用于生产，也尚未提供多份蓝图拆分。游戏内导入/碰撞矩阵未通过前，邻圈回退与自动选圈都只是生成器实验能力，不能标示为安全放置。
- 自动选圈的“最优”不是简单选择最大圈或赤道，而是：先排除无法证明可放置的圈，再优先选择碰撞安全余量高、无需跨圈且路线可达的候选；候选都合法时，再比较路线长度、辅助建筑数和稳定性。
- 靠近极区时离散格距/圈长快速收缩，设置经过实验得出的最小可用圈阈值；不允许无限缩放或把建筑投到同一位置。

### 5.4 建筑数量和重复布局控制

生成前后都输出分类账单：机器、传送带、分拣器、电力、喷涂、物流塔、桥接、总线/回流，并记录每个分类的新增原因。用于对比同一生产方案在平面、赤道和目标纬圈下的建筑数与路线长度。

可优化的候选：减少不必要的长距离供给带、共享可证明安全的局部物流通道、让拓扑块沿局部邻接布置、容量足够时避免因平面列宽策略提前拆线。每项优化必须保持机器数量、输入输出连接、速率约束与共享设施归属不变。不要通过缩短带路造成断连、删除分拣器、弱化多产物出口或忽略塔端口来降低建筑数。

关于“绕一圈又绕回去”：先加入环向有界放置和 wrap 冲突测试；针对每条连接检查最短合法路线、拓扑端点和路线复用。mode 6 的矩形闭环总线需独立设计为“球面总线拓扑”，不能把现有矩形 ring 的 X/Y 替换成经纬角后认为完成迁移。

### 5.5 球面布局的推荐权重模型

球面布局应采用“两阶段决策”：先过滤硬约束，再比较合法候选。碰撞、断路、超出纬圈容量和编码失败不能被软分抵消。下文的初始权重是未来筛选完整且已验证候选后的产品设计，不是当前代码行为；当前自动模式使用的实际排序见 12 节。游戏内碰撞规则尚未覆盖的结果只能标为 `partial`，不能宣称可放置；当前复制、导出和保存只提供风险提示，不把操作可用性当作放置证明。

对通过硬约束的候选，可先用归一化后的 100 分软目标作为实现初期的可解释基线：

| 软目标 | 初始权重 | 计算方向 | 说明 |
|---|---:|---|---|
| 球面占位安全余量与规则可信度 | 45 | 安全余量越大、原型/网格规则越可信越高 | 冲突和未验证规则不能用分数补偿；未验证候选默认不得自动选中。 |
| 路线可达与局部净空 | 25 | 合法路线越短、转弯/升降/跨缝越少越高 | 连通和净空是硬门槛，路线长度只在合法候选间比较。 |
| 邻圈扩展与目标圈偏差 | 15 | 使用目标圈或更少邻圈扩展越高 | 用户指定纬圈时优先贴合；自动模式下用于减少不必要的跨圈。 |
| 额外建筑成本 | 10 | 传送带、分拣器、塔、桥接、电力和喷涂设施越少越高 | 机器数量属于量化结果，默认不允许布局阶段改变；不得以删必要对象换分。 |
| 分区与拆分稳定性 | 5 | 跨接缝和蓝图拆分越少越高 | 仅作为合法候选的最后排序条件。 |

这些数值是以“实际可放置”为核心的初始产品策略，不是游戏常数，也不应直接写死在求解器里。实现时应保留权重版本和每项原始指标，输出类似 `scoreBreakdown` 的诊断数据，使用户能看到“为什么选择这一圈”。当用户明确选择“只能在该纬圈”时，目标纬圈变成硬约束；当用户允许邻圈扩展时，才启用邻圈偏差评分。自动模式不得在仅有未验证候选时给出“最优”结论。

建议的比较顺序为：

1. 先验证产能、连通、容量、坐标、碰撞、净空和编码等硬约束；任何无法确认可放置的候选不得作为默认结果。
2. 自动模式在合法候选中最大化球面安全余量和规则可信度；指定模式优先满足用户纬圈，再比较安全余量。
3. 在安全合法的候选中最小化跨圈扩展、路线长度和辅助建筑数量。
4. 最后用分区数量、接缝数量、候选生成耗时和稳定性打破平分。

不要把量化阶段的 `SpaceWeight` 直接复用为“蓝图路线空间权重”。前者以设施占地参与配方/设施选择，后者应以真实生成的建筑、带和路径账单参与布局评分；两者单位和决策阶段不同。可在工作区同时展示两类指标：`quantizationCost`（量化成本）和 `layoutCost`（蓝图布局成本），避免用户以为提高空间权重就会自动修复环向回绕。

## 6. 碰撞与放置正确性

现有 `footprint` 是按原型定义的固定 XY 包围盒；普通块边界用该占地做轴对齐 bounds，部分路径占位没有统一做 yaw 变换。`findPath` 与桥接验证也基于离散平面格点。因此，现在的 AABB 或“同格没有两个机器中心”只能是粗略检查，不能证明建筑模型、带、分拣器或游戏表面没有碰撞。

### 6.1 碰撞对象和判定层次

每个已放置对象都要形成统一的 `Occupancy` 记录，至少包含对象/原型 ID、对象类别、所属产线、Area/纬圈、锚点、朝向、两端坐标、实际高度范围、占地几何、连接端口和数据来源版本。不能只从最终建筑中心点反推所有信息，因为分拣器等对象有两个端点，塔/分流器有非中心端口，部分层叠机器高度也不相同。

| 对象对/规则 | 必须检查的内容 | 第一阶段可用的保守表示 |
|---|---|---|
| 机器/机器、机器/塔、机器/电力设施 | 原型 footprint、朝向旋转、地面高度、建筑之间的安全间距。 | 以游戏验证过的旋转占位格为窄相位；未验证方向或原型时膨胀 footprint，状态标为待验证。 |
| 分拣器/机器、分拣器/带、分拣器/分拣器 | 两端锚点、连接建筑与 slot、臂长度、方向/倾角、经过空间及垂直净空。 | 端点及扫掠包络都入占位；只检查中心点不足以放行。 |
| 带/带、带/机器、带/塔 | 每段路径格、带宽或游戏离散占位、坡升/下降及端口接入区。 | 以整条离散路径逐格检查并膨胀一格安全余量；路由规划与占位登记共用同一索引。 |
| 物流塔/其他对象 | 塔 footprint、碰撞/禁建半径、槽口/接驳空间、塔间距。 | 塔本体和保留区分开记录，路线不可穿过保留区；具体半径以游戏实测/可信原型表为准。 |
| 高架带/地面对象、不同层设施 | 对象真实高度区间、支架/升降段占位和垂直间隙。 | 用 3D 包围体做宽相位；净空未知时不得仅凭 Z 不相等就认定安全。 |
| 纬圈/接缝/相邻圈对象 | 球面或原生网格邻接、经度周期边界、圈间距离和极区收缩。 | 必须以目标 Area 的离散网格索引做周期感知冲突查询；经度取模后不能丢失同一物理格的别名关系。 |

碰撞状态要分层表达：`hardConflict`（已知规则下确定冲突）、`clearByModel`（通过当前占位模型）、`unverified`（游戏规则/原型数据未知）、`unreachable`（路径不能连通）。当前实现能拒绝静态建造盒碰撞和未知静态原型，并检查部分连接距离；但还不具备完整对象对覆盖，也未与当前运行游戏版本作动态校验。游戏内验收前，`clearByModel` 不能映射为“可放置检查通过”。承诺范围必须限定为已验证的游戏版本、建筑、模式、方向、纬圈和环境条件。

当前代码覆盖与缺口：静态碰撞目录从本机游戏构建 `25955035` 的数值 `buildColliders` 建立，并已从同一版本 `PrefabDesc/SlotConfig` 提取建筑端口、分拣器插入端口和附加区域几何；端口事实已用于分拣器修正及数值预检，但不能据此声明游戏内放置通过。对纳入检查的建筑按最终 float32 坐标变换为世界 OBB，采用空间哈希宽相位与 OBB 窄相位检查。球面传送带会检查已记录建筑连接的部分世界距离限制。静态碰撞集合不含传送带和分拣器，两者由动态数值检查分开处理；完整传送带 Physics 胶囊/通道豁免、分拣器逐帧摆臂、已有实体、地形/水面和 Unity Physics 查询尚未实现。版本目录也不检测用户当前游戏构建或运行时 Mod。

### 6.2 球面占位与碰撞算法

碰撞算法采用宽相位加窄相位，不能为所有对象做昂贵的全量两两比较：

1. 由游戏坐标适配器将每个对象转换为目标 Area 上的离散占位格和高度区间；对于无法直接表达到格点的对象，保留局部几何包络和映射误差。
2. 以纬圈/Area + 网格 cell + 高度层建立空间哈希或等价索引。索引必须处理经度周期边界，候选对象的包络跨缝时拆成多个索引片段，查询仍映射到同一环形邻域。
3. 宽相位找出相邻占位对象；窄相位比较旋转后的 footprint/路径扫掠包络、端口保留空间和高度区间。已知不相容就拒绝布局，不能用 `clearance` 分数抵消硬冲突。原型或碰撞规则缺失时按未知处理并拒绝自动生成，不允许把候选降级后仍当成功蓝图返回。
4. 浮点蓝图记录在写出前会量化为 float32；碰撞检查必须对最终量化后的坐标再执行一次，或在此前按最大量化误差膨胀占位，避免 double 精度下无冲突而编码后坐标合并。
5. 只有 validator 全部硬检查通过，才允许交给编码器；编码器自解码之后再核对对象数、连接索引和坐标摘要未发生变化。

球面距离可以用于安全余量和候选评分，但建筑合法格与邻接应由阶段 0 验证的原生网格提供。连续球面近似不能自行发明可放置规则。若一个原型的 footprint/朝向无法映射到已知网格，validator 应返回 `unverified` 或拒绝该候选，而不是默认零占地。

### 6.3 路由和碰撞诊断

路线规划须采用“规划一段、校验一段、提交一段”的事务式过程：候选路线只在完整验证成功后写入共享占位索引；失败尝试释放临时占位，不能留下半条带或影响后续候选。路由成本可包含长度、转弯、跨纬圈、跨缝、升降段和穿越保留区的惩罚，但这些只是合法路径之间的软代价。

每条失败报告至少指出对象 ID/类别、冲突对象 ID/类别、目标 Area/纬圈、网格或局部坐标、层高、冲突规则及数据来源。例如“传送带 B42 在纬圈 L7 的接缝 cell 0 与机器 M18 footprint 冲突”。用户界面可按错误严重度显示列表，并允许预览中定位候选；但预览器图形只能帮助诊断，不能参与碰撞判定。

建筑数量账单要与碰撞诊断关联：若为避碰新增了绕行带、物流塔或桥接，账单记录 `reason=collision_avoidance` 和被避开的占位；这样才能区分真正的冗余与避碰所需的额外建筑。

第一阶段可以将未适配设施限制在目标纬圈局部区域，明确拒绝跨纬圈大路由；以明确失败替代可能重叠的“尽力生成”。启用跨圈路线前，必须具备离散网格映射、跨圈占位和游戏内验证。

## 8. API、工作区与预览兼容

- `build.Request` 增加可选布局配置；新工作区缺省使用 `autoTropic`，旧请求/旧 JSON 缺少布局字段时按 `planar` 解释；服务仍使用已求解 plan 快照校验来源，不信任前端重写量化结果。球面模式沿用旧平面记录，只增加整块锚点候选和预检回退。
- 工作区 JSON 增加 schema 版本和可选布局配置；没有版本/配置的历史 JSON 读取为旧平面行为。导出新 JSON 要能被当前版本重新导入并复算。
- `ProductionBinding`、`Zone` 继续表达生产索引、建筑归属和预览分区；若新增纬圈/环向可视信息，应新增明确的布局结果 DTO，不能复用平面 `MinX/MaxX` 伪装球面距离。
- 预览器使用原始 BLUEPRINT 字符串进行 Three.js 绘制，当前 `BlueprintViewer` 并不代表真实游戏地表曲率或落点规则。UI 显示自动选择/用户指定的纬圈和邻圈扩展结果；球面输出标成 `partial`，复制、导出和写入蓝图库被拦截。只有完成实际游戏版本验收后，才能增加“可放置检查通过”状态。
- `DragBoxSize` 是二维头字段，Area 是离散元数据；如一个蓝图跨多个 Area/纬圈，应在格式样本和游戏导入验证后再决定是一份多 Area 蓝图还是拆成多份蓝图。所有本地生成结果（包括旧平面兼容结果）在 `PlacementStatus` 未为 `verified` 前都禁止复制、导出和写入蓝图库；导出确认期间若结果版本或编码发生变化，必须取消本次操作。

## 9. 验证计划与验收指标

### 自动验证

1. 固定输入/数据集/mode/settings 时，机器数、配方、产出与 PlanID 不变；默认自动选圈必须从已验证纬圈集合中产生结果。
2. 平面策略对既有参考蓝图保持建筑记录或语义级回归一致。
3. 每种建筑以方向变换后的 footprint 检查静态冲突；分拣器端点、连接 index、塔 slot 与带路径一致；所有 `hardConflict` 都必须拒绝生成。
4. 碰撞用例至少覆盖：机器旋转 0/90/180/270 度、footprint 相切/重叠边界、机器-机器、机器-带、机器-塔、带-带、分拣器双端点与扫掠区、高架/地面净空、研究站叠层、float32 量化后占位合并。
5. 纬圈环向容量边界：刚好放下、差一格、跨接缝、两块跨缝相撞、相邻纬圈隔离、极区低容量拒绝；碰撞索引要验证 wrap alias 不会漏报。
6. 随机生成小型拓扑做属性测试：所有建筑索引唯一、所有连接指向存在建筑、路线相邻且连续、占位无冲突、机器数和产能不变；随机平移/旋转后冲突判定保持一致。
7. 对计数、最长路径、布局面积、生成耗时与最大内存建立基线；重点观察是否减少不必要的带格和回绕路线，而不只追求 blueprint 文本短。
8. 对每个成功生成的结果仍运行严格 Encode/Decode 自检，并独立运行业务 validator；自动模型通过与游戏内验证状态分别记录。未覆盖的原型/朝向/模式/游戏版本必须阻止“可放置”成功状态。当前 Go 单测覆盖装箱、Area、坐标和静态 OBB/连接距离；尚无 Unity Physics 或游戏内粘贴自动化测试。

### 游戏内验收

每个阶段准备可复现的小型 `.txt`/蓝图编码，并在当前正式游戏版本中导入、预览放置和实际确认：赤道、中纬、非最大圈、高纬/极区边界、经度接缝、长带、机器 footprint 方向变化、带/机器相切、分拣器双端点、塔安全区、研究站叠层/高架净空、混料和副产物。重点检查游戏提示的红色/不可放置对象以及批量放置后实际重叠。记录游戏版本、星球半径/格网、是否有 Mod、成功/失败截图、冲突对象类别及位置；至少为常见建筑原型建立方向和占位样本集。一个模式的“可放置保证”需由该模式测试矩阵全通过后才启用；其余未覆盖模式应明确显示未验证并阻止当作保证可用的结果导出。

### 效果指标

- **正确性门槛**：自动模式选择已验证安全的纬圈；指定纬圈按规则扩展到邻圈；无自相交/重复占位，所有连接可达，产线机器数/产能不变。
- **重叠门槛**：支持范围内自动占位检查零冲突，且覆盖的游戏内样本无不可放置对象或建筑/带/塔碰撞；未覆盖情况不显示保证状态。
- **规模对比**：按同一 plan 报告每类建筑数量、最长带路、总路线格数、列/圈数、边界浪费比例；为每个指标与平面基线比较。避免先设“必须少 N%”这类缺少真实样本支撑的承诺。
- **回退门槛**：旧请求、旧工作区方案和旧平面模式仍可以生成、导入、复制和导出。

## 10. 主要风险与决策门

| 风险 | 影响 | 处理 |
|---|---|---|
| `TropicAnchor`/`AreaSegments` 语义不明 | 锚点单位或区段映射错误，蓝图落到错误纬线。 | 阶段 0 用游戏导出样本与最小导入实验确认。 |
| 蓝图建筑坐标并非连续球面坐标 | 经纬度/ECEF 写入后模型看似合理但游戏内不可放置。 | 使用游戏原生网格 adapter；不直接写地心 XYZ。 |
| 纬圈容量与经度接缝规则随星球半径/游戏版本变化 | 高纬布局密度错误或 wrap 重叠。 | 将星球/网格配置显式化；不同半径跑样本；未知时拒绝生成。 |
| 设施 footprint/朝向和物流槽规则不完整 | 静态无冲突仍会在游戏内重叠。 | 方向感知占位、保守安全余量、阶段性游戏实测。 |
| mode 3/4/6 路由依赖平面寻路 | 末端投影后连接断开、塔接驳穿越或回流重叠。 | 逐模式迁移，复用统一占位/路线图，不做最后一步全局投影。 |
| 一次迁移全部模式导致回归面过大 | 现有可用平面生成被破坏。 | 平面默认与新策略并存，按阶段明确启用。 |
| 把建筑总数下降误当唯一成功指标 | 删除必要带/分拣器、破坏产能或输出链。 | 机器和拓扑不变量优先，分项账单与路线效率联合评估。 |

## 12. 当前实现与范围

当前实现覆盖 `planar`、`autoTropic`、`explicitTropic` 三种布局请求。没有布局字段的旧请求继续按平面策略生成。球面布局采用本机游戏 build `25955035` 已核对的纬圈分段规则，只接受 `GridSegment=200`；自动模式按离赤道距离枚举完整平面 footprint 可容纳的锚点，再执行接线距离和静态建造盒预检。自动初选不受 `expandAdjacent=false` 限制；该开关只决定指定模式能否离开用户给定锚点。

球面编码器优先保留完整矩形；单纬带容量不足且允许扩展时，先由 `surface_rectangle.go` 在不截断设施的切面建立相邻原生 Area，按区域段数换算经向坐标，保留原建筑索引和跨区连接。矩形仍无法通过时，mode 1–5 用 `surface_multi.go` 接入 `surface_pack.go` 的 shelf 规划器。非塔式布局按独立机器行封装，塔式按塔组封装；喷涂供剂网在块内独立建立。装箱时按实际静态盒过滤可用纬向行，环向首尾及带间均留间距。每个建筑及两端归入同一个 Area；闭合块装箱仍明确拒绝跨块连接，不能静默切断。南北连续纬带保留中间空 Area，父链朝主区域收敛；主区域不一定为 0。指定且禁止扩展时保留原锚点。绝对纬度仍只作为 `SurfacePlan` 建议，不伪造写入根 Area。DLL 脚本按各 Area 的实际盒原点对照首端、次端原始世界坐标。

碰撞目录保存构建 `25955035` 的数值建造盒与来源指纹。静态建筑运行世界 OBB 空间哈希及分离轴检查；带检查已连接端点距离和无共享节点的三维段交叉，高架按实际高度区分，转弯/汇流不按无连接交叉误判。分拣器按机器 slotPoses 修正端点与姿态，再核对修正量、长度、加权跨格、相对旋转及偏斜，按游戏预览公式拉伸动态盒。分拣器之间检查占用，按预览类别豁免与非分拣器的重叠。未知端口/模型失败关闭。带段检查是保守的内部路径约束，不是完整 Physics 预览胶囊/通道豁免复现；没有覆盖摆臂逐帧运动、已有实体和地形。

因此球面生成结果的 `PlacementStatus` 仍为 `partial`。界面保留预览；未验证结果（含没有 SurfacePlan 的旧平面结果）目前仍允许复制、导出和保存，操作时显示风险提示，旧结果确认与快照一致性检查继续保留。静态 DLL 调用和数值 fixture 证明的是代码对已知坐标/Area 规则的复现，不是 Unity 场景内粘贴或实际放置的结果；也不覆盖用户当前安装的游戏构建和 Mod。

自动选择目前是容量过滤、靠近赤道优先、碰撞失败回退的确定性启发式，尚未按碰撞余量、路线代价和原型覆盖建立加权评分。第 5.5 节权重表仍是完整验证后的候选比较设计，不应解释为当前实现。

## 13. 游戏规则核对与验证记录
