# 用户登录与账号全流程客户端对接文档

本文档依据当前后端路由、API 请求模型和前端调用整理。部署时若配置了 `system.router-prefix`，请在所有路径前追加该前缀（例如 `/api/base/login`）。

## 1. 基础约定

- 默认服务地址：`http://127.0.0.1:8888`
- JSON 请求头：`Content-Type: application/json`
- 私有接口鉴权：`x-token: <JWT>`；前端还会发送 `x-user-id: <用户ID>`。
- 上传接口使用 `multipart/form-data`，不要手动设置 boundary。
- 统一响应：`{ "code": 0, "data": {}, "msg": "成功" }`。
- `code = 0` 表示成功；强制改密为 HTTP 409、业务码 `10001`。
- `expiresAt` 为 Unix 毫秒时间戳。

## 2. 推荐客户端流程

1. `POST /base/captcha` 获取验证码，根据 `openCaptcha` 决定是否展示输入框。
2. `POST /base/login` 登录并保存 `data.token`、`data.expiresAt`。
3. 若 `data.needChangePassword=true`，先完成改密；此状态下 JWT 只允许改密、获取用户信息和注销。
4. `GET /user/getUserInfo` 获取最新资料、角色、部门和岗位。
5. 头像先上传，再把返回的 `data.file.url` 提交到 `PUT /user/setSelfInfo`。
6. 退出时调用 `POST /jwt/jsonInBlacklist`，然后清理本地 token 和用户缓存。

## 3. 公开接口

### 3.1 获取验证码

`POST /base/captcha`，无需 JWT，无请求体。验证码答案默认有效期约 180 秒；登录失败次数按客户端 IP 计数，达到安全配置阈值后强制校验。

```json
{
  "code": 0,
  "data": {
    "captchaId": "验证码标识",
    "picPath": "data:image/png;base64,...",
    "captchaLength": 6,
    "openCaptcha": true
  },
  "msg": "验证码获取成功"
}
```

登录时原样提交 `captchaId` 与用户输入的 `captcha`。验证码错误或过期后应重新获取。

### 3.2 用户登录

`POST /base/login`，无需 JWT。

```json
{
  "username": "admin",
  "password": "******",
  "captchaId": "验证码标识",
  "captcha": "123456"
}
```

验证码未开启时两个验证码字段可为空；开启时必须填写。失败信息包括账号锁定、验证码错误、用户名或密码错误、用户被冻结。

成功响应：

```json
{
  "code": 0,
  "data": {
    "user": {
      "id": 1,
      "uuid": "用户UUID",
      "userName": "admin",
      "nickName": "昵称",
      "headerImg": "头像地址",
      "authorityId": 888,
      "authority": {},
      "authorities": [],
      "departments": [],
      "positions": [],
      "phone": "",
      "email": "",
      "enable": 1
    },
    "token": "JWT",
    "expiresAt": 1760000000000,
    "needChangePassword": false
  },
  "msg": "登录成功"
}
```

## 4. 登录后接口

### 4.1 获取当前用户信息

`GET /user/getUserInfo`（需要 JWT）。响应中的 `data.userInfo` 为最新用户对象。登录成功和资料修改后建议调用一次。

### 4.2 修改当前用户资料

`PUT /user/setSelfInfo`（需要 JWT）。昵称、手机号、邮箱、头像均可按需提交：

```json
{
  "nickName": "新昵称",
  "phone": "13800000000",
  "email": "user@example.com",
  "headerImg": "/uploads/file/avatar.png"
}
```

成功仅返回 `{ "code": 0, "data": {}, "msg": "设置成功" }`。当前后端没有短信/邮件验证码校验接口；个人页中的“获取验证码”只是本地倒计时，客户端不要将 `code` 当作服务端凭证。

### 4.3 修改密码

`POST /user/changePassword`（需要 JWT）：

```json
{
  "password": "旧密码",
  "newPassword": "新密码"
}
```

服务端校验旧密码和密码复杂度。确认密码字段只属于客户端校验，不要提交 `confirmPassword`。成功后建议清理旧登录态并重新登录。

### 4.4 注销当前 JWT

`POST /jwt/jsonInBlacklist`（需要 JWT，无请求体）。服务端将当前 token 加入黑名单并清理 Cookie；客户端应清理本地 token、用户信息和路由缓存。

### 4.5 强制改密状态

登录返回 `needChangePassword=true`，或私有接口返回 HTTP `409`、业务码 `10001` 时，跳转改密页面。改密完成前仅允许：

- `POST /user/changePassword`
- `GET /user/getUserInfo`
- `POST /jwt/jsonInBlacklist`

## 5. 头像上传

### 5.1 上传文件

`POST /fileUploadAndDownload/upload`（需要 JWT，`multipart/form-data`）。

- `file`：必填文件字段。
- `noSave=1`：可选查询参数，不保存媒体记录；头像通常使用默认 `noSave=0`。
- `classId`：可选表单字段。

成功响应的 `data.file` 包含 `id`、`name`、`url`、`size`、`mime`、`md5` 等字段。将 `data.file.url` 原样写入 `headerImg`，再调用 `setSelfInfo`；本地存储可能是相对地址，OSS 部署可能是完整 HTTPS 地址。

## 6. 后台账号管理（非普通用户自助流程）

| 接口 | 用途 | 说明 |
|---|---|---|
| `POST /user/admin_register` | 创建用户 | 需要 JWT/Casbin；字段含 `userName`、`passWord`、`nickName`、`authorityId`、`authorityIds`、`phone`、`email`、`headerImg`、`enable`。 |
| `POST /user/resetPassword` | 管理员重置密码 | 需要 JWT/Casbin；请求 `{ "ID": 1, "password": "新密码" }`。 |
| `PUT /user/setUserInfo` | 管理员编辑指定用户 | 需要 JWT/Casbin；请求必须包含目标用户 `ID`，可更新昵称、头像、手机号、邮箱、启用状态及角色。 |

普通客户端始终使用 `setSelfInfo`，不要暴露上述管理员接口。

## 7. 错误与安全处理

- 不在日志、埋点或崩溃上报中记录密码、JWT、验证码原文。
- HTTP 401：清理本地登录态并回到登录页。
- HTTP 409/`10001`：进入强制改密流程，不要按普通网络错误重试。
- 头像上传失败时不要覆盖已有 `headerImg`；资料更新失败时可保留 `file.url` 待重试。
- 客户端应使用 HTTPS，并对 `expiresAt` 做过期判断。
